## 一、方案 A 是什么、为什么是它

M1 的数据从哪来，当时给你两个选项：

- **A 方案（本次采用）**：继续由人维护 `seed-packs/external-sources/README.md` 第六节的台账表格，产品在**构建期**把这节解析成一份 JSON 快照提交进仓库，前端只读这份快照渲染。台账仍是一手真相源，产品只是它的镜像。
- B 方案（未采用）：先把台账结构化进数据库新表，产品读表。M0 刚把 9 个资产导进本机库，再加一张台账表意味着双写、迁移、两套语义要同步，M1 阶段不划算。

**为什么 A 对 M1 更稳**：台账是「来源地图 + 作业指引」，本来就是人读人维护的 Markdown；M1 只要求「产品里能看到」，不需要可编辑、不需要写回。构建期生成 JSON 让本地/云端都读得到（云端模式浏览器读不到仓库文件，见 `docs/engineering-map.md` 两种运行模式），且不引入新表、不碰迁移——符合「防过度设计」梯子第 1～5 阶。

> 上限与升级路径：A 方案的视图是 README 的镜像，README 改了要重跑生成脚本才会更新（T1 脚本 + `check:fast` 兜住）。等 M2 要接腾讯生态、台账变频繁变动时，再评估是否升级到 B（结构化入表）。这条简化已在代码注释里标注。

## 二、做什么 / 不做什么

### 做（M1）

1. **只读视图「采集台账」**：产品里新增一个只读页面，渲染台账全部来源，每条显示：来源名、类型（Skills／MCP／资讯流）、状态、来源链接（可点）、处置结论（已采／不采／暂缓／已安装）、落到哪条资产、核实日期、备注。
2. **来源详情抽屉**：点一条来源，展开看完整字段；「落到哪条资产」若已导入库内，显示资产标题并支持跳转到该资产详情；若未导入，显示资产 ID 文本。
3. **「是否已编译进 AGENTS.md」状态列**（M1 判定规则，见第三节）：规则类资产按库内状态推导（active 标「已编译候选」、candidate 标「未编译／候选」），文档类资产统一标「知识库资产（不编译进 AGENTS.md）」。
4. **采集合规检查（能跑的检查）**：一个脚本扫本机库里所有外部来源资产，验证 SOP 四条硬约束——
   - 外部资产默认 `candidate`；
   - 可信度初始 `hypothesis`；
   - 必须留 `source_references`；
   - 未经人工确认不许升 `active`（即 `authority:false` / `role:"source"` 才合规，已 `active` 且无确认记录的判违规）。
   输出不合规清单；**只读，不改数据**。

### 不做什么

- 不在产品里新增／编辑／删除台账（M1 只读，台账仍由人在 README 维护）。
- 不新建数据库表（走 A 方案，JSON 快照）。
- 不把外部资产自动编译进 `AGENTS.md`（一律先 candidate，与立项「不做什么」一致）。
- 不做 M2（采腾讯生态、双向同步）——M2 仍需你的腾讯生态账号与素材。
- 不在云端模式实时读仓库文件（只读构建期生成的 JSON 快照）。

## 三、产品变化（用户能看到什么）

新增一个**只读视图「采集台账」**，与现有「公共资产／文档／代码」并列放在顶部导航（若你觉得太重，可降级为「公共资产 → 更多 → 外部来源采集（只读）」——设计门确认时定）。

视图内两部分：

```
┌──────────────────────────────────────────────────────────────────┐
│ 采集台账（只读）                              [运行采集合规检查]   │
├──────────────────────────────────────────────────────────────────┤
│ 来源         类型    状态      处置结论   落到哪条资产   是否编译   │
│ S1 super…    Skills  已采集    已采       RULE-…001     已编译候选 │
│ S7 产品…     Skills  已采4/剩16 其余16见表 MTH-…/REF-…  知识库资产 │
│ …（共 23 条，与 README 第六节一致）…                                  │
└──────────────────────────────────────────────────────────────────┘
点一条 → 右侧抽屉：来源链接 / 类型 / 状态 / 处置结论 / 落到哪条资产
        （可跳转）/ 核实日期 / 备注 / 是否编译判定依据
```

「是否编译进 AGENTS.md」M1 判定规则（写进代码注释，明确上限）：
- 台账「落到哪条资产」为空（—）→ 标「—（未提炼资产）」。
- 落点资产在库内且 `assetType==="rule"`：库内 `status==="active"` → 标「已编译候选（待你确认）」；`candidate` → 标「未编译／候选」。
- 落点资产为文档类（`role:"source"`／`authority:false`）→ 标「知识库资产（不编译进 AGENTS.md）」。
- 落点资产在库内找不到 → 标「未导入库（仅台账记录）」。

> 这是 M1 的简化推导：不解析 AGENTS.md 正文做精确编译比对（那是 M2 或更后的事）。M1 阶段外部资产全部 candidate/知识库，视图会如实显示「未编译／知识库资产」，机制留好等资产被人工确认升 active 时自动变「已编译候选」。

## 四、交互路径（一步步怎么走）

**路径 1：看整体采集进度**
1. 打开产品 → 顶部点「采集台账（只读）」。
2. 看到台账表格，默认按来源顺序列出全部 23 条。
3. 每条一眼看到「处置结论」与「是否编译」两列，知道采到哪、哪些还没进编译。

**路径 2：追溯一条来源的落点**
1. 在表格点任意一条来源（如「S7 产品经理方法技能」）。
2. 右侧抽屉展开，显示该来源的完整字段（来源链接可点开原仓库／官方页）。
3. 看「落到哪条资产」：若已导入库（如 `MTH-TEAM-OKR-001`），点标题跳转到该资产详情；若未导入，显示资产 ID 文本。
4. 看「是否编译」判定与依据。

**路径 3：跑一次采集合规检查**
1. 在视图右上点「运行采集合规检查」。
2. 脚本扫本机库全部外部来源资产，按四约束校验。
3. 结果以清单展示：合规项绿色通过；违规项红色列出「哪个资产、违反哪条约束、当前值」。
4. 全部只读，不修改任何数据；可重复运行。

> 注：路径 3 的检查脚本在**本机模式**下扫 `.data/prompts.sqlite`；云端模式因浏览器读不到库，M1 阶段检查通过 `npm run` 脚本在本地跑（与 M0 导入脚本同一执行方式），不在产品内嵌按钮做写库。产品内「运行采集合规检查」按钮在 M1 可先作为「触发本地脚本」的提示入口，真实执行在终端；如你希望产品内直接出结果，列为 M1 的待定增强，确认时拍板。

## 六、数据与产品行为影响

- **数据源（A 方案）**：只读解析 `seed-packs/external-sources/README.md` 第六节表格。新增生成脚本 `scripts/generate-external-sources-ledger.ts`，读该节 → 写 `src/data/external-sources-ledger.json`（提交进仓库）。前端 `import` 这份 JSON 渲染，**本地／云端都能读**。
- **不新增数据库表**：台账数据不进 `assets`／新建表；已在库的 9 个外部资产（role:source / authority:false）照旧，视图通过「落到哪条资产」ID 与库内资产做只读关联，不写库。
- **「是否编译」判定**是前端只读派生，不持久化（见第三节规则），上限已在注释标明。
- **采集合规检查**只读取本机库（`node:sqlite`），不改任何行；可重复执行，跑两次结果一致。
- **运行模式差异**：视图在本地／云端都读 JSON 快照（一致）；合规检查脚本在本地模式跑（云端模式 M1 不内嵌写库，见第四节路径 3 注）。
- **数据对齐注意（落点跳转）**：台账「落到哪条资产」用的是规范 ID（`MTH-TEAM-OKR-001`、`REF-PRIORITIZATION-001`、`RULE-PREMORTEM-001` 等），但 M0 导入本机库时 `scripts/import-leads3-docs.ts` 用的是 slug 化库内 ID（`document-team-method-mth-team-okr-001`），**两者不是同一字符串**。M1 的「点 ID 跳转到资产详情」要做一层映射，否则点不动。两种走法，设计门确认时选：
  - **a（推荐，最小改动）**：T1 生成脚本顺带读对应源文件（`docs/team-methods/*.md`、`docs/reference/*.md`）frontmatter 里的规范 `id`，把「规范 id + 标题」一起写进 JSON；视图按规范 id 在库内资产 `metadata` 里找匹配（M0 导入时若没存规范 id，则先给导入脚本补一个 `canonicalId` 字段，属 M0 的小收尾，不改台账）。匹配到就深链，匹配不到显示规范 id 文本。
  - **b（文本优先）**：M1 只显示规范 id 文本 + 标题，不做深链；等 M2 结构化入表时再统一对齐。
- **对现有界面影响**：仅新增一个只读视图入口与一份 JSON 快照文件；不动「公共资产／文档／代码」既有逻辑（沿用档，按已有风格做，验收查风格一致性）。

## 七、验收标准（每条都能用一次操作判定）

1. 产品「采集台账」视图列出全部来源，行数 = README 第六节台账行数（当前 23）。
2. 点开任意来源，抽屉字段（来源链接／类型／状态／处置结论／落到哪条资产／核实日期）与 README 对应行逐字段一致。
3. 「落到哪条资产」已导入库内的，可跳转到该资产详情；未导入的显示资产 ID 文本，不报错。
4. 「是否编译」列按第三节规则标注：候选／知识库资产显示「未编译／候选」或「知识库资产」，不谎报「已编译」。
5. `npm run check:leads3-compliance` 能扫出全部外部来源资产，列出违反四约束（非 candidate／非 hypothesis／缺 source_references／未确认就 active）的项；当前 9 个 M0 资产 0 违规。
6. 视图全只读：界面不出现新增／编辑／删除入口（采集台账无写操作按钮）。
7. 生成脚本可重复执行：改 README 第六节后重跑，JSON 与 README 一致；连续跑两次产物无差异（幂等）。
8. 边界：台账某行缺字段时视图不崩，缺字段显示「—」；台账为空时显示空态提示而非报错。
