# 从「沉淀」到「立项」：这条链路现在断在哪

## 你要走的路（我复述一遍，确认理解对不对）

```
① 沉淀回流        把本产品开发过程中积累的规则、模板、文档，整理进「公共资产」
② 项目接入        把本产品这个项目自己的资产，完整接进产品（含文档、图谱、验收、发布）
③ 立项准备        拿新项目的基本需求，从公共资产里挑/组合，构建新项目的开发体系与全部模板
④ 持续分流        做的过程中不断沉淀：法则级内容 → 公共资产；项目专属 → 项目里
```

下面把这条路按现在的产品走一遍，标出**能走**和**断**的地方。

## 逐段走查

### ① 沉淀回流（项目 → 公共）

| 步骤 | 现在怎么做 | 结果 |
| --- | --- | --- |
| 把项目里的一条规则变成公共规则 | 只能手动在公共资产里新建一条、再把内容贴过去；或者把项目资产打包成规则包，再装到公共库 | **断**（G1） |
| 公共规则改好了，让各个项目跟上 | 装进项目的那一刻是**复制**，之后两边各自独立，产品不会提示"上游更新了" | **断**（G2） |
| 一眼看出哪些该进公共、哪些重复、哪些只在某个项目里 | 没有这样的视图，只能自己一条条翻 | **断**（G3） |

### ② 项目资产接入

| 步骤 | 现在怎么做 | 结果 |
| --- | --- | --- |
| 项目文档（需求/设计/验收/接口）进项目 | 本轮刚补：导入工程 →「项目文档」，选 Markdown 原样入库 | **通**（本轮） |
| 代码结构进项目 | 导入工程 → 分析代码目录 → 模块/接口节点 | **通** |
| 数据库结构进项目 | 导入工程 → 数据库 Schema | **通** |
| 文档挂到对应节点上 | 只能一个个进节点编辑器建关系 | **半通**（v2.13.0 补批量） |
| 让 AI 批量把资产灌进项目 | MCP 只有单条新增/编辑，没有批量工具 | **断**（G5） |
| 本地与云端之间搬数据 | 导出→导入，或 `npm run sync:from-cloud` | **通**（本轮） |

### ③ 立项准备（公共 → 新项目）

| 步骤 | 现在怎么做 | 结果 |
| --- | --- | --- |
| 把公共资产带进新项目 | 项目视图 →「从公共资产库挑资产」，自己一份份勾 | **通但不省事**（G7） |
| 知道"这个等级的项目该有哪些文档/规则" | 工程基线会列"已有／还缺" | **通** |
| 按这套要求**自动推荐**该装哪些公共资产 | 没有：基线知道缺什么，不知道哪份公共资产能补上 | **断**（G7） |
| 立项时生成一整套提示词（PRD、技术档案、工程基线…） | 只有技术档案有一个可复制的提示词（本轮补） | **断**（G8） |
| 把 AI 产出的内容回填进产品 | 技术档案：复制提示词→贴给 AI→贴回来（本轮补）；PRD/工程基线还没有这条路 | **半通**（G9） |
| 把新项目的开发体系导出成可交付的一包 | 只能逐个复制/下载 | **断**（G12） |

### ④ 持续分流（做的过程中）

| 步骤 | 现在怎么做 | 结果 |
| --- | --- | --- |
| 规则编译成 AGENTS.md/START_PROMPT.md | 通；两条产物的范围差别本轮在面板里说清了 | **通** |
| 编译产物存回项目 | 每次保存都**新建**一条文档资产，反复编译会攒出多份同名文档，不能"更新这一份" | **断**（G10） |
| 节点和文档互相挂钩，形成影响分析 | v2.13.0 在做 | **进行中** |
| 法则级内容自动分流到公共、项目内容留在项目 | 全靠手工判断 | **断**（G11） |

## 八个断点，按建议的处理顺序

| 编号 | 断点 | 影响 | 建议做法 | 放哪一版 |
| --- | --- | --- | --- | --- |
| G1 | 项目资产没有"提升到公共"的一键动作 | 沉淀回流全靠手工复制，容易两边分叉 | 资产详情加「提升为公共资产」：复制一份到公共库、记下来源、可选把项目那份改成引用 | v2.14.0 |
| G2 | 公共库更新后项目里的副本不知道 | 公共规则改了，老项目继续用旧的 | 项目里的资产标"来自公共库 X，上游有更新"；给「看看差异 / 拉取新版」 | v2.14.0 |
| G3 | 没有沉淀体检 | 看不出哪些该进公共、哪些重复 | 一个跨项目视图：只在项目里出现的高价值规则、与公共库内容重复的、长期没更新的 | v2.14.0 |
| G7 | 立项时不知道该装哪些公共资产 | 新项目起步靠人一份份挑 | 工程基线的每条要求后面接"用这份公共资产补上"，一键装进项目 | v2.15.0 |
| G8 | 没有立项提示词包 | 立项那套动作（PRD、技术档案、工程基线）每次都从头想 | 内置一组立项提示词（需求澄清、PRD、技术档案、验收清单），按项目规模给不同组合 | v2.15.0 |
| G12 | 不能整包导出项目开发体系 | 交付给外部协作者时要一个个复制 | 一键导出：AGENTS.md、START_PROMPT.md、技术档案、工程文档、模板清单 | v2.15.0 |
| G10 | 编译产物会重复累积 | 文件越攒越多，不知道哪份是最新 | 同名产物默认"更新这一份"（保留版本记录），要新建时显式选 | v2.15.0 |
| G5 | MCP 没有批量入库 | AI 只能一条条写 | MCP 加"按目录批量导入文档"和"按批次导入节点"，沿用导入工程的校验 | 单独立项 |
| G11 | 公共/项目的自动分流 | 判断全靠人 | 先做 G1/G2/G3 的手工闭环，攒够判据再谈自动 | 单独立项 |

## 结论

- **现在能走通**：项目资产接入（②，本轮补完）、规则编译（④ 前半）。
- **最缺的两条主线**：
  1. **项目 → 公共的回流**（G1/G2/G3）——你现在最想做的事恰好卡在这里：把本产品的沉淀"升"到公共库，而且之后要能持续同步。
  2. **公共 → 新项目的成体系起步**（G7/G8/G12）——从"缺什么"升级到"该装什么、怎么一键装好、怎么整包交出去"。
- **建议节奏**：v2.13.0（在做，收尾关联录入）→ v2.14.0「沉淀回流」→ v2.15.0「立项起步包」。MCP 批量与自动分流单独立项，因为它们要动写入通道和判据。
