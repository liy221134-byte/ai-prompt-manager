## 一、产品定位

**不是 LMS。** LMS 在行业里等于课程管理平台（排课、学分、进度条、证书）。这套东西是训练闭环，形态完全不同。

**一句话定位**：把一次性对话产出的学习计划，变成每天能执行、可追踪、能复测的系统。

**核心分工（这条决定了整个架构）**：

| | 谁 | 产出 |
| --- | --- | --- |
| **想** | AI（WorkBuddy 侧的会话） | 主题包计划文件（yaml） |
| **跑** | 本产品 | 执行、追踪、出题、复测、回流 |

```
AI 出计划 → 产品导入 → 产品执行/追踪 → 产品出数据
      ↑                                    │
      └────────── 下一版计划 ←──────────────┘
```

**产品只在三个点使用 AI**（都是「每次输入不同、需要判断」的环节）：诊断归因、自适应出题、素材表生成/知识图谱检查。其余全部是确定性代码。

**产品真正的价值不是「生成计划」，是「让计划被执行下去」。**

## 三、对照调研结论，缺的是哪几环

| 序 | 方法（调研结论） | 现状 | 缺口 |
| --- | --- | --- | --- |
| 1 | 先测再学（诊断） | 无任何诊断机制 | **全缺** |
| 2 | 搭学习阶梯（能力五级） | 只有 6 周**时间**大纲 | 缺能力维度结构 |
| 3 | 20% 核心前置 | 分类无权重 | 缺 `weight` |
| 4 | 连续拷问（自适应） | 静态随机抽题 | 缺自适应引擎 |
| 5 | 一页素材表 + 手绘知识图谱 | 无 | **全缺** |
| 6 | 信号筛选 | 无 | 缺 |

**最关键的一条**：第 1 和第 5 是整套方法的入口和出口，现在两头都是空的，
所以现有模块再完善也只是「练得多」，不会「学会」。

## 四、第一个版本做什么（M0：数据地基）

只做数据层，五件事：

1. **定死主题包 schema**（yaml 规格，附录有草案）。这是 AI 与产品的接口契约。
2. **迁移补字段**：`practice_questions` 加 `knowledge_point` / `source` / `source_url`；
   `practice_attempts` 加 `duration_ms` / `context`。
3. **新建四张表**（本版只建表、不写业务逻辑）：`learning_topics` / `learning_stages` /
   `knowledge_points` / `learning_diagnostics`。
4. **给 119 题回填元数据**：`difficulty` 填真实值、`knowledge_point` 全部打上、
   `source` 统一填 `manual`（现有题都是手工/历史生成，先归这一类）。
5. **主题包导入器**：读 yaml → 写入 `learning_topics` / `learning_stages` / `knowledge_points`。
   命令行脚本，无界面。

## 五、M0 明确不做什么

- **不改任何界面**（一个页面都不动，`/practice` 保持原样）
- 不做诊断、不做自适应出题、不做素材表、不做知识图谱
- 不改现有练习流程（分类/题型/状态筛选、错题重练、两栏布局、随机练习）
- 不做多用户、权限、分享（已定：只给自己用）
- 不做中项主题包的内容（那是 M1 的输入，见第九节待拍板 3）

**为什么第一个版本不出界面**

按 `docs/development-rules.md`：「如果一次改动同时动了数据结构和使用界面，
或者要改两条以上的链路，就应该拆成两次发布。」

M0 只动数据，可以独立验收；界面留到 M1。先出界面会把范围撑起来，
而 schema 没定死之前，界面做出来大概率要返工。

## 七、怎么验收（M0，逐条可判定）

1. 迁移在本地 / Preview 跑通，无报错。
2. `select count(*) from practice_questions where knowledge_point is null` → **0**。
3. `difficulty` 不再全部是 `medium`（至少有 `easy` / `hard` 两档出现）。
4. 四张新表存在且可读。
5. 用一份示例主题包跑导入脚本，`learning_topics` 与 `learning_stages` 能查出来，
   层级关系正确（stage 挂对 topic）。
6. **现有练习功能不回归**：`/practice` 能打开、能答题、能看错题、能按分类/题型/状态筛选。
7. `npm run check:fast` 通过。

> **必须提前说清：M0 你在界面上看不到任何变化。**
> 验收靠我贴出来的查询结果。这是刻意的——地基阶段不出界面，避免范围失控；
> 而且 schema 没被真实数据验证之前，界面一定会返工。

## 八、分里程碑计划

> **口径**：`v4` 是产品线版本号；`M0—M4` 是 v4 线内的里程碑（与项目既有习惯「体系治理 M0」「v3 M0」一致）。

| 版本 | 范围 | 你能感知到什么 |
| --- | --- | --- |
| **M0（本版）** | 数据地基 + schema + 导入器 | 无界面变化，只有查询结果 |
| **M1** | 计划导入 + 按阶梯出题（输入 = 中项主题包） | 能选主题、看阶梯、按阶段刷题 |
| **M2** | 诊断闭环（取证 + AI 归因 + 人确认 + 复测） | 能做入学测、看能力雷达、看到进步 |
| **M3** | 自适应出题 + 一页素材表 | 系统会追着你问；模块学完自动出一页纸 |
| **M4** | 手绘知识图谱检查 | 画完拍照上传，AI 指出遗漏 |

**顺序说明**：先「跑」（M1）再「诊」（M2）。
理由：诊断的 AI 归因需要作答数据做素材；没有 M1 的积累，M2 无料可归。

## 九、已拍板结论（2026-10-27）

### 1. 版本号 → **v4**
学习系统独立编号，不并入 v3。

### 2. M0 不出界面 → **确认不出**
理由：schema 没被真实数据验证之前，预览页做出来大概率返工；而 M1 的主界面天然会包含它，现在做是重复劳动。
代价：M0 交付时你在界面上看不到任何变化，验收靠我贴出的查询结果（见第七节）。

### 3. 中项主题包 → **现在同步做**
定位为**内容资产，不进代码库**（先放 WorkBuddy 侧工作区，后续需要时再作为 seed 数据单独入库）。

目的不是「多一份资料」，是用真实主题把 schema 跑一遍，**提前暴露缺口**——
比如 stage 之间要不要依赖关系、题目与知识点是一对多还是多对多、一个知识点跨多个 stage 怎么办。
空写 yaml 一定漏字段。

**因此顺序是**：先出中项主题包 → 用它反过来校 schema → schema 定稿 → 写《设计 + 任务清单》。
