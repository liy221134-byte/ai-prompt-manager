## 一、M2 的定位为什么改写

原立项 M2 写的是「接腾讯生态采集 + 补双向同步」。2026-09-29 晚复核后判定：**这个写法把手段写成了目的**。

- 「采腾讯生态」的真实意图是「把外部生态的规则采进资产库」，腾讯只是当时想到的第一个来源。
  产品价值不在「支持腾讯」，而在「任何一家的 MCP / Skills 都能进同一条采集流水线」。
- 「双向同步」是市场仓库时代的遗留目标（`E:\AI资产市场` → 库，单向）。它和「生态采集」
  是两件事，混在一个里程碑里会让 M2 变成两个不相干的活。

**M2 改写后的一句话定位**：把「外部生态采集」从一份人手工维护的 Markdown 台账，变成产品里
**能登记、能发起、能追踪、能走到编译候选**的流程；来源不限于任何一家厂商。

## 二、三个核心设计判断

### 判断 1：采集记录进库，**用现有资产体系承载，不新开表**

M1 走的是 A 方案（台账仍是 README，产品读构建期生成的 JSON 快照），设计稿当时就写明这是
过渡形态，并预留了升级路径：「等 M2 要接生态、台账变频繁变动时，再评估是否升级到 B
（结构化入表）」。**M2 的触发条件到了**——要新增记录、要改状态、要跟踪进度，手改 README 不成立。

但「结构化入表」不等于「新建一张 `source_records` 表」。这里按防过度设计梯子逐阶检查：

| 阶 | 检查 | 结论 |
| --- | --- | --- |
| 能不做吗 | M2 明确要新增/更新记录，不能不做 | 否 |
| 能用最简单的表达吗 | 现有 assets 体系已支持 10 种资产类型、任意 `metadata` | 可以 |
| 能不改数据模型吗 | `documentType` 是自由字符串，`metadata_json` 是 jsonb（云端列已存在） | **能，零迁移** |

**落地方案**：一条采集记录 = **一条 document 资产**，落在公共资产库（默认项目）：

- `assetType: "document"`、`metadata.documentType: "采集记录"`
- `metadata.role: "source"` + `authority: false`（沿用 M0 就定下的「外部来源、未采信」表达）
- `metadata.collection`：结构化字段（生态／类型／处置结论／落点／核实日期／备注／确认记录）
- 正文 = 人可读的 Markdown 说明（为什么要采、提炼角度、注意什么）

**白拿的现成能力**（这是选它的真正理由，不是省事）：

| 能力 | 现成在哪 |
| --- | --- |
| 增删改查 | `/api/assets`（GET 列表 / POST 新建）、`/api/assets/[id]`（PUT 更新）、`src/lib/prompt-api.ts` |
| 版本记录 | 每次保存写一条不可变版本，`save_asset` RPC 已实现 |
| 云同步 / 备份 / 导入导出 | 已有链路，不用为「采集记录」单开一条 |
| 资产详情、深链跳转 | M1 的落点深链 `/?asset=<id>` 已在用 |
| 权限与账号 | 复用 RLS 与登录体系，不新增鉴权面 |

**代价**：文档资产没有「候选／假设」这对规则专有概念（M0 已踩过这个坑），所以记录的「未采信」
仍用 `role:"source"` + `authority:false` 表达——与 M1 合规脚本的口径一致，不引入第二套语义。

**如果选新开表**：要写迁移、写 RLS 策略、写云端同步分支、写一套新的 CRUD 与备份兼容，
还要再写一套详情界面。收益只有一个「名字更正规」。→ **建议不选。**

### 判断 2：产品负责「发起 + 记录 + 把关」，智能体负责「执行」

「我给你说采集的需求你就能找到目标资产」这句话里，**「你」是智能体（WorkBuddy / Codex），不是产品**。
产品内没有联网搜索能力，也不应该加（成本、稳定性、以及不联网的模型给出的来源大概率是幻觉，反而害事）。

所以这条能力落地为：

1. 你在产品里写一句采集需求（例：「采 Figma 官方 Skills 里的设计规范类规则」），
   或直接给一个压缩包 / 仓库地址；
2. 产品按这份需求生成一份**采集任务单**——就是 `seed-packs/external-sources/README.md`
   第五节那份 SOP 话术的参数化版本（目标来源、提炼要求、去重口径、合规硬约束、回填格式），
   可一键复制；
3. 你把它交给 WorkBuddy / Codex 执行（智能体有联网与读仓库的能力，这正是它的活）；
4. 执行结果回填成：一条采集记录 + 若干候选资产；
5. **产品在人工确认点停下来**：候选资产默认 `candidate` / `draft` + `hypothesis` + 带来源，
   等你确认才升 `active`。

这条判断同时决定了 M2 不做「一键自动采集入库」——与立项「不做未经人工确认的自动入库」一致。

### 判断 3：压缩包入口复用已有的文档包导入链路

项目里已经有这条链路，且是真跑过的：ZIP 上传 → `api/ai/extract-package` 提取 →
`source-package-import-dialog` 预览 → `planSourcePackageCreation` 确认落库（v2.1.1 交付）。

**M2 的压缩包入口 = 在这条链路上加一个「外部采集」模式**（不是新造一条）：

- 提取出的规则强制 `status: draft` + `confidence: hypothesis` + 记来源摘录（现有代码已把
  规则落成 `draft`，只差信任度与来源两项）；
- 落库同时自动生成一条**采集记录**，「落到哪条资产」指向这批新资产；
- 上传的原始 ZIP 仍留一条 `source_package` 资产，可追溯。

## 三、做什么 / 不做什么

### 做

**M2.0（本次，地基 + 闭环）**

1. **采集记录进库**：新增 `documentType: "采集记录"` + `metadata.collection` 字段；
   23 条 README 台账迁成 23 条记录（幂等脚本，可 `--dry-run`）。
2. **视图改读库**：`/external-sources` 从读 JSON 快照改为读库内采集记录（本地／云端同一套
   `/api/assets` 通道，表现一致）；保留 M1 的「是否编译」五档推导与合规检查入口。
3. **记录可新建 / 可编辑**：轻量表单（来源、类型、生态／厂商、来源链接、处置结论、落点、
   核实日期、备注）。台账不再只能靠人手改 Markdown。
4. **走通到编译候选（本版核心价值）**：候选资产经确认动作升 `active` + 记**确认记录**
   （谁、何时、凭什么）→ 自动进入规则编译抽屉的候选集 → 可编译出 `AGENTS.md` 草稿；
   视图「是否编译」列同步从「未编译／候选」变为「已进编译候选（待确认发布）」。
5. **合规判据演进**：第四约束由「active 必须是 verified」改为「**active 必须有确认记录**」。
   理由见第七节第 3 条——原判据把「人工把关」和「实战验证」两件事压成了一件。
6. **顺带修正一处措辞**：M1 五档里 `compiled_candidate` 的标签写的是「已编译候选（待你确认）」，
   与事实不符（还没编译，只是够格进候选）→ 改成「已进编译候选（待确认发布）」。
7. **拿一条真实外部技能走完全程**（立项验收标准第 4 条）。

**M2.1（下一步，两条入口 + 生态维度）**

8. **说需求 → 生成采集任务单**（可复制话术，参数化）。
9. **给压缩包 → 进采集流程**（复用文档包导入链路的「外部采集」模式）。
10. **生态／厂商维度**：来源登记加生态字段，视图可按生态筛选／分组。

**M2.2（方向已定，不塞进本版）**

11. 双向同步（库里的改进回写正本 / 市场仓库）。它是独立议题，与生态采集无关；
    且要跨仓库写权限（同 T6 技能仓库去副本那条，卡 token）。建议单独立项。

### 不做什么

- **不做产品内联网自动检索**：没有搜索能力，也不引入（理由见判断 2）。
- **不自动入库、不自动升 active**：候选一律要人工确认，与立项一致。
- **不新开数据库表**：用现有 assets + metadata（判断 1）。
- **不接管任何厂商账号或权限**：只读沉淀，不做写回。
- **不做爬虫式批量抓取**：一次一条来源、读完提炼确认再开下一条（README 采集原则第 1 条）。
- **不把外部资产直接编译进 `AGENTS.md`**：仍走「确认 → 进候选 → 你决定是否编译」。
- **不在云端写采集记录**：M2.0 先只写**本机库**，云端由你点头后用现有 `npm run sync` 推。
  （沿用 M0 / M1 的做法——写入资产库的动作逐次点头。）

## 四、产品变化（用户能看到什么）

**入口不变**：顶部并列的「采集台账」（M1 已上线），仍与公共资产／文档／代码同级。

**视图从「只读镜像」变成「活的台账」**：

```
┌────────────────────────────────────────────────────────────────────────┐
│ 采集台账        [新建采集]  [生成采集任务单] [运行采集合规检查]         │
├────────────────────────────────────────────────────────────────────────┤
│ 生态  来源        类型    处置结论   落到哪条资产      是否编译          │
│ 社区  S1 super…   Skills  已采（部分）PLAYBOOK-DEBUG-001 已进编译候选…   │
│ 社区  S2 anthrop… Skills  未采集      —                  —（未提炼资产） │
│ 社区  S7 产品…    Skills  已采 4/16   MTH-…/REF-…(9 条)  知识库资产      │
│ 腾讯  待采（新登记）MCP  暂缓        —                  —                │
│ …（共 23 条 + 你新增的）…                                               │
├────────────────────────────────────────────────────────────────────────┤
│ 点一条 → 抽屉：来源链接 / 生态 / 处置结论 / 落到哪条资产（可跳转）/      │
│           核实日期 / 备注 / 是否编译判定 / [编辑]                        │
└────────────────────────────────────────────────────────────────────────┘
```

**新增两处动作**（M1 时全只读，M2 有写入口了，都只在人工点击后发生）：

- 「新建采集」：登记一条新来源。
- 「生成采集任务单」：把你写的采集需求变成一段可复制的话术。

**编译候选那一环在既有界面里体现**，不新增页面：候选资产在资产详情里确认后升 `active`，
规则编译抽屉的候选集里就能看到它，台账视图的「是否编译」列同步变档。

## 五、交互路径（一步步怎么走）

**路径 1：看整体进度并追溯到落点（M2.0）**
1. 打开产品 → 点顶部「采集台账」。
2. 看到全部来源（含你新登记的），每行有生态、处置结论、是否编译。
3. 点任意一条 → 右侧抽屉显示完整字段；已入库的落点显示「打开资产」按钮，点开跳到资产详情。

**路径 2：登记一条新来源（M2.0）**
1. 视图点「新建采集」→ 填来源名、类型（Skills／MCP／资讯流）、生态（开源社区／腾讯／阿里／
   字节／OpenAI／Anthropic／Google／本机／其他）、来源链接、处置结论（已采／不采／暂缓／已安装）、
   落点、核实日期、备注。
2. 保存 → 库里多一条「采集记录」文档资产，视图立刻出现这一行。
3. 后续改动点行内「编辑」，改动写版本记录（可回溯什么时候改的、改成什么）。

**路径 3：把一条候选推到编译候选（M2.0，本版核心）**
1. 采来的候选规则在资产库里是 `candidate`（规则）／`draft`（导入的规则），可信度 `hypothesis`，
   带来源摘录——这是 M1 合规检查盯着的那四条。
2. 你看过内容、点了确认（在资产上做「确认」动作：记确认人、时间、依据）→ 资产升 `active`。
3. 规则编译抽屉里立刻能选到它，编译出的 `AGENTS.md` 草稿里含这条规则。
4. 回到采集台账：这条来源的「是否编译」列变成「已进编译候选（待确认发布）」。
5. 每一步都有人工确认点，没有任何一步是自动的。

**路径 4：发起一次采集（M2.1）**
- 4a 给压缩包：视图点「给压缩包」→ 传 ZIP → AI 提取候选 → 预览 → 确认 →
  生成一批候选资产（`draft` + `hypothesis` + 带来源）+ 一条采集记录。
- 4b 说需求：视图点「生成采集任务单」→ 写下需求 → 生成话术 → 复制 → 交给智能体执行 →
  结果回填（智能体写采集记录 + 候选资产，走同一条写入通道）。

## 六、用户故事（产品负责人视角）

> 按 `templates/methods/user-story.md` 格式，每条带可判定验收条件。

**US-1 台账是活的**
- 作为产品负责人，我想在产品里直接新建和修改采集来源，以便不用再手改 Markdown 才能更新进度。
- 验收：点「新建采集」填完保存，视图立刻出现该行；再点「编辑」改处置结论，改动保存后有版本记录。

**US-2 看生态分布**
- 作为产品负责人，我想按生态（开源社区／各家厂商）看采集分布，以便知道哪些生态还没碰。
- 验收：视图能按生态筛选，筛出的行数与登记录数一致；默认「全部」。

**US-3 一条外部资产走通到编译候选**
- 作为产品负责人，我想把一条真实外部技能从采集一路推到编译候选，以便确认这条流水线是通的。
- 验收：该来源的候选资产经确认升 `active` 后，出现在规则编译抽屉的候选集里，
  且采集台账对应行的「是否编译」变为「已进编译候选（待确认发布）」。

**US-4 发起采集不靠记话术**
- 作为产品负责人，我想在产品里给一个压缩包或写一句需求，就能拿到该做的事，以便不用每次
  翻 README 第五节抄话术。
- 验收：给一个含 `SKILL.md` 的 ZIP，能提取出候选并在预览里看到；写一句需求能生成一段
  可复制的话术，含提炼要求、去重口径、合规硬约束、回填格式四段。

## 七、数据与产品行为影响

1. **数据源换代**：M1 是「README 第六节 → 构建期 JSON 快照 → 视图读快照」；M2 改成
   「库内采集记录 → `/api/assets` → 视图读库」。本地与云端读同一套接口，表现一致。
2. **对 M1 已交付东西的处置（要说明，不能装作没发生）**：
   - `scripts/generate-external-sources-ledger.ts` 与 `src/data/external-sources-ledger.json`：
     **退役**（不再作为数据源）。`npm run generate:leads3-ledger` 从 `check:fast` 里摘掉。
   - `tests/external-sources-ledger.test.mjs` 里的「JSON 与 README 一致」类断言：随之退役，
     替换为「采集记录解析与派生」的单测。
   - `src/lib/external-sources-ledger.ts` 的**派生逻辑保留**（五档「是否编译」推导、规范 ID
     抽取），改从库内资产计算——这部分逻辑本身与数据源无关，是 M2 的资产。
   - `seed-packs/external-sources/README.md` 第六节：**保留**，定位改为「人读的作业指引 +
     历史留档」，并加一行说明「产品视图已改读库，本节不再要求与产品同步」。
   - 合规检查脚本 `check:leads3-compliance` **保留**，第四约束判据按第 3 条演进。
3. **合规第四约束的判据演进**：M1 判「`active` 且 `confidence !== "verified"` → 违规」。
   这条把两件事压成了一件——「人工把关」与「真实项目里用过并留证」。
   按 SOP 原文，`provisional` 的语义恰恰是「人工确认过、还没实战验证」，它就该允许 `active`
   （否则「进编译候选」必须先在真实项目里跑一遍，逻辑上倒置）。
   **改为**：「`active` 且**没有确认记录**（`metadata.collection.confirmation`）→ 违规」。
   确认记录由确认动作写入，含确认人、时间、依据。
4. **新增字段（都不需要数据库迁移）**：`metadata.documentType` 取值新增「采集记录」；
   `metadata.collection` 为新对象字段。`assets.metadata_json` 是 jsonb（云端列已存在），
   改的是 TypeScript 类型与校验函数，不写迁移。
5. **写入范围**：M2.0 只写本机库（`.data/prompts.sqlite`）；云端经你点头后用 `npm run sync` 推。
6. **对现有界面影响**：只改 `/external-sources` 一个页面的数据来源与动作，新增一个
   「采集记录」表单组件；不动「公共资产／文档／代码」既有逻辑。
7. **落点深链**：M1 靠「库内资产 `sourceLocation` → 源文件 frontmatter id」建桥。
   采集记录如果落点是库内资产，直接用库内资产 ID 存进 `collection.collectedAssetIds`，
   比 M1 那座桥更直接（M1 的桥保留给历史数据）。

## 八、验收标准（每条都能用一次操作判定）

1. 采集台账视图的行数 = 库内「采集记录」文档资产条数（迁移后应含 README 原有 23 条）。
2. 点「新建采集」填完保存，视图立刻出现该行；刷新后仍在（不是前端假数据）。
3. 点任意一条，抽屉字段与库内记录逐字段一致；落点为库内资产时可跳转资产详情。
4. 「是否编译」按五档正确标注；措辞已由「已编译候选（待你确认）」改为「已进编译候选（待确认发布）」。
5. 走完全程：一条真实外部技能的候选资产经确认升 `active` 后，出现在规则编译抽屉候选集里，
   台账对应行档位变为「已进编译候选」。**每一步都有人工确认点**（无自动升档）。
6. `npm run check:leads3-compliance` 在「有确认记录」的新判据下扫全库，0 违规；
   人为构造一条「active 且无确认记录」的样本能被抓出来。
7. 迁移脚本可重复执行：连跑两次，第二次 0 新增（幂等）；`--dry-run` 不写库。
8. 按生态筛选出的行数与登记录数一致；「全部」档不丢行。
9. 边界：某条记录缺字段时视图不崩，缺字段显示「—」；采集记录为 0 条时显示空态提示而非报错。
10. 界面改动**在浏览器里真看到渲染**（本地模式 + 云端模式各看一遍），不是只跑测试。
11. `npm run check:fast` 全过（类型检查 + 全量测试，基线 564 项，退役与新增后计数会变，需在清单里写明新基线）。
