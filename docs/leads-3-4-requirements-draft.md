## 一、线索 3：把外部生态的规则采进资产库，并沉成 AI 能读的知识库

### 一句话定位

把外部生态里的技能、规范、方法**采成资产库里的资产**，让它们既能编译进 `AGENTS.md`
影响 AI 的行为，也能被 AI 当知识库检索。

### 现在卡在哪（都有出处）

| 现象 | 出处 |
| --- | --- |
| 采集靠人会话，一次一条，产品里没有"采到哪了"的视图 | `seed-packs/external-sources/README.md` 的采集台账 S1～S8，最新到 0.1.9 |
| S7 采了 4 条，剩下 15 个技能的处置只写在台账里，没落地 | 台账 S7 行：`job-stories`／`user-stories`／`wwas` 该进模板层；`prioritization-frameworks`／`ui-ux-pro-max` 该进参考文档层；7 个团队管理方法建议"单独立一片" |
| 市场仓库 → 资产库刚跑通，但是单向、且靠脚本 | `scripts/sync-market-skills.ts`（2026-09-28），只同步 5 个技能的 `SKILL.md` |
| 腾讯生态（腾讯文档／企业微信／TAPD／知识库）还没采 | 2026-09-28 那条裁决的原话：「腾讯的生态完整还集成了知识库体系」 |

### 做什么

**M0：零代码先跑通一遍（不动产品代码）**

1. 把 S7 那 15 个技能的处置落地：需求表达格式进模板层、会腐化的清单进参考文档层、
   7 个团队管理方法单独立一片。
2. 采集台账每条来源补四个字段：来源链接、核实日期、处置结论（已采／不采／暂缓）、
   落到哪条资产。

**M1：进产品（只读视图 + 检查）**

3. 台账变成产品里的一条只读视图：来源 → 提炼出的资产 → 是否已编译进 `AGENTS.md`。
4. 把「外部来源采集 SOP」的硬约束做成能跑的检查：外部资产默认 `candidate`、可信度初始
   `hypothesis`、必须留 `source_references`、未经人工确认不许升 `active`。
   （编译侧的同类约束已经由 `RULE-CONFIDENCE-COMPILE-001` 挡着。）

**M2：接腾讯生态 + 补双向同步**

5. 采腾讯生态里与本项目相关的技能与规范，仍走"先提炼规则，不照搬流程"。
6. 市场仓库与资产库的同步补双向：现在只有"市场 → 库"，缺"库里的改进怎么回写正本"。

### 不做什么

- 不做爬虫式批量抓取，不做未经人工确认的自动入库。
- 不接管腾讯生态的账号与权限（先只读沉淀，不做写回）。
- 不把外部技能直接编译进 `AGENTS.md`，一律先 `candidate`。
- 不做面向第三方的技能市场——这不是本产品的方向。

### 验收标准

1. 台账里每条来源都能看到「来源链接 + 核实日期 + 处置结论 + 落到哪条资产」四个字段。
2. S7 剩下 15 个技能各自都有结论，不留"待定"。
3. 产品里能看到一条只读视图：来源 → 资产 → 是否已编译。
4. 拿一条真实外部技能走完全程：采集 → 提炼 → 入库 → 进编译候选，每一步都有人工确认点。
5. 同步脚本可重复执行，跑第二遍报 0 差异。

### 需要拍板

- 第一版是否只做 M0（不动代码，本周就能出东西）。
- 腾讯生态的采集现在做还是等真需要（要你的账号与素材）。

## 二、线索 4：把内网／自建环境缺的四块能力练成可复用的起步包

### 一句话定位

用一个小项目把**数据库、证书、文件存储、邮件**四块自建能力练通，产出一份可复用的起步包，
给第一个内网交付项目直接用。

### 现在卡在哪（都有出处）

- `docs/project-map.md` 第五节的「环境差异」表：10 个环节里 **9 个标"不能靠配置解决"**
  （自动部署、应用托管、认证、文件存储、邮件、证书、观测、备份……）。
- `docs/learning/engineering-readiness.md`：数据库 → 证书 → 文件存储 → 邮件四块，当时定的是
  "等产品迭代完再补"，到现在没有练习记录。
- `docs/v3-requirements-draft.md` 的 M1／M2（环境台账、交付制品包）依赖这套能力；
  没有它，环境体检只能写"要补能力"，补不了。

### 做什么

**M0：一个练习项目，本机跑通**

1. `docker-compose` 起四件：Postgres、Nginx 反代、自签 HTTPS、一个附件上传页，
   外加一条 SMTP 收信验证。
2. 一份手册：怎么起、怎么验、怎么停、怎么备份与恢复、密钥放哪。
3. 练习记录：每一步"我以为会怎样 / 实际怎样"，重点是证书分发和邮件这两块最容易卡。

**M1：抽成起步包**

4. 四块的最小可用配置抽成模板资产（可导入公共资产库），配一份「环境体检清单」，
   每项标"配置能解决"还是"要补能力"。
5. 和 `docs/project-map.md` 的环境差异表对齐，把那张分析表变成可勾的清单。

**M2：用真项目验收**

6. 在第一个真实的内网或自建环境交付项目里用它，记录哪些默认值被实践推翻
   （这正是 `MTH-STACK-001` 那条触发条件等的东西）。

### 不做什么

- 不练信创数据库（达梦、人大金仓）的迁移，等真有项目再练。
- 不做 K8s、不做集群、不做多机编排。
- 不把密钥写进仓库；演示用的自签证书和口令不进 Git。
- 不在公司网络或客户环境做实验，先在本机。

### 验收标准

1. 一条命令起全栈（Postgres + 反代 + HTTPS + 上传页），浏览器能打开上传页并成功上传一个文件。
2. HTTPS 用自签证书能正常访问，手册里写清根证书怎么分发。
3. 邮件能收到一封测试信（或用替代方案并写明）。
4. 备份与恢复各做一次：备份后删掉一条数据，恢复后能查回来。
5. 手册能让另一个人（或另一个 AI 会话）照着独立跑起来。

### 需要拍板

- 这条做成本机练习项目，还是直接做成产品里的"环境"能力？
- 谁来写：WorkBuddy 先行，还是 Codex 做（或 Codex 出任务书、WorkBuddy 执行、Codex 复验收）。

## 三、两条线索的排序建议

按"一个版本只做一个子系统"和依赖关系：

1. **先线索 4**：它是 v3 零代码交付线的前置能力，且能独立验收——跑起来就是证据。
2. **后线索 3**：它接的是资产库的入口，需要腾讯生态的权限和素材，等线索 4 稳了再做。

两条都不影响当前产品的验收收口（`docs/pending-items.md` 里那三项线上验收）。
