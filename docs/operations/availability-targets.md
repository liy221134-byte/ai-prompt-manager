# 可用性与恢复目标

按 `docs/project-map.md` 第三步补齐的立项产物。这一份是**当前项目**的实例，不是通用方法。

## 三个数字

| 数字 | 取值 | 状态 |
| --- | --- | --- |
| 可用性目标 | 无对外承诺（个人工具，只有自己用） | 已定 |
| RTO | 目标 1 小时内恢复 | **待确认**（建议值） |
| RPO | 接受「上次导出之后的数据」 | **待确认**（建议值） |

按地图的 RTO 分档，本项目落在「小时级：备份加一键重建脚本」这一档，不需要高可用。

## 选型基线核对

当前技术栈：Next.js（单体应用）+ Supabase（托管数据库）+ Vercel（托管部署）。

对应地图第二步的「个人工具 + 全托管」默认档，**没有偏离**，因此不需要新增 ADR。

## 当前能力（2026-09-21 核实）

- **部署**：Vercel 保留历史版本，出故障可以切回上一个 Ready 版本，恢复是分钟级。
- **数据**：生产数据在 Supabase。需要说清楚一件事——**自动每日备份只对 Pro 及以上
  计划开放**，官方文档明确建议免费计划自己用 CLI 导出并异地保存。也就是说免费计划
  虽然有备份，但我们访问不到、也恢复不了。
- **应用层备份**：界面里有手动导出和导入 JSON 的入口。
- **本地副本**：项目目录里留有一份早期本地模式的数据文件，可能与云端不同步，不能
  当作可靠副本。

**结论：RPO 实际上等于「上次手动导出的时间」，没有任何保障。**

## 明确接受的风险

个人提示词库的数据量和业务价值都很低，出错的主要形式是**误删单条内容**，而这一点已经
被垃圾箱的 30 天保留覆盖。所以本项目的决定是：

- **不升级 Supabase 计划**（每月 25 美元换每日备份，对这个项目不划算）。
- **不新建自动备份管道**（要加定时任务、存储目标和密钥，属于典型的过度建设）。
- **接受 RPO 等于上次导出时间**，用纪律补：每次开新版本时导出一份，并把导出时间记进
  部署台账。

这个决定和地图里的判断一致：**「能快速重建」比「永不停机」划算**；而在重建这件事上，
个人工具的最低成本做法就是"导出频率跟着版本走"，不是自动化。

## 什么时候需要重新评估

- 数据从"自己用"变成"别人也在用"。
- 出现第一份无法手工重建的数据（例如用户上传的文件、外部同步来的记录）。
- 出现任何一次真实的数据丢失或误删事故。

满足任意一条时，回到这里重新定三个数字，再决定要不要买备份或上自动化。
