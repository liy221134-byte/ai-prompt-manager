# 发布与回滚

## 当前发布方式

```text
本地 main
-> GitHub main
-> Vercel 自动构建
-> 生产环境
```

每个稳定阶段创建版本标签，例如 `v0.6.0`。

## 发布前检查

- `npm run check` 通过。
- Node.js 版本为 `24.x`。
- Git 工作区干净。
- `main` 与 `origin/main` 同步。
- 版本号与标签一致。
- Vercel 环境变量齐全。
- 数据库迁移已经执行并完成验证。
- 当前版本已导出 JSON 备份。

## 数据库迁移顺序

发布必须严格按以下顺序执行：

1. 确认迁移 SQL 已经评审，且只包含预期变更。
2. 在 Supabase 执行迁移。
3. 验证目标表、字段、策略和数据读写结果。
4. 记录迁移名称、执行时间和验证结果。
5. 将代码推送到 `main`，触发 Vercel 部署。

不允许先部署依赖新结构的代码，再补执行数据库迁移。

## Vercel 构建门禁

`vercel.json` 将 Vercel Build Command 固定为 `npm run check`。只有代码检查、
类型检查、自动化测试和生产构建全部通过，部署才能继续。

## 发布门禁证据

每次生产发布都要在发布记录中留下以下证据：

| 证据 | 内容 |
| --- | --- |
| 工程检查 | `npm run check` 的通过结果 |
| 数据库迁移 | 迁移名称、执行时间和验证结果 |
| 数据备份 | 备份时间、文件位置和资产条数 |
| 环境变量 | Production 与 Preview 的配置范围检查结果 |
| 回滚目标 | 上一个正常 Ready 部署 |
| 发布验证 | 登录、数据读取、编辑、导入和 AI 采集结果 |

缺少任何一项时，不进入正式发布。

发布后把这次门禁的勾选情况记进产品里的「发布记录」（工程基线 → 最近一次发布），
两边口径一致：能勾上的项才算过了门禁。

## Vercel 回滚

1. 打开 Vercel 项目的 Deployments。
2. 找到上一个状态为 Ready 的正常版本。
3. 选择 Redeploy。
4. 使用生产域名验证登录、提示词读取和 AI 采集。

## Git 回滚

优先使用新的修复提交：

```powershell
git revert <有问题的提交>
```

不要使用 `git reset --hard` 修改已经推送的共享历史。

## 数据库回滚

数据库迁移必须优先向前兼容。

如果只涉及新增列或新增表：

- 应用先回滚。
- 保留新增结构，等待修复版本重新部署。

如果涉及破坏性结构修改：

- 先恢复备份到临时数据库。
- 校验数据数量。
- 得到明确确认后再替换生产结构。

## 回滚前置检查（2026-09-24 演练发现）

**回滚代码之前，先确认库里有没有「旧版本不认识」的资产类型。**

演练实测：库里只要有 1 条 v2.10.0 才引入的「发布记录」，用 v2.9.0 的代码打开这个库会
**直接启动失败**，报「资产数据无法识别：release_record-…」，界面都进不去。
原因是每个版本只认识自己那套资产类型，读到不认识的类型就报错（没有静默跳过，
因为少显示数据比报错更危险）。

各版本引入的资产类型：

| 版本 | 引入的资产类型 |
| --- | --- |
| 2.0.0 | 统一资产（提示词、规则、文档等基础类型） |
| 2.1.2 | 技术档案 |
| 2.2.0 | 规则包 |
| 2.4.0 | 模板 |
| 2.5.0 | 图谱节点 |
| 2.9.0 | 验收记录 |
| 2.10.0 | 发布记录 |

跨这些版本回滚时按这个顺序：

1. **先导出 JSON 备份**（备份只含当前内容，见 `backup.md`）。
2. 在界面上把旧版本不认识的那几类资产删除（归档也可能被旧代码读到，稳妥做法是删除；
   不想删就接受旧版本读不出来）。
3. 再切回旧代码。
4. 按下面的清单验收一遍。

同一个版本内的回滚（例如 v2.11.0 回到 v2.10.0）没有这个问题：类型集合一样。

## 数据恢复

优先使用提示词工具导出的 JSON 备份：

```text
数据管理 -> 选择备份文件 -> 查看导入预览 -> 确认导入
```

导入只合并不删除，适合恢复少量丢失数据。

## 回滚后的验收

- 邮箱密码登录正常。
- 项目列表和资产列表能打开，条数与回滚前的备份一致（垃圾箱和归档除外）。
- 各类资产（提示词、规则、文档、模板、技术档案、图谱节点、验收记录、发布记录）都能打开详情。
- 新增、编辑、归档和删除正常。
- 备份导入、规则编译、项目图谱、MCP 服务各能跑通一次。
- AI 采集接口正常。
- 没有出现跨用户数据。

## 生产故障演练

每个大版本至少进行一次受控演练。演练优先使用 Preview、测试账号和测试数据，
不得直接在唯一的生产数据上制造故障：

1. 使用错误环境变量启动隔离环境，确认系统安全关闭。
2. 导出测试数据，修改一条测试提示词后完成恢复。
3. 回滚到上一个正常 Ready 部署，完成基础验收。
4. 检查 Preview 环境没有生产 Service Role Key 和 Cron Secret。
5. 记录演练目标、操作、结果、恢复时间和改进项。
