# 发布与回滚

## 当前发布方式

```text
本地 main
-> GitHub main
-> Vercel 自动构建
-> 生产环境
```

每个稳定阶段创建版本标签，例如 `v0.6.0`。

## 发布前检查

- `npm run check` 通过。
- Node.js 版本为 `24.x`。
- Git 工作区干净。
- `main` 与 `origin/main` 同步。
- 版本号与标签一致。
- Vercel 环境变量齐全。
- 数据库迁移已经执行并完成验证。
- 当前版本已导出 JSON 备份。

## 数据库迁移顺序

发布必须严格按以下顺序执行：

1. 确认迁移 SQL 已经评审，且只包含预期变更。
2. 在 Supabase 执行迁移。
3. 验证目标表、字段、策略和数据读写结果。
4. 记录迁移名称、执行时间和验证结果。
5. 将代码推送到 `main`，触发 Vercel 部署。

不允许先部署依赖新结构的代码，再补执行数据库迁移。

## Vercel 构建门禁

`vercel.json` 将 Vercel Build Command 固定为 `npm run check`。只有代码检查、
类型检查、自动化测试和生产构建全部通过，部署才能继续。

## Vercel 回滚

1. 打开 Vercel 项目的 Deployments。
2. 找到上一个状态为 Ready 的正常版本。
3. 选择 Redeploy。
4. 使用生产域名验证登录、提示词读取和 AI 采集。

## Git 回滚

优先使用新的修复提交：

```powershell
git revert <有问题的提交>
```

不要使用 `git reset --hard` 修改已经推送的共享历史。

## 数据库回滚

数据库迁移必须优先向前兼容。

如果只涉及新增列或新增表：

- 应用先回滚。
- 保留新增结构，等待修复版本重新部署。

如果涉及破坏性结构修改：

- 先恢复备份到临时数据库。
- 校验数据数量。
- 得到明确确认后再替换生产结构。

## 数据恢复

优先使用提示词工具导出的 JSON 备份：

```text
数据管理 -> 选择备份文件 -> 查看导入预览 -> 确认导入
```

导入只合并不删除，适合恢复少量丢失数据。

## 回滚后的验收

- 邮箱密码登录正常。
- 可以看到自己的全部提示词。
- 新增、编辑和删除正常。
- AI 采集接口正常。
- 没有出现跨用户数据。
