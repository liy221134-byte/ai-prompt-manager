# 备份与恢复

## 本地与云端之间搬数据

产品不做自动同步（两边都能改，自动合并会把数据弄乱）。要搬数据时走产品的两步：

1. 源那一侧「数据管理 → 导出备份文件」；
2. 目标那一侧「数据管理 → 选择备份文件」导入。

导入语义是**只新增、不覆盖**：同 id 的资产跳过，同名项目合并，垃圾箱里的内容不进备份。

云端拉到本机可以省掉第一步，用脚本代跑（先起 `npm run dev:local`）：

```powershell
npm run sync:from-cloud                    # 真拉
node scripts/sync-from-cloud.mjs --dry-run # 只看会拉什么
```

## 备份对象

- 项目（含质量等级）。
- 全部资产：提示词、规则、文档、模板、技术档案、规则包、图谱节点、验收记录、发布记录。
- 资产之间的关系（引用、依赖、替代、实现）。
- 每个资产的**当前内容**（历史版本不在备份里，见下）。
- Supabase 用户和权限配置。
- 必要环境变量名称。
- 代码和 Git 标签。

## JSON 备份

入口：

```text
数据管理 -> 导出备份文件
```

备份内容：

- 备份格式版本。
- 导出时间。
- 项目、各类资产和它们之间的关系。
- 每个资产的当前内容。

**不在备份里的东西**（2026-09-24 加固演练核对）：

- **资产的历史版本**：恢复后每个资产只有 1 条版本记录（当前内容）；
  要留历史版本得另外留数据库文件或旧备份。
- **来源包上传的原始文件**：备份里只有资产和相对路径，原文件要另行保留。

## 建议频率

- 每次发布前导出一次。
- 每月至少导出一次。
- 大批量导入或 AI 合并前导出一次。
- 修改数据库结构前强制导出。

## 保存位置

至少保留两份：

- 本机文件目录。
- 私人云盘或其他离线存储。

不要把包含提示词内容的备份提交到 GitHub。

## 手工复制数据库文件时（2026-09-24 演练发现）

本机库用 SQLite WAL 模式：最近的写入先落在 `prompts.sqlite-wal`，过一段时间才合并回主文件。
**只复制 `prompts.sqlite` 会丢掉最近的写入**——演练里这样复制出来的库少了 1 条刚建的发布记录。

两种正确做法：

1. 先把应用正常关掉，让 WAL 落盘，再复制 `prompts.sqlite`。
2. 或者 `prompts.sqlite`、`prompts.sqlite-wal`、`prompts.sqlite-shm` 三个文件一起复制。

日常备份优先用界面导出的 JSON 备份，不复制数据库文件。

## Supabase 数据备份

自动每日备份只对 Pro 及以上计划开放。免费计划虽然也在做备份，但我们**访问不到、也
恢复不了**，官方文档的建议就是免费计划自己导出并异地保存。

所以本项目不把 Supabase 当作可用的备份来源，恢复点完全取决于上面的导出频率。这一条
和可用性目标的关系见 `operations/availability-targets.md`。

## 恢复流程

1. 先导出当前数据，避免恢复过程覆盖新内容。
2. 打开数据管理。
3. 选择备份文件。
4. 检查新增、更新和跳过数量。
5. 确认导入。
6. 刷新页面并核对提示词数量。

预览和实际导入使用同一套垃圾箱过滤规则。备份中存在、但当前仍在垃圾箱中的
提示词会显示为“跳过”，导入后不会复活。

## 恢复演练

至少每三个月进行一次（用真实数据的副本做，不在唯一的数据上试）：

- 导出当前数据（JSON 备份）。
- 在一个空库上导入，按资产类型逐一对数量，关系条数也要对。
- 核对标识、标题、正文和关系都一致；**版本记录只有 1 条是正常的**（历史版本不进备份）。

2026-09-24 的演练结果：1 个项目、82 条资产（7 类）、2 条关系；导入后逐项一致，
标识和标题保持不变。
