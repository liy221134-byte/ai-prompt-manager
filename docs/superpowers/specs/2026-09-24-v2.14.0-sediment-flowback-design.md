# v2.14.0 沉淀回流：设计 + 任务清单

## 来源

来自链路断点评估里的 G1／G2／G3（见 [从沉淀到立项：链路断点评估](../../project-lifecycle-gaps.md)）：

> 你要在开新项目之前，把当前产品开发过程中积累的规则、模板沉淀"升"到公共资产中心；
> 之后还要能持续同步——项目里改的、公共库改的，不能互相不知道。

现状是：项目里的资产搬进公共库**只能手工复制正文**；装进项目的资产是**复制**语义，
两边之后各自独立，谁也不知道对方改了；也没有一个地方能看出"哪些该升到公共、哪些重复了"。

## 一、做什么 / 不做什么

### 做什么

1. **提升为公共资产**（G1）：在项目资产的详情里加「提升为公共资产」——
   把这份资产复制一份到公共资产库，并记下**它来自哪个项目的哪一条**；
   项目里那份保持不变（不删不改），避免"升一次东西就没了"。
2. **记录上下游关系**（G2 的前半）：提升时给两边都记一条「同源」标记：
   公共那条记来源项目资产，项目那条记公共对应条目。用现有的资产关系字段，不新增表。
3. **上游有更新时给提示**（G2 的后半）：打开项目里那条资产时，如果公共那条
   更新时间更新，详情里显示「公共库那份在 X 时间改过」，并给「看差异 / 拉取公共版本」两个动作。
   **不自动覆盖**——拉取是显式动作，拉完产生一条新版本。
4. **沉淀体检**（G3）：新增一个只读视图（公共资产视图里进），列出三类线索：
   - 只在某个项目里出现、且没提升过的**规则**（按标签/包来源分组，给「提升」入口）；
   - 与公共库内容**标题重复或高度相似**的项目资产；
   - 公共库里**长期没更新**的资产（超过 90 天，提示复核）。

### 不做什么

- 不做自动同步、不做后台任务：两边都能改，自动合并会把数据弄乱。
- 不做双向引用（项目资产直接引用公共资产、改一处全项目变）：那是另一种模型，
  会牵动全部读写路径，本版不碰。
- 不做删除：提升只新增；差异拉取只产生新版本。
- 不加表、不改字段类型：全部落在现有 `assets`／`asset_versions`／关系字段上。

## 二、数据和产品行为影响

| 项 | 影响 |
| --- | --- |
| 数据库结构 | 无变化（不新增表／列／迁移） |
| 同源标记 | 复用现有关系字段：公共那份记 `reference → 项目那份`，项目那份记 `reference → 公共那份`，备注写「同源：<项目名>」 |
| 提升动作 | 在公共资产库新增一条资产（新版本从 v1 起），来源标 `manual`，原资产不动 |
| 上游提示 | 只读比较更新时间，不写数据 |
| 差异拉取 | 用公共那份的正文覆盖项目那份，产生一条新版本（旧版本仍在历史里，可恢复） |
| 沉淀体检 | 只读视图，不写数据 |

## 三、验收标准

1. 项目里任意一条规则／文档／模板能「提升为公共资产」；提升后公共库里出现同名副本，
   两边详情都能看到「同源」关系。
2. 公共库那份改了之后，打开项目那份，详情里出现「公共库那份在 X 时间改过」的提示。
3. 点「拉取公共版本」后正文变成公共那份，并新增一条版本记录；旧的正文能从历史恢复。
4. 点「看差异」能看到两边正文的行级差异（复用 AI 优化那套差异视图）。
5. 沉淀体检里能看到"只在项目里出现的规则"清单，并能逐个提升。
6. 重复标题的资产在体检里被列出来，给「去比对」入口。
7. 提升／拉取都不会删除任何数据；本机与云端语义一致（同一套纯逻辑 + 契约测试）。

## 五、需要拍板的三件事

| 编号 | 决定 | 我的建议 |
| --- | --- | --- |
| H1 | 提升时项目里那份怎么处理 | 保持不动（只新增公共副本）。另一种是"改成引用公共"，本版不做 |
| H2 | 差异拉取的方向 | 只做「把公共版本拉到项目」这一向；反向（项目改动推回公共）走"再提升一次" |
| H3 | 沉淀体检放哪 | 放在公共资产视图的「更多」里（它是账号级的体检，不是某个项目的） |
