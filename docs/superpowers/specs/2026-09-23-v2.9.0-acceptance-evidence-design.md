## 一、做什么 / 不做什么

### 做什么

1. **新增资产类型「验收记录」**（`evidence`），一条记录对应一个需求节点的一次验收：
   - **验收条件**：什么结果算完成（正文第一节）。
   - **测试步骤**：怎么验的，一步步写（正文）。
   - **实际结果**：跑完看到什么（正文）。
   - **证据**：证据说明 + 链接或文件路径（元数据，可多条）。
   - **提交版本**：提交号或版本标签（元数据，手填）。
   - **结论**：通过／未通过／例外（元数据），**默认「待确认」，只能由你在界面上改成通过**。
   - **已知问题和例外**：正文最后一节。
2. **挂在需求节点上**：验收记录指向一个图谱节点（默认需求类型），
   需求节点详情里显示「验收记录 n 条，其中通过 m 条」。
3. **覆盖缺口**：在工程基线里加一块「验收覆盖」——
   列出当前项目里还没有「通过」验收记录的需求节点（按编号排序），点一下能进新建验收记录。
4. **MCP 也能用**：查询和写入工具都支持这种类型（AI 可以提交草稿证据，结论仍然由你确认）。

### 不做什么

- 不接 GitHub／CI：提交号手填，不自动拉提交历史，也不自动跑测试。
- 不自动判定通过：AI 只能提交记录，**结论改成「通过」必须由你在界面上点**。
- 不做验收清单模板生成器：v2.8.0 已经给了 8 份工程文档模板，这一版不再生新文档类型。
- 不做跨项目的验收统计看板。
- 不做附件上传：证据先支持「说明 + 链接或文件路径」，真传文件以后再说。

## 二、数据和产品行为影响

- 资产类型新增 `evidence`，**不改表结构**（`asset_type` 是文本字段），
  本机和云端都不用迁移。
- 元数据结构：`{ nodeId, conclusion, commitRef, evidenceItems[], note }`，
  缺字段按空值读，老数据不受影响。
- 关系：验收记录用现有关系字段指向需求节点；需求节点不必反向存一份，
  缺口和统计都从验收记录反查，避免两处各存一份。
- 类型筛选新增「验收记录」；编辑器按这个类型渲染专用字段。
- MCP 工具开放 `evidence` 的读写（写工具已存在，只是把它加进允许列表）。

## 三、验收标准

1. 能新建验收记录：选需求节点、填验收条件、测试步骤、实际结果、证据、提交版本；
   不填需求节点或验收条件时保存被拦下并给中文提示。
2. 结论默认「待确认」，界面上可以由人改成「通过」「未通过」「例外」。
3. 需求节点详情能看到它有多少条验收记录、几条通过。
4. 工程基线的「验收覆盖」列出没有通过验收记录的需求节点，点一下能进新建记录。
5. 类型筛选能筛出验收记录；搜索能搜到正文和证据说明。
6. MCP：AI 能查、能新建验收记录，但把结论改成「通过」需要人在界面上操作
   （MCP 写入时结论只能是默认值或待确认）。
7. `npm run check` 通过。

## 五、三个决定（2026-09-23 已确认）

1. **做成新资产类型** `evidence`：一等资产，能版本化、能被筛选和 MCP 复用。
2. **结论只能人改**：AI 可以提交证据，但「通过」必须人在界面上点。
   实现上 MCP 的写入字段里**根本没有 conclusion**，从接口层面堵住。
3. **提交号手填**：不接 GitHub，先支持手填提交号或版本标签。

## 六、设计偏差（实施后填）

1. **需求节点的关联放在元数据里**（`nodeId`），不是写成一条关系。设计原文写的是「用现有关系字段
   指向需求节点」，实现改成专用字段：这条关联语义固定（只能挂需求节点、覆盖统计按它算），
   混进通用关系里既不好校验也容易和用户自己建的关系搅在一起。
   代价：需求节点的「谁指向它」清单里不会出现验收记录，要的话以后再加。
2. **「例外」算未覆盖**：只有结论是「通过」才算这条需求验收过；
   「例外」表示这次特殊处理，不算通过，仍然留在缺口清单里。
3. **只有活跃、没进垃圾箱的验收记录算数**：草稿还没提交，归档表示不再用。
4. **新建时的标题不重复编号**：从缺口点进编辑器，标题是「<需求标题> 验收记录」，
   编号在面板和字段里本来就挨着显示。
5. **实施中修掉两处标签**：详情抽屉以前把非规则资产一律叫「文档」、正文字段叫「选型说明」，
   验收记录显示成了「文档 / 选型说明」；现在按类型显示「验收记录 / 验收条件、步骤与实际结果」。
