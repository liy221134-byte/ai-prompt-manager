# v2.22.0 设计 + 任务清单：规则的技术上下文参与编译筛选

背景一句话：`schema.md` 里规则有「技术上下文」这个字段（`generic`／`nextjs`／`supabase`／
`postgres`／`vercel`），界面上能填、冲突检测也会用，但它**不决定规则要不要收**——
一条标着 `nextjs` 的规则，装进 Vue 项目照样进编译候选。这一版把它接上。

## 一、做什么 / 不做什么

### 做什么

1. **规则的技术上下文参与编译筛选**：规则标了具体技术时，只有项目技术栈里有它，才进
   「参与编译」；否则进「已排除」，理由写明是哪一项技术对不上。
2. **技术栈只有一个来源**：项目里那份**活跃的技术档案**（`findProjectTechProfile`）的
   技术栈清单 `stack[].name`。不读 `package.json`，不从项目说明里猜。
3. **项目的技术上下文集合为空就不筛**：维持现在的行为，所有活跃规则照旧进候选。
   集合为空有两种来路，都按不筛处理——
   ① 项目没有活跃的技术档案；② 有档案，但技术栈里的名字一个都对不上技术上下文
   （例如档案里只写了 React、Tailwind）。第二种如果也拿来筛，会把所有标了具体技术的规则
   一次全排除，而且界面上看不出为什么。编译抽屉里把这两种情况都说明。
   （2026-09-27 产品负责人裁定：按实现的这条来，改设计。）
4. **匹配口径：有交集就收。** 规则的 `generic` 永远算命中；除 `generic` 之外，
   **只要有一项**在项目技术栈里，这条规则就收；一项都对不上才不收。
   （产品负责人 2026-09-27 定「放宽」：宁可多收一条，也不要因为标签写了多项而漏收。）
   技术栈名字先归一化（小写、去掉空格 / 点 / 连字符），再过一张小别名表：
   `next` → `nextjs`，`postgresql` / `pg` → `postgres`。别名表以外的名字不猜、不报错，
   只是不参与匹配。
5. **冲突检测不动**：技术上下文在那里的用法仍是「有交集就算维度相关」，本次不改。

### 不做什么

1. 不改表结构、不加字段、不写迁移。技术档案的 `stack` 和规则的 `techContext` 都已存在。
2. 不做「项目级技术上下文」这种新设置——不新增第二个技术栈来源，避免两套口径。
3. 不在编译产物（AGENTS.md 草稿）正文里额外标注适用技术：筛选本身已经决定了它在不在，
   再标一遍是重复信息。
4. 不做更严的「全中」判定：规则标了多项技术时，只要有一项对上就收。代价是可能多收
   一条只沾边的规则——这是产品负责人 2026-09-27 明确选的宽松一侧。
5. 不改编译产物的结构、不自动保存草稿（保存仍然是人工点）。

## 二、数据和产品行为影响

**数据**：不新增、不修改任何表和字段；只读技术档案和规则元数据。

**行为**：

| 情形 | 现在的行为 | 改后的行为 |
| --- | --- | --- |
| 项目**有**技术档案，规则标的那些技术**一项都不在**项目技术栈里 | 照收 | 不收，进「已排除」并写明原因 |
| 项目**有**技术档案，规则标了几项、**至少一项**在项目技术栈里 | 照收 | 照收 |
| 项目**有**技术档案，规则标的是项目有的技术 | 照收 | 照收 |
| 项目**有**技术档案，规则只标 `generic` 或没标 | 照收 | 照收 |
| 项目的技术上下文集合为空（没有技术档案，或档案里认不出技术栈） | 照收 | 照收（不筛） |

**短期影响面**：库里现在 **0 份技术档案**（实测：74 文档、83 图谱节点、19 提示词、
46 规则、6 规则包、21 模板，没有技术档案），所以这一版上线后现有项目行为不变；
等哪天给某个项目建了技术档案，它编译出来的 AGENTS.md 才会开始少收不匹配技术的规则。
现有规则的分布是 `generic` 36 条、`supabase` 2 条、`vercel` 2 条、`postgres` 1 条、
`nextjs` 0 条——真正会被筛掉的是少数。

**顺带的效果**：技术档案从「填了只给自己看」变成「真的影响编译结果」，它才算有了下游作用。

## 三、验收标准

每条都能用一次自动化测试或一次手工操作判定。

1. 项目技术栈里有 `Next.js` 时，标 `nextjs` 的规则进「参与编译」。— 测试
2. 项目技术栈里只有 `Next.js`，一条标 `supabase` 的规则进「已排除」，理由里点名 Supabase。— 测试
3. 规则只标 `generic`、或者根本没标技术上下文时，任何技术栈下都进「参与编译」。— 测试
4. 项目的技术上下文为空时（没有活跃技术档案，或档案里的技术栈名一个都对不上），
   一条标 `supabase` 的规则照旧进「参与编译」（不筛）。— 测试
5. 名字能对上：技术栈里写 `Next.js`、`next.js`、`next` 都算 `nextjs`；
   `PostgreSQL`、`postgres`、`pg` 都算 `postgres`；写别的名字不报错、也不参与匹配。— 测试
6. 规则同时标 `[nextjs, supabase]` 而项目只有 `nextjs` 时，照收（有一项对上就收）。— 测试
7. 冲突检测行为不变：同层级、技术上下文有交集的两条规则仍算冲突候选。— 测试
8. 编译器里能看到当前按哪套技术栈筛；没有技术档案时显示「不按技术栈筛」。— 手工
9. 完整检查通过：`npm run check`（类型检查、全部测试、代码检查、生产构建）。— 自动化

## 四、任务顺序与改动文件

1. **技术栈 → 技术上下文的映射与读取**（纯逻辑）
   - `src/lib/tech-profile.ts`：新增读取项目技术上下文集合的函数（复用已有的
     `findProjectTechProfile`），含名字归一化和别名表。
2. **筛进候选集**
   - `src/lib/rule-compile.ts`：`listCompileCandidates` 增加「项目技术上下文」入参；
     不匹配的规则带理由进 `excluded`；`generic` 不参与判定。
3. **调用方把技术栈传进去**
   - `src/components/prompt-library.tsx`：算一次项目技术上下文，传给编译相关调用。
4. **界面上说清楚**
   - `src/components/rule-compile-drawer.tsx`：顶部显示「按技术栈 X 筛」或
     「没有技术档案，不按技术栈筛」；已排除列表照旧显示逐条理由。
5. **测试**
   - `tests/rule-compile.test.mjs`：验收标准 1～4、6、7。
   - `tests/tech-profile.test.mjs`：验收标准 5（归一化与别名）。如果该文件不存在就新建。
6. **验收清单**
   - `docs/acceptance/v2.22.0.md`：逐条对照上面 9 条。

工单做完再跑一次 `npm run check`，并按界面改动的规矩在浏览器里走一遍编译抽屉。
