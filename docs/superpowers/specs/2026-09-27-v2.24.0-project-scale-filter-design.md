# v2.24.0 设计 + 任务清单：项目规模参与编译筛选

背景：规则资产上有「适用项目规模」这个字段（`personal`／`medium`／`large`／`regulated`），
但编译器不看它——一条标着「只适用于大型平台」的规则，装进个人工具项目照样进编译候选。
0.7.0 采进来的 6 条 Postgres 规则就是这么一类：它们对中大型项目成立，本项目用不上，
可是**光打标签挡不住它们**。

技术上下文（v2.22.0）已经能筛了，这一版把项目规模也接上，口径照抄那一版。

## 一、做什么 / 不做什么

### 做什么

1. **技术档案加一个结构化字段「项目规模」**（多选，四档：个人工具／中型产品／大型平台／
   监管或高敏）。技术档案模板里本来就有这一项，只是一直写在正文里、没变成字段——
   这一版把它变成能读的字段。**不动 `projects` 表**。
2. **规则编译按项目规模筛**：规则标了规模时，只有和项目规模**有交集**才收；
   一项都对不上就进「已排除」，理由写明两边是什么规模。
3. **和 v2.22.0 完全同一个口径**：规则的规模列表为空 → 一直收；项目没填规模、
   或者项目没有技术档案 → **不筛**，行为与现在一致。
4. **编译抽屉里说清楚**：当前按哪些规模筛；没填就是「这个项目没填规模，不按规模筛」。
5. 技术档案编辑器里能多选这四档。

### 不做什么

1. **不给 `projects` 表加字段。** 规模从技术档案读，和技术上下文同一个来源；
   加第二个来源就会出现两套口径。
2. **不拿质量等级推算规模。** 质量等级（个人／低风险／用户数据／高敏）说的是「出事代价」，
   规模说的是「复杂度」，两个轴；用一个推另一个是猜。
3. 不改技术上下文那一版的判定逻辑，也不动它的取值。
4. 不强制填规模：留空就是「项目自己没说规模」，那就不筛。
5. 不改编译产物的结构、不自动保存草稿。

## 二、数据和产品行为影响

**数据**：技术档案的 `metadata` 里多一个 `projectScale` 字段（字符串数组）。
技术档案的元数据存在资产的 JSON 里，**不涉及表结构变更、不需要迁移**。
老档案没有这个字段时按空数组读，行为不变。

**行为**（和 v2.22.0 的表一一对应）：

| 情形 | 现在的行为 | 改后的行为 |
| --- | --- | --- |
| 项目填了规模，规则标的规模**一项都对不上** | 照收 | 不收，进「已排除」并写明原因 |
| 项目填了规模，规则标的规模**至少一项对得上** | 照收 | 照收 |
| 项目填了规模，规则没标规模 | 照收 | 照收 |
| 项目没填规模，或项目没有技术档案 | 照收 | 照收（不筛） |

**短期影响面**：库里现在 **0 份技术档案**，所以这一版上线后行为完全不变。
等哪个项目建了档案并填了规模，它编译出来的 AGENTS.md 才会开始少收对不上规模的规则。

**这正好补上 0.7.0 那 6 条的位置**：它们是 `medium`／`large`／`regulated` 的规则，
本项目（个人工具）建好档案、填 `personal` 之后，它们会被自动筛掉，不需要手工逐条排除。

## 三、验收标准

每条都能用一次自动化测试或一次手工操作判定。

1. 档案填 `personal`，一条只标 `large` 的规则进「已排除」，理由里写明两边的规模。— 测试
2. 档案填 `personal` 和 `medium`，一条标 `medium` 的规则照收（有交集就收）。— 测试
3. 规则没标规模时，任何项目规模下都收。— 测试
4. 项目没填规模、或项目没有技术档案时，不筛：所有活跃规则照旧进候选。— 测试
5. 技术档案元数据校验：规模里出现非法值要被拒绝；缺这个字段时补成空数组，不报错。— 测试
6. 技术档案编辑器里能多选四档规模，存回去能读出来。— 手工
7. 编译抽屉里能看到当前按哪些规模筛；没填时显示「不按规模筛」。— 手工
8. 用 0.7.0 采进来的那 6 条做真实验证：给本项目建档案并填 `personal` 后，
   它们在编译候选里进「已排除」，而不是「参与编译」。— 手工
9. 完整检查通过：`npm run check`（类型检查、全部测试、代码检查、生产构建）。— 自动化
