# 项目资产两条链路：文档视图与代码视图（v2.17.0 设计 + 任务清单）

## 来源

2026-09-24 产品负责人复盘时提了四件事，本文只处理其中两件，另外两件单独立项：

| # | 复盘内容 | 本文是否处理 |
| --- | --- | --- |
| 1 | 项目数据只适合本地维护，公共资产适合上云端；项目过程文档体量大，不适合线上维护 | 否，属于「数据来源与云端分工」，另立一版 |
| 2 | 单独做一个代码视图和文档视图，分开导入项目资产 | **是，本版主题** |
| 3 | 验收记录和发布记录本来就有（`docs/acceptance/` 里 30 份清单 + 28 个版本标签），产品里却又有一套平行结构化的「验收记录／发布记录」，两处重复 | **是，本版一起归位** |
| 4 | 项目里只挂着 4 条规则，而公共库 28 条规则里有 24 条的证据就出自本项目 | 否，属于「规则引用模型」，另立一版 |

第 3 件的现场事实：全库 `evidence`（验收记录）0 条、`release_record`（发布记录）0 条——
这两类资产从上线到现在**一次都没被用过**；而同一时间，验收结论一直写在
`docs/acceptance/*.md` 里，发布的事实一直在 git 标签（28 个）和 `CHANGELOG.md` 里。
也就是说：产品按「一条需求一条记录」设计了这套东西，而实际做法是「一版一份清单」。
两套口径同时存在，必然重复。

第 2 件的现场事实：一次「导入工程 → 代码目录」扫出 62 个模块／接口节点，直接灌进了项目图谱，
把人工维护的需求树冲掉了（2026-09-24 已归档处理）。

## 一、做什么 / 不做什么

### 做什么

1. **项目里分成两个视图**：**文档视图**（默认，放需求、规格、交付、验收、发布、规则、模板）
   和**代码视图**（放数据库 Schema 节点、代码目录节点、影响分析）。
   两个视图各自有类型筛选，互不混淆。
2. **导入入口拆成两个**：导入文档（选一批 Markdown，原样建成文档资产，进文档视图）和
   导入代码（SQL 建表语句／本机代码目录，进代码视图）。现在三种来源挤在同一个抽屉的三个页签里，
   是「代码和文档混在一起」的根源。
3. **图谱只收文档型节点**：需求／数据／接口／测试／模块五类节点由人建或按文档建；
   代码目录扫描出的模块和接口节点**不再进项目图谱**，落进代码视图。
4. **文档链路从五段改成六段**：需求 → 规格与计划 → 交付 → **验收** → **发布** → 其他。
   验收按需求走、发布按版本走，两件事的输入不同，合成一段看不出缺哪一环。
5. **验收记录与发布记录并入文档链路**：新建文档时选文档类型「验收记录」或「发布记录」，
   正文写验收条件／步骤／结果，或版本号／门禁／结果；结论、版本号、回滚目标这种**能用来算口径的字段**
   写进文档元数据。工程基线的「链路完整性」和「验收覆盖」改成读文档，不再读那两类结构化资产。
6. **老数据只读保留**：两个旧资产类型仍能读出来、打开、备份、还原，界面上不再提供新建入口
   （现存 0 条，实际没有迁移负担）。
7. **代码视图能看历史**：已归档的 62 个代码扫描节点在代码视图里可见（标明归档），
   要恢复就改状态，不删。

### 不做什么

- **不改数据库表结构**：`asset_type` 是文本字段，验收与发布要用的字段放 `metadata` JSON；
  本机和云端都不需要迁移。
- **不动公共资产库的形态**：它仍然是默认项目，仍然放着规则、提示词、模板和参考文档。
- **不做规则引用模型**（项目引用公共规则，而不是各存一份）：那是下一版，会牵动全部读写路径。
- **不做云端与本机的分工和同步**：同样是下一版；本版不改 `NEXT_PUBLIC_DATA_MODE` 的两态语义。
- **不自动读 git 标签、不接 CI**：版本号、提交号仍然手填，验收结论仍然只能由人在界面上给。
- **不删功能数据**：代码扫描节点归档保留、旧类型只读保留。

## 二、数据和产品行为影响

| 项 | 影响 |
| --- | --- |
| 数据库结构 | 无变化（不新增表／列，不做迁移） |
| 视图 | 项目从 1 个视图变 2 个（文档视图／代码视图）；公共资产视图不变 |
| 导入工程 | 一个抽屉三个页签 → 两个入口：导入文档、导入代码 |
| 项目图谱 | 只显示文档型节点；代码扫描节点改到代码视图，默认不进图谱 |
| 文档分段 | 五段变六段：验收与发布分开；分组依据仍是文档元数据里的文档类型 |
| 验收记录／发布记录 | 由「独立资产类型」改为「文档的两种类型 + 结构化元数据」；工程基线的链路检查与验收覆盖改读文档 |
| 需求覆盖 | 口径不变（还是「哪些需求还没有通过的验收」），但数据来源从 `evidence` 资产改为验收记录文档的元数据 |
| 备份 | 备份格式不变（仍然存 assets／asset_versions）；旧类型资产仍能导入导出 |
| MCP | 验收记录／发布记录改走文档工具；`create_asset` 不再接受这两种类型的新建 |

## 三、验收标准

1. 项目视图里有「文档」和「代码」两个视图，切换后类型筛选和列表内容跟着变，且互不混入。
2. 「导入文档」只产生文档资产；「导入代码」只产生代码视图里的节点；两个入口的文案各自说清产出去哪。
3. 扫描一次代码目录：新节点出现在代码视图，项目图谱里**不出现**；
   已归档的 62 个节点在代码视图里能看到并标明归档状态。
4. 项目文档分组显示六段；同一份文档从「验收记录」改成「发布记录」后，它会从验收段移到发布段。
5. 新建一份文档类型为「验收记录」的文档，填好结论与版本号后：工程基线的「验收覆盖」能算到它，
   「链路完整性」的验收那一环变绿。
6. 新建一份「发布记录」文档并填版本号、回滚目标、结果后：工程基线的「最近一次发布」显示它。
7. 新建资产的类型下拉里不再出现「验收记录」「发布记录」两个独立类型；旧数据仍能打开、备份和还原。
8. `npm run check` 通过（类型检查、自动化测试、lint、生产构建）。

## 下一版（不在本版范围，先记下来）

- **规则引用模型**：项目不再各存一份公共规则的副本，改成引用公共库那份；
  公共库改一处，所有引用它的项目跟着变；项目只持有本项目专属的规则。
  现场证据：公共库 28 条规则里 24 条的证据出自本项目，但项目里只挂 4 条
  （2026-09-24 06:51 一次「从公共资产库挑资产」的自测残留），两边没有同源关系。
- **公共资产上云、项目数据本地**：云端只存公共资产，本机存项目全量，
  一条单向同步（公共库 → 本机），冲突口径只认公共库那份。
  现状是 `NEXT_PUBLIC_DATA_MODE` 二选一、两边各一份全量数据，
  现成的 `scripts/sync-from-cloud.mjs` 是本机主动拉，只新增不覆盖。
  体量事实（2026-09-24 实测）：全库资产 222 条、正文合计 0.21 MB，历史版本 325 条、0.27 MB；
  仓库 `docs/` 84 个文件 567 KB。**两边都放得下，体积不是理由**——真正的理由是维护方式：
  项目文档在 git 里改、公共资产在应用里改，两边的入口和节奏不一样。

## 设计偏差

1. **发布记录的门禁清单跟着文档走**：设计写的是「门禁写进正文」，实现改成门禁仍然结构化存在
   文档元数据里（`metadata.release.gates`）——否则 v2.10.0 的「门禁 x／y 完成」就没数据可算，
   等于删掉一个已经能用的能力。
2. **验收记录用关系表达「覆盖了哪些需求」**：设计没写清挂需求的字段放哪，实现选择复用资产关系
   （一份文档可以指向多条需求），不再单独存 `nodeId`；MCP 侧用 `requirementCode` 换算成关系。
   关系**两个方向都认**：文档指向需求，或需求节点指向文档——图谱里的「批量挂文档」
   挂的正好是后者，只认一个方向会让那条已有的链路白挂。
3. **MCP 仍然能改老类型的验收记录**：新建已经关闭（`mcpWritableAssetTypes` 去掉 `evidence`），
   改内容和状态保持可用，免得老数据在 AI 侧完全动不了。
4. **编辑器里发布记录与老类型共用一套字段**：抽出 `ReleaseFields` 组件，两处渲染同一份界面，
   避免门禁清单出现两套写法。
