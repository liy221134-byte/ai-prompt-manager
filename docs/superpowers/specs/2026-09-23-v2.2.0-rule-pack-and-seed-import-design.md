# 规则包与种子资产包导入设计（v2.2.0）

## 文档状态

- 目标版本：`v2.2.0`（建议编号：`2.1.x` 是资产管理底座的连续迭代，这一版开新的功能线，
  所以进一位到 `2.2.0`；编号要改的话说一声）。
- 状态：**待产品负责人确认**，确认后才开始写代码。
- 这一版对应 [2.0 需求草案](../../v2-requirements-draft.md) 里回填的
  「规则包、理由与来源片段、规则集导出」，并把 [种子资产包](../../../seed-packs/engineering-foundations/README.md)
  正式导入产品做验证。
- 本文只写决定，不写实现步骤、SQL 和成段代码。

## 一、做什么 / 不做什么

### 做什么

1. **规则包**（新资产类型 `rule_pack`）
   - 包级元数据：名称、包版本、状态、可信度（假设／暂时验证／已验证）、适用项目规模、来源、说明。
   - 成员清单：包内资产的稳定标识、类型和优先级；包详情能看到成员、能点进成员详情。
   - 一个项目可以安装多个包：安装后资产进项目，并记下来源包和包内标识。
2. **每条规则补两个字段**：理由（为什么立这条规则）和来源片段（从原文哪句话来），
   编辑器能填、详情能看。
3. **包内非规则内容**：模板和案例按文档资产存，包内原始类型（方法／流程／模板／案例）
   保留在元数据里，界面上仍按产品的类型筛选。
4. **种子资产包导入**：把 `seed-packs/engineering-foundations` 的 17 条资产、3 个项目画像
   和 3 份编译验证记录解析成 1 个规则包 + 附属资产导入产品。
5. **包的导出与再导入**：导出一个包为 JSON 文件（含包元数据和成员），能在别的库导入；
   重复导入同一个包只跳过，不产生重复资产。
6. **备份兼容**：新增字段随 v2 备份一起走；`2.1.x` 时期导出的旧备份仍旧能导入。

### 不做什么

- 不建独立规则表和独立规则抽屉，规则沿用统一资产模型（2026-09-23 复核结论）。
- 不做规则冲突检测与人工裁决：这一版只把「规则包」和「留痕字段」铺好，
  冲突检测与编译一起放到下一版设计。
- 不做编译产出 `AGENTS.md` / `START_PROMPT.md`。
- 不做规则包市场、共享、多人协作。
- 不改提示词侧行为和现有筛选语义。

## 二、数据和产品行为影响

### 字段映射（种子包 → 产品）

| 种子包字段 | 产品里的位置 | 说明 |
| --- | --- | --- |
| `id` | 元数据 `packItemId` + 资产标识前缀 | 保留原编号，方便回溯 |
| `asset_type` | 元数据 `packAssetType` + 产品类型 | `rule`／`method`／`playbook` → 规则资产；`template`／`case_note` → 文档资产 |
| `rule_type` | 规则元数据 `ruleType` | 只有规则类资产有这个字段 |
| `purpose`／`layer`／`scope`／`tech_context`／`lifecycle_phase`／`priority`／`override_allowed`／`verification` | 规则元数据对应字段 | 一一对应，已经存在 |
| `confidence` | 规则元数据 `confidence`（新增） | 假设／暂时验证／已验证 |
| `evidence`／`source_references` | 规则元数据 `evidence`（来源证据） | 合并成一段可读文本，保留原始条目 |
| `project_scale` | 包元数据 + 资产元数据 `projectScale`（新增） | 适用项目规模 |
| `related_assets` | 资产关系 | 导入时按编号建「引用」关系 |
| `version`／`last_reviewed` | 元数据 `packVersion`／`lastReviewedAt`（新增） | 包版本与最近复核日期 |
| `compile_target` | 元数据 `compileTarget`（新增） | 现在只存不用，供下一版编译 |

### 新增字段（全部可选，旧数据缺字段按空值读）

- 规则元数据：`rationale`（理由）、`sourceExcerpt`（来源片段）、`confidence`（可信度）、
  `compileTarget`（编译去向）。
- 通用资产元数据：`pack`（`packId`／`packItemId`／`packVersion`／`packAssetType`／`projectScale`）。
- 包元数据：`packVersion`、`packStatus`、`packConfidence`、`projectScale`、`sourceNote`。

### 行为影响

- 类型筛选新增「规则包」；包详情抽屉支持「安装到项目」和「导出这个包」。
- 安装是**复制**不是引用：包以后升级不会改掉项目里已经确认过的资产，
  资产详情只标注「来自某个包」。
- 成员清单不单独存一份：包详情按资产的 `pack.packId` 扫描得到，避免两处数据打架
  （个人工具的数据量，扫描够用）。
- 本地和云端都不需要改表结构：`asset_type` 本来就是文本字段，
  本地资产表、云端资产表和资产函数都不做类型白名单（已核对）。

## 三、验收标准

1. 把 `seed-packs/engineering-foundations` 导入后，产品里出现 1 个规则包和 17 条成员资产，
   逐条比对类型、优先级、可信度、适用项目规模、来源片段和理由，与 `manifest.md`
   和资产文件的 front-matter 一致。
2. 包详情能看到包元数据（版本、状态、可信度、适用项目规模）和完整成员清单，
   成员可以点进详情。
3. 资产详情能看到所属包、理由和来源片段。
4. 一个项目能安装多个包；安装后在资产列表里能按包筛选，只显示这个包带来的资产。
5. 把某个包导出成 JSON，再导入到一个空库，包和成员被完整重建；
   同一个包重复导入只跳过，不产生重复资产。
6. 导出的 v2 备份包含规则包和新增字段；`2.1.x` 时期导出的旧备份仍能正常导入。
7. 模板和案例落在文档类型，方法、流程和规则落在规则类型，包内原始类型在界面上可见。
8. `npm run check` 通过（类型检查、自动化测试、lint、生产构建）。

## 五、需要你拍板的三个决定

1. **类型映射**：方法、流程、规则 → 规则资产；模板、案例、画像、验证记录 → 文档资产；
   包内原始类型保留在元数据里。按这个做可以吗？
2. **规则包的载体**：新增资产类型 `rule_pack`（建议），还是复用现有的 `source_package`？
   建议新增：来源包是上传的原文包，规则包是可复用的知识单元，语义不同。
3. **安装方式**：安装 = 把包内资产复制进项目并记录来源（建议），不是实时引用。确认吗？
