# AI 提示词优化设计

## 文档状态

- 方案：B —— 元数据 + 正文结构优化，只做整理和规范化，不改变原意。
- 版本目标：`v0.9.0`（暂定，实施前确认）。
- 状态：设计草案，等待确认后再写实施计划，不进入当前 `v0.8.0` 开发。
- 前置依赖：`v0.8.0`（AI 合并与垃圾箱）先合并到 `main`，提供 `prompt_versions`
  快照表、`prompts` 的软删除字段和清理任务。

## 目标

让一条已有提示词在**不改变原意**的前提下变得更好用：元数据更准确、正文结构更
统一、变量更规范；优化结果必须由用户预览确认，并且可以随时回到优化前。

核心流程：

```text
打开提示词
-> 点击「AI 优化」
-> AI 返回优化草稿和优化说明
-> 用户对比、编辑、确认
-> 保存并生成优化前快照
-> 需要时可以回到优化前
```

## 本期范围

### 包含

- 元数据优化：标题、分类、标签、适用场景。
- 正文结构优化：只做整理和规范化，不改变原意。
- 可选「优化要求」输入，用于说明整理方向。
- 优化说明：AI 逐条说明改了什么、没改什么。
- 优化前后差异对比：按行显示新增、删除和修改。
- 变量变化清单：新增变量、写法统一、重命名映射。
- 保存前可编辑全部字段。
- 保存时自动生成「优化前」快照，支持回到优化前。
- 优化记录列表：时间、说明摘要、剩余保留天数和回退入口。
- 本地 SQLite 与云端 Supabase 行为一致。

### 不包含

- 按目标改写（更简洁版、更严格版、面向特定模型的版本），属于方案 C。
- 批量优化多条提示词。
- 把合并记录和优化记录合并成统一的完整版本历史。
- 提示词分支和合并关系图。
- 手动创建版本、手动命名版本。

## 优化规则

这一节是本方案的核心：明确 AI 允许改什么、禁止改什么。

### 允许的改动（白名单）

1. 统一 Markdown 结构：标题层级、列表符号、代码块、段落空行。
2. 补全结构小节标题，例如把散落的要求整理到「任务」「约束」「输出格式」小节下。
3. 把非标准占位符统一成 `{{变量名}}`，例如 `[项目名称]`、`<项目名称>`、
   `{{ 项目名称 }}` 统一为 `{{项目名称}}`。
4. 修正明显的排版错误：多余空行、错位的编号、Markdown 语法错误。
5. 元数据优化：标题更简洁、分类归入已有分类、标签补齐到 8 个以内、
   适用场景补全。

### 禁止的改动（黑名单）

1. 不得新增原文没有的约束、要求、示例、背景知识。
2. 不得删除或弱化任何一条原始要求。
3. 不得改变提示词的目标、语气、受众和角色设定。
4. 不得改变输出格式的实际含义，只能规范化写法。
5. 不得改变变量语义，不得静默重命名用户已有的变量。
6. 不得添加模型平台专属限制，例如「仅适用于某个模型」。
7. 不得编造事实、数据或专业结论。

### 变量安全规则

- 原文已经存在的变量，默认保持原名不变。
- 只把非标准写法统一为 `{{变量名}}`，并在「变量变化清单」中列出。
- 只有用户主动打开「允许统一变量名」开关时，才允许把指向同一内容的多个变量
  合并成一个名字；此时必须在清单里列出完整映射。

### 长度与限额

- 单条正文最多 20000 个字符，与 AI 合并接口保持一致。
- 优化后正文不得超过 30000 个字符，超过时禁止保存并提示用户手动处理。
- 优化后正文超过原文 1.5 倍时，预览中显示提醒。

## 用户交互设计

### 入口

提示词详情抽屉增加「AI 优化」按钮，放在「编辑」按钮旁边。

编辑抽屉本期不增加入口：编辑抽屉里可能有未保存的修改，两套草稿容易互相覆盖。
如果希望在编辑时也能优化，需要「先保存再优化」的确认步骤，建议放到后续版本。

### 优化面板

点击后打开优化抽屉，分区显示：

1. 当前提示词摘要：标题、分类、标签、适用场景。
2. 可选「优化要求」文本框，最多 2000 个字符。示例：

```text
统一成 Markdown 小节
不要改动变量名
保留原有示例
```

3. 「允许统一变量名」开关，默认关闭。
4. 「开始优化」按钮。

生成过程中显示进度提示；失败时保留用户输入，并提供重试入口。

### 优化结果

生成后显示：

- 优化说明：只读，1 至 6 条，说明改了什么、没改什么。
- 可编辑草稿：标题、分类、标签、适用场景、Markdown 正文。
- 差异对比：正文按行对比，新增行、删除行、修改行分别标识，默认折叠为摘要，
  可展开查看全文。
- 变量变化清单：新增变量、写法统一、重命名映射。

### 保存

保存按钮必须说明影响，例如：

```text
保存优化结果，并保留优化前版本（30 天内可回退）
```

点击保存前不修改任何数据。保存成功后：

- 提示词更新为优化结果。
- 生成一份「优化前」快照。
- 页面提示「已保存，可回到优化前」，并提供回退入口。

### 优化记录与回退

详情抽屉增加「优化记录」入口，列出该提示词的优化快照：

- 优化时间。
- 优化说明摘要。
- 剩余保留天数。
- 「回到这个版本」按钮。

回退必须二次确认。回退不是删除版本，而是把当前内容替换为快照内容；本设计默认
同时生成一份「回退前」快照，避免回退本身不可撤销（见待确认问题 3）。

## 数据模型

复用 `v0.8.0` 已建的 `prompt_versions` 表，不新增表。

### `version_reason` 取值

| 取值 | 含义 | 来源 |
| --- | --- | --- |
| `merge_before` | AI 合并前的目标提示词快照 | `v0.8.0` |
| `optimize_before` | AI 优化前的提示词快照 | 本期新增 |
| `restore_before` | 回退前的提示词快照 | 本期新增（取决于待确认问题 3） |

`version_reason` 是 `text not null`，没有枚举约束，因此**不需要修改表结构**。

### 快照数量与保留

- 沿用 30 天过期策略，由现有清理任务统一处理，不新增定时任务。
- 同一个提示词的优化快照最多保留 20 条，超出时删除最旧的记录。

### 本地 SQLite

- `version_reason` 的类型从固定的 `"merge_before"` 放宽为联合类型。
- 其余结构不变，不需要数据迁移，升级过程不得丢失现有数据。

## 接口设计

### AI 优化接口

```text
POST /api/ai/optimize-prompt
```

输入：

```json
{
  "prompt": {
    "id": "prompt-1",
    "title": "标题",
    "category": "分类",
    "tags": ["标签"],
    "content": "正文",
    "useCase": "适用场景"
  },
  "instruction": "可选优化要求",
  "allowVariableRename": false
}
```

输出：

```json
{
  "draft": {
    "title": "优化后的标题",
    "category": "分类",
    "tags": ["标签"],
    "content": "优化后的正文",
    "useCase": "适用场景",
    "optimizationSummary": ["统一了小节结构", "把 [项目名称] 统一为 {{项目名称}}"],
    "variableChanges": [
      { "type": "normalized", "from": "[项目名称]", "to": "{{项目名称}}" }
    ]
  }
}
```

接口规则：

- 云端模式必须先登录。
- 正文最多 20000 个字符，优化要求最多 2000 个字符，超限返回明确错误。
- 超时 50 秒，失败返回明确错误，不写入任何数据。
- 提示词正文作为数据传入，不作为系统指令执行。
- AI 输出必须经过结构化校验，字段超长时按现有规则处理。
- 优化说明至少 1 条、最多 6 条。
- AI 不得直接写数据库。

### 保存接口

```text
POST /api/prompts/ai-optimize
```

输入只包含优化结果、提示词标识和客户端生成的 `versionId`。快照内容必须由服务端
在事务内读取当前提示词生成，客户端提交的「优化前内容」不得进入快照。这一点与
`v0.8.0` 的合并提交保持一致。

- 云端：新增 PostgreSQL 函数 `commit_prompt_optimize`，使用 `SECURITY INVOKER`，
  在同一事务内完成「校验用户 → 锁定并读取当前提示词 → 写入 `optimize_before`
  快照 → 更新提示词」。
- 本地：使用同一个 SQLite 事务完成等价操作。

### 回退接口

```text
POST /api/prompts/ai-optimize/restore
```

输入为 `versionId`。云端使用 `restore_prompt_optimize` 函数，本地使用等价事务，
回退后把快照标记为已恢复。

### 数据源接口扩展

`PromptDataSource` 增加：

```text
commitAiOptimize
fetchOptimizeVersions
restoreOptimizeVersion
```

## 错误处理

- AI 生成失败或超时：保留用户输入，可重试，不修改数据。
- AI 返回格式错误：提示重试，不写入数据库。
- 用户取消：不修改数据。
- 保存失败：事务回滚，提示词保持原样，不出现部分更新。
- 回退失败：快照状态和提示词内容都保持不变。
- 网络失败：提示重试，不自动重放写操作。

## 安全要求

- 所有读写都必须遵守当前用户隔离，云端依赖 RLS，本地为单用户模式。
- 云端只有登录用户可以调用优化接口。
- 不把提示词全文、AI Key、请求头写入应用日志。
- 不向浏览器暴露 AI Key 和 Service Role Key。
- 优化结果必须经过用户确认后才写入数据库。

## 成本影响

- 复用现有 `AI_API_BASE_URL`、`AI_API_KEY`、`AI_MODEL`，不引入新库或新服务。
- 每次优化调用 1 次 AI 请求，输入约等于单条提示词全文，成本低于 AI 合并。
- 不新增定时任务，不新增第三方依赖。

## 测试范围

### 单元测试

- 请求校验：正文长度、优化要求长度、变量开关。
- AI 输出解析和异常 JSON 处理。
- 优化说明与变量变化清单清洗。
- 行级差异对比计算。
- `version_reason` 类型放宽后的兼容处理。

### 数据库测试

- 保存优化结果时生成 `optimize_before` 快照。
- 保存具有原子性，失败时整体回滚。
- 回退恢复为快照内容并标记 `restored_at`。
- 优化快照数量上限清理。
- 过期清理覆盖优化快照。
- 本地 SQLite 旧库升级不丢失数据。

### 云端验证

- 未登录不能调用优化接口。
- 用户只能读取自己的优化记录。
- 优化后刷新页面结果一致。
- 回退后内容正确，来源数据不受影响。

## 风险与处理

### AI 改动超出「不改变原意」

- 在 system 提示词中写明白名单和黑名单。
- 强制返回优化说明，超出范围的改动要在预览中可见。
- 保存前必须人工确认。

### 变量被改名导致已填过的变量值失效

- 默认禁止重命名。
- 只有用户打开开关才允许，并展示完整映射表。

### 正文被越改越长

- 超过 30000 个字符禁止保存。
- 超过原文 1.5 倍时显示提醒。

### 预览信息过载

- 差异对比默认折叠为摘要，可展开查看全文。
- 优化说明最多 6 条。

### 快照过多

- 沿用 30 天过期策略，并限制单个提示词的优化快照数量。

## 已定方案

以下 5 项在 2026-09-20 的流程复盘中定稿，实施时按此执行；如果后续发现不合适，
可以单独提出修改，不阻塞其他部分。

1. **正文改动采用「整段替换 + 全文对比 + 可编辑草稿」**：与 AI 合并的交互一致，
   我的学习成本最低；「逐段建议、逐条接受」会把复杂度推到前后端段落映射上，
   收益不明显。
2. **保留「允许统一变量名」开关，默认关闭**：变量改名会让已填过的值失效，所以
   安全默认是不改名，开关把选择权交给我。
3. **回退时生成新的「回退前」快照**：回退本身也是一次覆盖。没有新快照就无法撤销
   误操作，这与「AI 不得静默覆盖内容」一致。
4. **同一个提示词最多保留 20 条优化快照**：与 30 天过期策略叠加后足够回溯，同时
   避免单个提示词的版本无限增长。
5. **版本号为 `v0.9.0`**。

## 当前阻塞

本功能依赖 `v0.8.0` 提供的 `prompt_versions` 快照表和清理任务，因此顺序是：

```text
v0.8.0 合并到 main
-> 云端执行 Supabase 迁移并验证
-> 再开始 v0.9.0
```

注意：`main` 分支推送会触发 Vercel 生产部署，所以在 Supabase 迁移执行并验证之前，
`v0.8.0` 分支不能先合并到 `main`，否则线上代码会依赖尚不存在的数据库结构。
