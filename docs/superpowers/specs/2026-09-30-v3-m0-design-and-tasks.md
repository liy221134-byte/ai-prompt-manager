# 零代码交付线 M0：设计 + 任务清单

日期：2026-09-30。状态：**已确认，T1/T2 已落地（2026-09-30）**——产品公共资产库已建两条 M0 资产并推云端：`rule-delivery-checklist-v3m0`（环境交付清单）、`template-deploy-rollback-handbook-v3m0`（部署/回滚手册模板），均 `draft`、来源 `manual`。T3/T4 等用户定第一条实战项目（Q3）后跑。

本稿把 v3 需求草案（已确认）第五节的 M0 落成一版可执行的「设计 + 任务清单」。  
M0 不写代码、不引新依赖，纯粹用现有产品的**规则包与模板机制**，装一份「环境交付清单」  
和一本「部署/回滚手册模板」，在下一个真实交付项目里手工跑一遍，把卡点记下来。

**M1–M3 不在本稿设计范围内**——它们的内容要等 M0 真跑出卡点才有资格写（见第六节）。

---

## 一、目标与边界

**目标**：把手上已有的资产（规则、模板、验收证据链）第一次接到「真实环境交付」这条链路上，  
跑通一次，知道哪些环节值得以后做成代码。

**做（M0 范围）**：

- 用现有规则包机制，建一份「环境交付清单」，覆盖草案第三节断点清单的 7 个环节
- 用现有模板机制，建一本「部署/回滚手册模板」
- 选一个真实交付项目，手工按清单走一遍
- 每个勾不了、卡住的环节，记成待办

**不做（明确排除）**：

- 不动任何代码，不新增 npm 依赖
- 不建环境台账数据对象（那是 M1）
- 不做制品包打包脚本、迁移守门（M2）
- 不接 MCP（M3）
- 不写「通用部署手册」——锚定真实项目，不造场景（草案：「用真实项目验收，不用造场景」）

---

## 二、载体：怎么「装」进现有产品

草案说 M0 用「规则包与模板机制」。具体落法（设计确认后才执行）：

- **环境交付清单** → 作为一条 rule（或一组 rule）进公共资产库，类型 `draft`，  
  形态是带勾选标准的 checklist；来源标注本产品（不是外部采集，不走台账落库命令）
- **部署/回滚手册** → 作为 `template` 进资产库
- 这样它们能像其他资产一样被引用、被编译候选集收，M0 跑出的卡点也能直接挂到资产上

---

## 三、既定约束（写死，后面段也沿用）

这些是本稿的硬输入，不是待定项：

- **数据库双库**：MySQL 与 PostgreSQL 都是第一类目标，迁移守门默认同时覆盖两者
- **部署目标**：大陆边上的云（阿里云 / 腾讯云 / 华为云 / 浪潮云等国内可达 RDS），不走境外
- **架构抽象（草案第十节）**：将来数据库层 / 认证层要留抽象，M0 虽不碰代码，  
  但卡点记录要往「换库不改几十个文件」这个方向攒——凡卡在「换库要改很多地方」的，  
  记下来作为 M1 抽象层的需求素材

**待用户确认的输入（不阻塞开工，但第一次实战前要有）**：

- Q1 公司代码仓库是 Gitea / GitLab / 别的？——决定 CI 模板怎么写
- Q2 客户服务器怎么进：直连 SSH / 堡垒机 / 网闸摆渡？——决定部署走「推」还是「拉」
- Q3 第一条实战对象是哪个项目？——用真实项目，不造场景
- Q4 数据库以 MySQL 还是 PG 为主？——**用户已定：两者都做**（见上「数据库双库」）

## 四、任务清单

### T1 建环境交付清单（rule 形态）

- 覆盖草案第三节的 7 个环节：环境信息登记 / 部署动作单 / 数据库迁移 / 回滚预案 /  
  内网摆渡清单 / 部署后验证 / 出故障排查
- 每项给「勾选标准」和「卡点记录位」
- 落库：`draft`、公共资产库、来源标注本产品
- 验收：资产库里能搜到，且 7 环节齐全

### T2 建部署/回滚手册模板（template 形态）

- 含：环境档案段、部署步骤段、回滚步骤段、验证段、排查段
- 留占位符，实战时填真实值
- 落库：资产库 `template`
- 验收：能被真实项目引用、占位符清晰

### T3 选实战项目 + 手工跑一遍

- 用户定 Q3 后，在真实项目里按清单走
- 每环节要么勾选、要么记卡点（不强行勾）

### T4 卡点回收

- 把所有勾不了 / 卡住的环节汇总成待办
- 标注分类：**值得做成代码**（→ M1–M3 候选）/ **永远手工**（不值得自动化）
- 这份回收表是 M1 设计的唯一输入

## 五、验收（仅 M0 层）

1. 环境交付清单已进资产库，覆盖草案第三节全部 7 个环节
2. 部署/回滚手册模板已进资产库，可被真实项目引用
3. 至少一次真实交付，清单上每个环节要么勾选、要么有卡点记录
4. 卡点已汇总成待办，且标注了「值得做成代码 / 永远手工」的分类
5. 全程零代码、零新依赖

> 草案第七节那 10 条整线验收里，属于环境台账（#1/#2/#3/#4）、迁移守门（#6/#7）、  
> MCP 只读（#8/#10）、部署记录（#9）的几条，**本稿不验**——它们要 M1–M3 的代码才成立，  
> 留给对应段的设计文档。

## 六、M1–M3 为什么现在不设计

它们的内容来自 M0 跑出的卡点，不是凭空设计：

- **环境台账（M1）** = 把 M0 手工登记的「环境信息」变成一等对象
- **制品包 + 迁移守门（M2）** = 把 M0 卡住的「迁移完整性 / 摆渡清单」变成脚本
- **只读 MCP（M3）** = 把 M0 手工「看服务状态 / 版本」变成工具

所以 M0 跑完、T4 卡点回收后，再写 M1 设计——那时才有真素材，不会白做。
