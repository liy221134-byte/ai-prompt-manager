# 本地与云端定期同步（v2.19.0 设计 + 任务清单）

## 来源

2026-09-24 讨论：本机是干活的地方、云端是随时能看的地方，两边长期各存一份全量。
产品负责人拍板走**方案 A（定期双向同步）**，理由是数据量很小，冲突用规则管住就行。

体量事实：全库约 250 条资产、正文合计 0.2 MB、库文件 1.7 MB
（Supabase 免费额度 500 MB）。**体积不是约束**，要管的是冲突和谁来触发。

## 一、做什么 / 不做什么

### 做什么

1. **同步计划**（纯逻辑）：两边各一份全量，按资产标识配对，算出「推到云端」「拉到本机」
   「待裁决」「两边一样」四类。项目行同样按标识补齐。
2. **三条纪律**：
   - **只增不删**：同步不做物理删除；删除状态（`deletedAt`）本身照常同步过去。
   - **谁新谁赢**：两边都有同一条时按 `updatedAt` 比，新的覆盖旧的；被覆盖的内容留在
     那一侧的版本记录里，能回退。
   - **判不出来就留**：时间一样但内容不同 → 两边都不动，列进待裁决清单，由人决定。
3. **一条命令**：`npm run sync`（默认双向；`--dry-run` 只看、`--push`／`--pull` 限方向）。
4. **连不上云端时的兜底**：`npm run sync -- --export-push-file` 导出全量本机备份，
   到线上站点用「数据管理 → 导入备份」推上去（只增不覆盖）。
5. **写入留痕**：推上云端时同时写一条 `asset_versions`，和界面写入保持同一口径。

### 不做什么

- **不做共同祖先比对**：只按时间判新，不维护"上次同步时的状态"。真要精确判"两边都改过"，
  得引入同步快照，本版不做（见风险）。
- **不带历史版本**：同步只同步资产主行（当前内容），历史版本不跟着走——备份本来也不含历史版本。
- **不做自动定时任务**：本版只给命令。要"每天自动跑一次"，那是 Codex 定时任务或云端定时入口的事。
- **不做云端侧同步入口**：本机连不上 Supabase 时不能直连推送（见"网络事实"），
  这条要靠备份导入兜底；云端侧做一个受保护的同步入口属于下一版。
- **不做冲突裁决界面**：待裁决只打印在命令行，由人来处理。

## 二、网络事实（2026-09-24 实测）

开发机直连 `https://<项目>.supabase.co` 时 **TLS 握手被重置**（`ECONNRESET`；
换成 TLS 1.2、HTTP/1.1、浏览器 UA 都一样）。同时 `supabase.com`、`github.com`、
`vercel.com` 都正常，说明不是整体断网，而是这个主机的出口被针对性地拦了。

影响：**这台机器现在不能直接用 REST 推送/拉取**。两条可用路径：

1. 换网络（手机热点等）后跑 `npm run sync`。
2. 用 `--export-push-file` 导出备份，到线上站点导入（走 Vercel 的网络，不经过本机出口）。

## 三、数据和产品行为影响

| 项 | 影响 |
| --- | --- |
| 数据库结构 | 两边都不变 |
| 本机写入 | 走本机库这一层，每次写入留版本记录 |
| 云端写入 | 服务角色直连 upsert，同时补一条 `asset_versions` |
| 冲突 | 不自动合并，列出来等人裁决 |
| 备份 | 不变；同步复用同一套备份格式 |

## 四、验收标准

1. `planAssetSync` 能算出四类：推、拉、待裁决、一样；方向限定时另一向不动。
   依据：`tests/asset-sync.test.mjs`（6 条）。
2. 两边内容一样时不算冲突、不动。
3. 时间一样但内容不同 → 进待裁决，两边都不动。
4. `npm run sync -- --dry-run` 能打印本机/云端条数与四类计数。
5. `--export-push-file` 能导出备份文件，线上导入后云端条数等于两边并集。
6. `npm run check` 通过。

## 六、风险与已知缺口

- **时间判新不可靠**：两台机器的时钟不同步、或者两边在同一分钟内都改过，可能判错。
  被覆盖的内容仍在版本记录里，但要知道去哪儿找。
- **待裁决没有界面**：只在命令行列出；条数多了要人工比对。
- **本机出口被拦**：不换网络就推不上去，只能用备份导入兜底。
