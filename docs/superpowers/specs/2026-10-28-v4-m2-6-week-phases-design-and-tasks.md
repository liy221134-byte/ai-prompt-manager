## 一、做什么 / 不做什么

### 做三件事

1. 目标上存一份「阶段定义」：四段的名称、起止日、里程碑。
2. 今日计划多显示一行：现在第几周、在哪个阶段、离下一个里程碑还有几天。
3. 设置弹窗里能改这份阶段定义，并且有一个「按目标日期自动切分」的按钮。

### 不做（每条都有理由，不是省事）

- **不做阶段门禁**：不到基础期就不让做某个模块的题。
  阶段日期是估算，模块工时也是估算，两个估算互相约束只会放大误差；更要紧的是，
  它会把「今天有空想多学」变成「系统不让」。今天计划的现有语义是「建议」，不是「许可」，这条不能破。
- **不存「当前在哪一段」**：由日期现算。存了就得每天维护，算出来永不落后。
- **不与模块摊派做强一致校验**：阶段是人的外框，模块窗口是按工时分的内框，两者错开是常态。
  每日弹一条「阶段与模块不一致」等于噪声。产品已经在用「两套位置并列」的做法
  （`plannedModule` vs `actualModule`），这里沿用同一个态度。
- **不改模块摊派算法**（`allocateModuleDays`），不改取题顺序，不改配额公式。
- **不做多套阶段方案、不做模板库、不做拖拽调整、不做提醒推送**。
  报名提醒那件事在 `v4-plan.md` 判断 3 里已定：产品只加倒计时，兜底靠手机日历。

## 二、数据与产品行为影响

### 2.1 表：`learning_goals` 加一列

`phases jsonb not null default '[]'`，元素形状：

```
{ key, name, start, end, milestone: { date, label } | null }
```

- 数据库层只挡脏类型：必须是数组、最多 8 段。段间连续性**不进数据库约束**，
  由保存时的归一化保证（见 2.3）。
- **为什么不上独立表**：一个目标最多 8 段，用途是「读出来展示 + 一次计算」，
  没有按段聚合查询的需求。建表要多一套 RLS、索引和关联查询，收益为零。
  将来真需要按段统计时再加，那是一次带数据的迁移，成本可控。
- **回滚**：`drop column phases`。新列默认空数组，不影响现有任何查询。

### 2.2 派生：`resolvePhase(phases, today)`

返回 `{ index, name, start, end, weekIndex, weeksTotal, daysLeftInPhase, milestone, state }`，
`state` 取 `before / inside / after`。

三条边界口径，必须写死在测试里：

- 今天早于第一段起点 → 返回**第一段** + `before`（界面上说「还没开始，还有 N 天」）。
- 今天晚于最后一段终点 → 返回**最后一段** + `after`（说「已过 N 天」）。
- **不返回 null 来表达「不在任何段内」**。返回 null 会让界面在某一天突然整行消失，
  让人以为功能坏了。
- `phases` 为空数组、非数组、缺字段、`start > end` → 返回 `null`，界面整行不渲染，
  **不抛错**。配置坏了不该让今日计划整块挂掉。

`weekIndex` 从**本段起点**算（第 3 周＝本段第 3 周），不从整个目标起点算——
「启动期第 3 周」比「目标第 24 天」好读。

### 2.3 自动切分：比例，不是日期

`autoSplitPhases(targetDate, startedAt)` 按 **8 : 8 : 9 : 5** 切四段（共 30 周），
首尾相接、最后一段收在 `targetDate`。

- 这个比例是**魔数，来源可查**：2026-10-28 读到的飞书周计划表就是 8/8/9/4+1 周（30 周）。
  替换成别的比例只需改一个常量，但常量旁必须留这条注释。
- **不照抄那张表的日期**：它是 30 周的高项排布，中项从现在到 2027-05-22 只有约 28.6 周。
  抄日期＝把别人的日历套到自己头上。日期一律由 `targetDate` 现算。
- 没有 `target_date` 时按钮禁用，并说明「先设目标日期」——**不猜一个日期出来**，
  这和今日计划里「都留空时兜底成无终点」是同一条原则。

保存时归一化，三件事：去掉首尾空白、`start <= end`、按 `start` 排序。
归一化后仍不合法就拒绝保存并说清哪一行不对，**不静默修正**。

### 2.4 界面改动两处

1. **主题页今日计划卡片**（`learning-topic.tsx` 今日计划那一段）：加一行阶段信息。
   文案形状：`第 3 周 / 共 8 周 · 启动期 · 距「摸底模考」还有 4 天`。
   没有里程碑时省掉最后一段；`state` 为 `before` / `after` 时换成对应说法。
   **不放占位**：没有 phases 就不渲染这一行，不显示「未设置阶段」——
   未设置是常态，不是异常，不用天天提醒。

2. **设置弹窗**（`goal-settings-dialog.tsx`）：新增「阶段划分」小节，
   4 行（名称 / 起 / 止 / 里程碑日 + 里程碑名）+「按目标日期自动切分」按钮 + 保存。
   沿用弹窗现有风格，不新开页面。

## 三、验收标准

每条都能用一次测试或一次手工验证判定。

1. 迁移在本地 PGlite 与真库都能执行；`phases` 列存在、默认 `[]`、既有行不受影响。
2. **执行后必须往 `schema_migrations` 插一条对应记录**——手动迁移不进记录，
   下次 GitHub 集成会自动重跑，撞上重复建列报错（2026-10-28 踩过一次）。
3. 单测覆盖 `resolvePhase` 五种边界：段首日、段末日、早于第一段、晚于最后一段、段间边界。
4. 单测覆盖非法输入四种：空数组、非数组、缺 `start`、`start > end` → 返回 `null` 且不抛错。
5. 单测覆盖 `autoSplitPhases`：四段首尾相接无缝隙、最后一段 `end` 等于目标日、
   总天数等于目标区间天数。
6. 浏览器实测：目标有 phases 时，今日计划卡片出现阶段行，文案与库内值一致。
7. 浏览器实测：无 phases 时该行**不渲染**（不是显示「未设置」）。
8. 浏览器实测：点「自动切分」保存后刷新，四段日期落库且连续；改掉目标日期再切一次，段随之变化。
9. **不影响做题**：同一份输入，有 phases 与无 phases 两种情况下，
   题单、配额、`status`、`headline` 完全一致。这条是防回归的主证据。
10. `npm run check:fast` 全绿。
