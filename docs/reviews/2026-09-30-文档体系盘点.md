## 0. 一句话结论

- **那次"整理"没有模板，不是因为技能没装**：`create-prd`（PRD 技能）WB 侧已经装了；zod 当时按你的拍板落成了**规则**（`AGENTS.md` 第 7 条 + 种子包 `RULE-SCHEMA-CHECK-001`），形态是"约束"不是"模板"，所以你找不到"zod 模板"是正常的。
- **真正的缺口**是：PRD / SDD / 数字契约（zod）这三类**可复用模板文件**，在 CodeX 项目侧从未沉淀；zod 目前只有"规则"这一种形态，没有"可复制骨架"。
- **WB 侧缺 SDD 类技能、缺 zod 契约技能**；CodeX `templates/` 缺 PRD / SDD / 契约模板。两边最大的**共同缺口**就是这三类模板。

## 1. 先回答核心疑问：为什么那次整理没有模板？

把那次动作拆开看，它本质是"**技能盘点 + 挂载**"，不是"模板沉淀"：

1. **技能挂载动作**：把 Codex 的 `create-prd` / `test-scenarios` / `next-dev-loop` / `dummy-dataset` 等挂到 WB，WB 从 8 个涨到 12 个。这是技能层面的事，和模板无关。
2. **zod 数字契约的归处**：当时你拍板把它作为**规则**写进 `AGENTS.md` 第 7 条，并落到工程方法种子包（规则编号 `RULE-SCHEMA-CHECK-001`）。
   - 规则 = "遇到 AI 产出 / 外部输入，先过 schema 校验"的**强制约束**；
   - 模板 = "一份可复制的 `.md` 骨架"，告诉你**怎么写一份契约**。
   - 两者用途不同，所以你找不到"zod 模板"——它本来就没被做成模板形态。
3. **PRD 模板的去向**：WB 侧 `create-prd` 技能**已装**（通用 8 段 PRD）。但 Codex 项目侧 `templates/` 里**没有 PRD 模板文件**——CodeX 自己的大需求走的是 `AGENTS.md` 的"设计 + 任务清单"路线，没有独立的 PRD 模板。

**所以答案**：技能基本都装了；缺的是**项目侧可复用模板文件**（PRD / SDD / 契约），以及 WB 侧缺 SDD、zod 契约两个技能。根因是那次动作定位在"技能挂载 + 规则落地"，**模板沉淀被跳过了**。

> 一个值得你拍板的点：你当时把 zod 落为"规则"而非"模板"。现在回头看——你想要的到底是"强制约束"（规则），还是"可复制骨架"（模板）？其实两者不冲突：**规则管"必须做"，模板管"怎么做"**。后面第 4 节建议双形态并存。

**几个关键观察**：

- Codex 的文档体系是"**模板 + ADR + 规则**"三件套，偏*项目内沉淀*；WB 是"**技能**"驱动，偏*即开即用*。两边形态不一样，不是谁多谁少的问题。
- 两边**最大的共同缺口**完全一致：**PRD 模板、SDD 模板、zod 数字契约模板**。
- zod 在 Codex 是"规则"不是"模板"——这是个有意思的设计分叉，值得你定：要不要也补一份契约模板？
- Codex 已有 `templates/engineering/implementation-spec.md`（实现规约），它和 SDD 容易混。区别在于：**实现规约是"代码层面怎么改"，SDD 是"目标 + 仓库上下文 + 约束 + 验收"**——前者是后者的子集。补 SDD 时不该和实现规约重复，SDD 要往上提一层。

## 3. 主流文档体系调研：优劣对比

| 体系                              | 是什么                                                                                                                       | 适用场景         | 优点                             | 缺点 / 风险                | 对 CodeX 的适配度                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------ | ---------------------- | ----------------------------------------------- |
| **PRD**（产品需求文档）                 | 大需求阐述，轻量 8 段（Summary / Contacts / Background / Objective / Segments / Value / Solution / Release）；Amazon 逆向工作法            | 新功能 / 新方向立项  | 对齐 stakeholder、可逆工作法、结构清晰、可读性高 | 易写成"功能清单"、维护成本高、易过时    | **高**——CodeX 有"设计+任务清单"但无独立 PRD，可补              |
| **ADR**（架构决策记录，Michael Nygard）  | 轻量：Context / Decision / Alternatives / Consequences + Status 生命周期                                                         | 架构 / 技术选型留痕  | 极轻、决策可追溯、不绑定实现、零维护负担           | 只记"决策"不记"how-to"、需纪律维护 | **已用（7 份），成熟**                                  |
| **Diataxis**（四象限）               | Tutorial / How-to / Reference / Explanation 分类法                                                                           | 文档站 / 知识库组织  | 分类科学、用户导向、防混淆                  | 需持续分类、对内部开发项目偏重        | **中**——适合资料库 / 帮助文档，不适合核心开发文档                   |
| **arc42 + C4**                  | 12 章节架构模板 + 分层图（Context / Container / Component）                                                                          | 复杂系统架构文档     | 全面、标准化、利于新人 onboard            | 重、对小项目过度工程             | **低-中**——CodeX 已有 `architecture.md` 模板，arc42 偏重 |
| **SDD（软件设计文档，IEEE 1016）vs RFC** | AI 时代的 SDD = 给 Agent 的"执行包"（Plain-English goal / Repo-aware context / Constraints / Acceptance / Validation）；RFC = 人类评审导向 | AI 辅助开发的设计文档 | SDD 直接可执行、RFC 防昂贵错误            | SDD 需配套验证机制；RFC 偏慢     | **高**——Codex 走 AI 辅助开发，SDD（执行包形态）比传统 SDD 更贴     |

**几个调研结论**：

- **PRD 和 SDD 不是一回事**：PRD 解决"为什么要做、做成什么样"（面向人/ stakeholder）；SDD 解决"怎么落地、Agent 怎么执行"（面向实现）。Codex 现在用"设计+任务清单"部分覆盖了 SDD 的"决策"部分，但缺 PRD 的"背景与价值"部分和 SDD 的"验收场景"部分。
- **ADR 是 Codex 已经做对的事**，不用动，保持即可。
- **arc42 / Diataxis 对 Codex 偏重**：Codex 是单人 PM + AI 的内部工具，不是大型团队文档站，引入 arc42 会制造维护负担，性价比低。
- **AI 时代的 SDD 形态最值得抄**：把 SDD 写成"执行包"而非"立场文件"，正好契合 Codex"AI 辅助开发 + 验收门"的现有流程。

## 4. 综合判断与建议（供你拍板）

**建议采用的体系组合**：`PRD（大需求）+ ADR（已用）+ SDD（AI 执行包形态）+ zod 数字契约模板`，**不引入 arc42 / Diataxis**（偏重 / 偏文档站）。

**具体建议**：

1. **补三类模板到 CodeX `templates/`**：
   - `templates/product/prd.md`——大需求阐述，8 段结构，和现有"设计+任务清单"衔接（PRD 定"做不做、为什么"，设计门定"怎么做"）。
   - `templates/engineering/sdd.md`——AI 执行包形态：目标（自然语言）/ 仓库上下文 / 约束 / 验收标准 / 验证场景。往上提一层，不和 `implementation-spec.md` 重复。
   - `templates/engineering/contract.md`——数字契约模板：用 zod 定义输入/输出 schema 的可复制骨架。
2. **zod 契约双形态并存**：保留 `AGENTS.md` 第 7 条作为**强制规则**（管"必须做"），同时补 `contract.md` 作为**可复制模板**（管"怎么做"）。两者互补，不冲突。
3. **WB 侧技能**：现有市场没有成熟的 SDD / zod 契约技能。可选——（a）从 Codex 的 `templates/` 反向生成 WB 技能挂载；（b）暂用 Codex 模板代替，不单独造技能。这条等你定。
