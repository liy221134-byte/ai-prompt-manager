## 一、豆包那份内容的核对结果

结论先给：**方向对，具体工具报错不少，别照着它写的名字去装。**

### 成立的部分（可以直接用）

| 它的判断 | 核对结果 |
| --- | --- |
| 「最后一公里」是真断点 | 和本项目 `project-map.md` 的「已知缺口：换环境时的零代码边界」是同一个问题，两边各自独立得出同一结论 |
| 别造 CI/CD 轮子，造连接器 | 认同。真正执行部署的是 Runner 或服务器上的脚本，MCP 只是让 AI 能读状态、能发指令 |
| MCP 替代不了执行引擎，也替代不了内网可达性 | 认同。物理隔离环境里再多 MCP 也连不上。这句已经写在 `project-map.md` 里 |
| 数据库是两个不同问题，别混在一起 | 认同。「查数据」走只读 MCP；「改表结构」走迁移脚本进仓库、由部署执行。这和 `AGENTS.md` 的「不静默覆盖」「生产库写入一次一议」是同一件事 |
| 安全门第一天就要有 | 认同。读自动执行、写弹审批、全程留痕。现有 MCP 的 `MCP_READ_ONLY` 就是这个思路的雏形 |
| 自用验证要先于产品化 | 认同。先拿一个真实项目跑通，再决定要不要固化成能力 |

不是「推荐了哪个工具」，而是**把断点定在了「代码写完到服务跑起来」这一段**。

## 二、方向判断

**不做独立的「产品二」，做一条新支线：把已有的资产链路接到真实环境上。**

三条理由：

1. 你缺的不是「再管一种东西」，而是「把手上的资产变成一次能执行、能回滚、能留痕的交付动作」。
2. 现有产品恰好已经有这条链路的骨架：发布记录与发布门禁、验收证据链、工程基线查缺、
   本机 MCP、环境差异表。缺的只有两件——**环境**这个对象，和**执行**这个动作。
3. 另起一个产品（协作工作台）等于把已有沉淀复制一遍，只会多一份要维护的东西。

一句话定位：**从「我知道该怎么交付」到「系统能带着我交付」。**

## 三、断点清单：这条链路上，现在哪些还在靠人肉

链路：本机（AI 写代码）→ 公司仓库 → CI/CD → 镜像仓库 → 客户服务器 → 自建数据库 → 验证与回滚。

| 环节 | 现在怎么做 | 断在哪 | 后果 |
| --- | --- | --- | --- |
| 环境信息 | 记在脑子里、聊天记录里、几个 `.env` 里 | 没有「这是哪台机、什么账号、跑什么版本」的正式登记 | 换个会话就得重新问一遍；也说不清「线上现在到底是哪一版」 |
| 部署动作 | 手工敲命令，或照着上次的命令复制 | 没有「这一次要执行什么」的动作单 | 步骤靠记忆，漏一步就要现场救火 |
| 数据库迁移 | 手写 SQL，手工执行 | 没有守门：脚本全不全、有没有编号冲突、能不能重复执行，事前不知道 | 迁移跑一半失败，应用起不来 |
| 回滚 | 记一个 git 标签 | 只有「版本号」，没有「怎么退回去」 | 真出事时才发现没演练过 |
| 内网摆渡 | 手工压缩一个包，附一张「记得改这几个配置」 | 制品包没有清单和校验和 | 传到客户现场才发现少文件、版本对不上 |
| 部署后验证 | 手工点界面 | 没有和验收标准挂钩的检查 | 验了什么、谁验的，说不清 |
| 出故障 | SSH 上去敲命令看日志 | 排查过程不落库 | 同一个坑下次还得再踩一遍 |

## 四、候选方向与取舍

| 候选 | 是什么 | 判断 | 理由 |
| --- | --- | --- | --- |
| 环境台账 | 把「目标环境」变成一等对象：类型、访问方式、数据库、当前版本、回滚目标 | **做** | 没有它，后面所有动作都无根；有了它，也天然实现「默认不可达」的安全 |
| 环境适配体检 | 按环境类型生成「这个环境还缺哪些能力」清单，产出可当运维手册骨架 | **做，而且第一个做** | 纯逻辑加模板，零新依赖，能独立验收；现在就有真实项目可用 |
| 交付制品包 | 一键打包：制品 + 部署手册 + 回滚手册 + 诊断脚本 + `manifest.json`（带 SHA-256） | **做** | 内网场景的刚需；`scripts/` 已有打包脚本先例可复用 |
| 数据库迁移守门 | 部署前查迁移完整性，部署后比对表结构快照 | **做** | 这是唯一「必须写代码但不该由你手写」的地方；红线是绝不让 AI 直连生产库跑 DDL |
| 交付执行 MCP（只读） | 看服务状态、容器列表、日志尾部、磁盘、环境上版本 vs 仓库版本 | **做** | 复用现有 MCP 服务，只加工具；只读意味着没有破坏性风险 |
| 交付执行 MCP（写） | 触发部署、重启、回滚 | **缓做** | 不是「AI 直接执行」，而是「生成待审批动作 + 你点确认」。等只读用顺了再开 |
| 自建 CI/CD 引擎、包装 Coolify | 自己造部署平台 | **不做** | 造轮子。Coolify／Dokploy 当可选后端，我们只做适配层 |
| 跨会话协作过程工作台 | 记录每次对话、每轮修改、每个决策 | **不做** | 录入摩擦是硬伤；且现在靠资产库加决策记录已经能覆盖 |
| Secret 管理 | 库管密钥 | **不做** | 红线。库里只存「引用名」，本体留在系统凭据管理器或本地文件，不进库、不进 Git、不进 AI 上下文 |

## 五、推荐范围：四段，每段都能单独验收

### M0：零代码先跑一遍（不动代码，本周就能用）

用现有产品的规则包与模板机制，装一份「环境交付清单」和一本「部署／回滚手册模板」，
在下一个真实交付项目里手工跑一遍，把卡点记下来。

**为什么先做这个**：能立刻用上；跑完才知道哪些值得做成代码，避免凭空设计。
按项目规矩里的「爬梯子」顺序，这停在第一个成立的台阶上。

验收：下一次真实交付的每一个环节，清单上都能勾；勾不了的地方记成待办。

### M1：环境台账 + 环境适配体检

- 环境是一等对象，挂在项目下：名称、类型（全托管／自建云主机／公司托管／内网隔离）、
  访问方式、数据库类型与连接方式、当前部署版本、回滚目标、上次部署时间。
- 凭据只记「用哪个引用名」，本体不入库。
- 按环境类型生成交付检查清单，每项判定为「配置能解决／要补能力／不适用」。
- 产出可以直接当运维手册的骨架。

验收：新建一个内网环境，能列出它相对全托管环境缺的能力，并且逐项能勾。

### M2：交付制品包 + 迁移守门

- 一键打包：源码或镜像、`docker-compose.yml`、迁移脚本、配置样例、
  部署手册、回滚手册、诊断脚本，外加一份 `manifest.json`（清单 + SHA-256 + 目标环境 + 版本）。
- 迁移守门：部署前查迁移是否齐全、编号是否冲突、能否重复执行；部署后比对表结构快照。
- 红线：只生成脚本和校验，绝不提供「AI 直连生产库改表」的能力。

验收：打一个包，故意改坏其中一个文件，校验脚本能报出来是哪一条对不上。

### M3：交付执行 MCP（只读先行）+ 部署记录

- 只读工具：服务状态、容器列表、日志尾部、磁盘、环境上的版本。
- 关键一条：**比对「环境上跑的版本」和「仓库里的版本」**，不一致就报出来。
- 每次动作写一条部署记录（时间、环境、版本、结果、证据），挂到已有发布记录上。

验收：`npm run mcp:check` 能列出新工具；只读模式下写工具不可见。

## 六、不做清单

- 不做独立的第二个产品（协作工作台）。
- 不做自建 CI/CD 引擎，不自研部署平台。
- 不让 AI 直接连生产数据库执行 DDL。
- 不在库里存任何密钥本体。
- 不做多租户和团队协作。
- 不在 M0 阶段引入任何新依赖。

## 七、验收标准草案

每条都能用一次测试或一次手工验证判定。

1. 环境台账能记录至少两类环境（全托管、内网隔离），并显示各自当前部署版本。
2. 环境记录里查不到任何密钥本体，只有引用名。
3. 选一个内网环境，能生成一份检查清单，逐项标注「配置能解决／要补能力／不适用」。
4. 检查清单能导出成一份可直接当运维手册用的文档。
5. 打出的制品包带 `manifest.json`，改动其中任一文件后校验脚本能报出具体哪一条不匹配。
6. 部署前检查能报出「迁移编号冲突」和「迁移不完整」两种情况。
7. 部署后表结构比对能报出「实际与预期不一致」的字段。
8. MCP 只读模式下看不到任何写工具。
9. 一次部署动作产生一条部署记录，含时间、环境、版本、结果和证据。
10. 环境上跑的版本与仓库版本不一致时，能明确报出差异。

## 九、和现有产品的关系

这条支线不推倒重来，主要是复用：

| 已有能力 | 在这条支线里怎么用 |
| --- | --- |
| 发布记录与发布门禁 | 部署记录挂上去，「这次上了什么、怎么退」合成一条 |
| 验收证据链 | 部署后验证的检查项直接引用验收标准 |
| 工程基线（按质量等级查缺） | 环境体检的入口 |
| 本机 MCP | 新增只读工具，沿用 `MCP_READ_ONLY` 语义 |
| 项目地图第五步的环境差异表 | 从分析文字变成可勾的清单（M1 的主要素材） |
| 规则包与模板机制 | M0 的载体，不用改代码 |
| 备份格式的版本号先例 | 制品包 `manifest.json` 参照它设计 |
