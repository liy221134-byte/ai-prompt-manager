# 开发规则说明（给人看的版本）

## 这份文档是什么

规则正文只写在项目根目录的 `AGENTS.md`。**本文件不复制任何条款**，只解释三件事：

- 每条规则为什么存在。
- 你（产品经理）在每个环节需要看什么。
- 出问题时怎么判断问题出在哪。

两份文档表述不一致时，以 `AGENTS.md` 为准。

## 为什么先设计再动手

你不读代码，能审的只有方案。所以动手前必须先看到四样东西：做什么、不做什么、
改哪些文件、我怎么验收。缺了「不做什么」，功能会越做越大；缺了「改哪些文件」，
出了问题无法判断影响范围。

这也是「设计门」只保留四块内容的原因：内容越少，你越能看完。

## 为什么要求「先复用、再少写」

AI 天然会多写：加抽象、装依赖、顺手重构，而你不读代码，没法从代码量上看出哪里做多了。
所以这条规矩把「少写」变成一条有先后顺序的判断：先问要不要做，再看项目里有没有现成的，
最后才允许写新代码，顺序错了就是多写。你要看的不是代码，而是交付说明里那句「这次省掉
了什么」。

同时划两条边界，防止「简化」被执行成偷工减料或擅自删除：校验、错误处理、安全、防数据
丢失这些不许砍；涉及数据表、对外接口和新依赖时，仍然先设计后开发，删文件删数据仍要
你确认。

## 为什么一个版本只做一个子系统

`v0.8.0` 名义上是「一个功能」，实际装了 AI 合并、垃圾箱与恢复、30 天清理三套东西，
结果 25 个提交里只有 9 个是功能提交，其余是文档和评审修复。版本范围越大，验收越难
签收，也越难判断到底做完了没有。

判断标准：如果一次改动同时动了数据结构和使用界面，或者要改两条以上的链路，就应该
拆成两次发布。

## 为什么 AI 结果必须先预览

AI 会稳定地做错一些事：多写一条你没提过的要求、把变量名改掉、把长内容砍短。预览
不是不信任 AI，而是把「AI 的改动」变成「你看得见的改动」。所以规则是：AI 生成、
优化、合并的结果一律先给草稿，你确认后才写进数据库，并且保留可回退的版本。

## 为什么限制新依赖

每引入一个库或外部服务，你就多一个需要长期维护、可能需要付费、可能停止维护的东西。
你不读代码，无法评估这些风险，所以默认不引入；确有必要时，先告诉你它是什么、
做什么用、有没有免费额度、以后能不能替换。

## 为什么交付前必须跑检查

「代码写完了」和「能跑」是两件事。检查分两档：

- 日常任务跑 `npm run check:fast`：类型检查加自动化测试，约 40 秒。
- 合并和推送前跑 `npm run check`：再加代码检查和生产构建，约 3 分钟。
- 纯文档、纯内容改动可以只跑自动化测试。

跑过什么就说什么，不允许用「应该没问题」代替真实结果。

## 为什么要保留提交和版本标签

提交是你能回退的地方，版本标签是你能指认「当时上线的是哪一版」的地方。没有它们，
出问题时只能整段重做。所以一次提交只做一件事，每个阶段记录提交和标签。

## 你每次只需要做三件事

1. 说清需求边界：这次做什么、明确不做什么。
2. 审设计文档：重点看「不做什么」和验收标准是不是你想要的。
3. 交付时对着验收标准逐条确认，不通过就退回。
