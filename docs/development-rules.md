# 开发规则与协作提示词

## 文档用途

这份文档把项目规则整理成产品经理可以直接理解和使用的版本。技术层面的规则文件是项目根目录的 `AGENTS.md`，两份文档应保持一致。

## 一、与 AI 协作的规则

1. 开始修改前，先用自然语言说明准备改什么、为什么改、修改后的用户可见效果，以及可能影响的文件或功能。
2. 重要代码块、复杂逻辑和容易误解的地方写中文注释，不给每一行代码加注释。
3. 未经明确确认，不删除文件，不删除或覆盖用户数据，不执行破坏性 Git 操作。
4. 未经确认，不引入新的第三方依赖、外部服务或部署环境。
5. 优先修改指定范围，不进行无关重构。
6. 只有用户明确要求重构时，才可以重写整个文件。
7. 遇到会影响数据结构、产品行为、外部依赖或成本的决定，必须先询问用户。
8. 普通实现细节可以自行决定，但要在交付说明中解释。

## 二、产品规则

1. 当前产品是个人使用的 AI 提示词资产管理工具。
2. 当前使用个人邮箱密码登录保护云端数据，不做团队协作和多租户权限。
3. 提示词卡片包含标题、分类、标签、正文和适用场景。
4. 核心使用流程必须保持顺滑：

   ```text
   找到提示词 -> 填写变量 -> 一键复制 -> 使用
   ```

5. 采集流程必须保持简单：

   ```text
   粘贴原文 -> AI 识别结构和标签 -> 用户确认 -> 保存
   ```

6. AI 不得静默覆盖用户内容。AI 生成或合并的结果必须先预览，再由用户确认。

## 三、变量与复制规则

1. 正文中的 `{{变量名}}` 打开详情时自动识别为输入框。
2. 变量按照第一次出现的顺序排列。
3. 同一个变量重复出现时，只显示一个输入框。
4. 变量名两侧的空格不参与变量识别。
5. 填写变量后，预览区立即显示替换后的完整内容。
6. 原始模板保持不变，替换只作用于当前预览和最终复制结果。
7. 只要存在变量，所有变量未填写完成前不得复制。
8. 未填写完整时，复制按钮必须明确显示还缺多少个变量。
9. 没有变量时，不显示变量输入区，复制按钮直接可用。
10. 复制结果必须与最终预览完全一致。

## 四、交付规则

1. 每次完成后列出修改了哪些文件、每个文件改了什么、如何验证，以及未完成事项。
2. 不提交带 `TODO` 的产品占位功能。
3. 用户可见文案使用中文。
4. 不提交无法运行的代码。
5. 每次功能变更都要有可执行的验收标准。
6. 每次修改后至少完成一次代码检查、类型检查和构建验证。
7. 没有明确确认，不创建远程仓库，不推送代码，不部署生产环境。

## 五、Git 规则

1. 功能开发前确认当前 Git 状态。
2. `main` 分支始终保持在可运行状态。
3. 功能开发从 `main` 创建功能分支。
4. 一次提交只处理一个清晰目标。
5. 提交信息使用 `feat:`、`fix:`、`docs:`、`test:`、`chore:` 前缀。
6. 每个阶段完成后记录提交和版本标签。
7. 未经确认，不执行 `git reset --hard`、强制推送或删除 Git 历史。

## 六、完成定义

一个功能只有同时满足以下条件才算完成：

- 产品行为和验收标准一致。
- 正常流程和边界情况都经过验证。
- 页面没有明显溢出、遮挡或不可操作区域。
- 代码检查、类型检查、自动化测试和生产构建通过。
- 文档记录了修改内容和验证结果。
- Git 中形成了可回退的提交版本。

## 七、每次开发可复用的提示词

```text
先阅读项目根目录的 AGENTS.md、README.md、产品范围和现有验收文档。

本次目标是：……
本次只做：……
本次不做：……
验收标准是：……

请先告诉我：
1. 你准备改哪些文件
2. 每项修改的作用
3. 可能影响的产品行为
4. 可能的风险
5. 我如何验收

暂时不要修改代码，等我确认方案后再实施。
```
