## 验收标准

### 两条链路

- [x] 项目里有「文档」和「代码」两个视图，切换后类型筛选和列表内容跟着变，互不混入。
      依据：`tests/workspace-view.test.mjs`「图谱节点按节点类型分两条链路」与「提示词只出现在公共资产」。
- [x] 导入入口拆成「导入文档」和「导入代码」，各自只露出对应的来源，不再挤在一个抽屉里。
      依据：`engineering-import-drawer.tsx` 的来源过滤 + 本清单第 3 条手工验证。
- [x] 图谱节点按类型分链路：需求节点进文档视图，模块／数据／接口／测试节点进代码视图。
      依据：`readGraphNodeLane` 与同一条测试。

### 文档链路

- [x] 项目文档分成六段：需求 → 规格与计划 → 交付 → 验收 → 发布 → 其他。
      依据：`tests/document-flow.test.mjs`「文档类型能对上链路阶段（六段）」与「分组顺序固定，空组也保留」。
- [x] 链路完整性改成从文档里认：验收看文档类型「验收记录」，发布看「发布记录」。
      依据：`tests/document-flow.test.mjs`「链路完整性：四环齐了就是齐了」。

### 验收与发布归位

- [x] 新建资产的入口里不再出现「验收记录」「发布记录」两个独立类型；老数据仍能打开、备份、还原。
      依据：`tests/workspace-view.test.mjs`「验收记录与发布记录不再单独占位」。
- [x] 验收覆盖改成算文档：一份结论为「通过」的验收记录文档，指向的需求节点算通过；
      一版一份清单指向多条需求时，每条需求都算验收过一次。
      两个方向都认：文档指向需求，或需求节点指向文档（图谱「批量挂文档」挂的就是后者）。
      依据：`tests/acceptance-evidence.test.mjs`「按需求节点汇总」「按节点列验收记录」
      「需求节点反过来指向验收记录，也算覆盖」。
- [x] 最近一次发布从发布记录文档的元数据里读，门禁完成情况照旧能算。
      依据：`tests/release-record.test.mjs`「最近一次发布按发布日期算」。
- [x] MCP 只能把验收记录写成文档，不能自己给自己发发布记录。
      依据：`tests/mcp-write.test.mjs`「MCP 写验收记录：写成文档…」「发布记录不给 AI 写」。

## 需要你在界面上确认的

- [ ] 顶部三个视图切换（公共资产／文档／代码），两边列表内容确实分开。
- [ ] 「导入文档」只列文档来源、「导入代码」只列 Schema 和代码目录。
- [ ] 项目文档页签里能看到六段分组，空的那几段有说明。
- [ ] 打开一条验收记录文档（比如 v2.16.0 验收清单），能看到「结论」「提交版本」两个字段。
- [ ] 工程基线里：链路完整性的验收那一环是绿的；发布那一环还空着（见下一条）。
- [ ] 开一条发布记录（文档类型选「发布记录」），填版本号、结果、回滚目标，看「最近一次发布」是否出现它。

## 设计偏差

1. **发布记录的门禁清单跟着文档走**：设计里写的是「门禁写进正文」，实现改成
   门禁仍然结构化存在文档元数据里（`metadata.release.gates`）——否则 v2.10.0 的
   「门禁 x／y 完成」就没数据可算，等于删掉一个已经能用的能力。
2. **验收记录用关系表达「覆盖了哪些需求」**：设计里没写清挂需求的字段放哪，
   实现选择复用资产关系（一份文档可以指向多条需求），不再单独存 `nodeId`。
3. **MCP 仍然能改老类型的验收记录**：新建已经关闭，改内容和状态保持可用，免得老数据在 AI 侧完全动不了。

## 未完成事项与风险

- 验收结论与发布结果仍然是**文档级**：一版一份清单时，单条需求「过没过」看清单正文，
  产品不逐条解析正文。要逐条结构化，得再立一版（暂不排期）。
- 代码视图只是「看得见」：模块／接口节点不做依赖分析，影响分析仍然只按人工关系算两层。
- 规则引用模型（项目引用公共规则、不再各存一份）不在本版，已记进 `docs/pending-items.md`。
