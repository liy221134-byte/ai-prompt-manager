## 怎么用

- 版本：`v2.5.0`，主题是「给项目建一棵可维护的上下文树，并看清改动会波及谁」。
- 状态：**功能与界面补验已完成，等你签字**。
- 设计见 [项目图谱设计](../superpowers/specs/2026-09-23-v2.5.0-project-graph-design.md)。
- 能对上就在方框里打勾；每条都写依据，证据只记一处。

## 验收记录

- 2026-09-23 由 Codex 开发并代跑，全程在**本地库副本**上执行，原始本地库没有被改动。
- 实测数据：3 个需求节点（REQ-001 根、REQ-002 子、REQ-003 子）+ 2 条规则
  （一条引用 REQ-001，另一条依赖第一条规则，用来验证两层影响分析）。

  试重复编号被拦下 → 改成新编号并选父节点保存 → 点影响清单里的条目跳转。

## 一、图谱节点

- [x] 能新建图谱节点：选类型、填编号、选父节点（父节点只列同类型节点）。
      依据：从图谱视图「新建需求节点」进入编辑器，字段有「节点类型（默认需求）」
      「稳定编号」「父节点（列出 REQ-001／REQ-002）」「备注」；保存后节点带父节点。
- [x] 同一项目同一类型里编号重复时保存被拦下并给中文提示。
      依据：把编号填成 `req-001`（大小写不同也算重复）后保存，
      提示「编号「REQ-001」已经被「需求一：资产入库」用了，换一个。」；
      单元测试覆盖只看同项目同类型、忽略大小写、排除自己。
- [x] 类型筛选能筛出图谱节点；详情显示编号、类型和完整路径。
      依据：类型筛选有「图谱节点」；节点详情显示「节点类型：需求 · 编号：REQ-002 ·
      路径：需求一：资产入库 → 需求二：规则编译」。

## 三、影响分析

- [x] 选中节点能看到三块清单：指向谁、谁指向它、间接影响。
      依据：选 REQ-001 显示「这个节点指向谁（0）」「谁指向它（1）」
      「间接影响（1）」。
- [x] 间接影响写清是通过谁串起来的。
      依据：间接项显示「检查规则本身也要复核（通过 需求一必须保留原文）」——
      那条规则依赖指向 REQ-001 的规则，所以算二层影响。
- [x] 每条都能点开对应资产或节点。
      依据：点「需求一必须保留原文」打开它的资产详情（显示规则类型），
      点「去编辑这个节点」跳到节点编辑器。
- [x] 关系来自现有的资产关系字段，编辑器里建的关系同样能算进影响分析。
      依据：影响分析只读 `metadata.relations`；本次实测的关系就是按编辑器写入的
      同一字段结构建的（编辑器关系区在 v2.1.2 已验证）。

## 五、设计偏差

1. 图谱视图做成「左树右详情」两栏，而不是单独一页：和其他抽屉的交互保持一致。
2. 节点路径除了在资产详情显示，也在图谱视图里显示；两处都读同一份节点列表。
3. 影响分析只做二层反向（谁依赖「依赖我的东西」），不做正向二层和全图遍历，
   避免给出不可信的结论。

## 六、已知边界（不在本版）

1. 不自动导入 Schema、不分析代码模块、不自动猜映射（留给 Agent 连接那一版）。
2. 没有图形化的数据流视图和追踪矩阵，这一版是树 + 影响清单。
3. 节点类型固定五类，不支持自定义类型。
4. 加固与验收等整个 2.0 产品做完后统一做。

## 七、这一版省掉了什么

- 没有为节点做批量导入（需求清单一条条建，或用文档包导入再改类型）。
- 没有做节点顺序的手工拖拽：树按编号排序，编号就是顺序。
- 没有做影响等级评分：只列出受影响的条目。
