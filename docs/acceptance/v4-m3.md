## 一、这一版要解决的问题

到 M2.5 为止，系统能准确说「今天做哪几道题」，但答不了「这个知识点到底在讲什么」。

算一下就知道这不是小缺口：中项 380 小时配 118 道题，一天 3 道，40 天刷完，
剩下 160 天没有东西可学。**缺的是内容，不是功能。**

所以这一版补的是内容：每个知识点一份讲义，固定四段——一句话定义 + 要素 / 例题 / 怎么考。

## 三、讲义放在哪：改过一次决定

原方案是在 `knowledge_points` 上加 `summary` / `note_md` 两列，写一份迁移，导入器把讲义写库。
**这个方案当晚被推翻**，迁移文件 `20261028170000_add_knowledge_notes.sql` 已删除（从未执行过，删掉无副作用）。

| | 存数据库（原方案） | 编译成常量（现方案） |
| --- | --- | --- |
| 真源 | 库里一份 + 主题包一份，**两份要对齐** | 主题包一份 |
| 改讲义后 | 要重导一次库；漏了就是页面显示旧内容，且看不出异常 | 改 yaml → `npm run gen:topic-notes` → 提交 |
| 运行时开销 | 本来就要查知识点，讲义顺带取，无额外请求 | 零请求，随 bundle 走（29 篇：源码 131 KB，gzip 52 KB） |
| 迁移依赖 | 要一次 DDL | 无 |
| 谁来写 | 导入器 | 生成器（`scripts/build-topic-notes.mjs`） |

判据是「它是什么」：讲义是随主题包分发的**静态内容**，有读无写，不参与判分也不参与统计。
给只读内容建副本，等于给自己多养一份必须同步的真源。

**代价说清楚**：多了一个生成步骤。所以加了两道守卫——
`npm run check:topic-notes`（挂进 `check:fast`）与 `tests/topic-notes.test.mjs` 的同步用例，
改了 yaml 忘了重新生成会直接失败，不是靠人记得。

## 四、验出来的真错

### 4.1 练习页的讲义入口点了没反应（已修）

`learning-topic.tsx` 在练习模式下**提前 return**，只渲染 `PracticeQuiz`；
讲义抽屉挂在下面那段主 `return` 里。结果是：点「看「…」的讲义」→ 状态设上了 → 但抽屉节点不在渲染树上 → 界面毫无变化。

浏览器实测才发现的（读 DOM 确认没有 `z-50` 层）。修法是把抽屉提到两个 `return` 之前定义，两边共用同一个 `noteDrawer`。
单测覆盖不到这种错——它是「组件树分支少挂一个节点」，只有真点一下才知道。

### 4.2 第一版讲义文档没写清「存哪」（已补）

`topic-pack-schema.md` 原来只说 `note` 怎么写，没说写完去哪。补了第三节末尾那张对照表与实现路径。

### 4.3 按块式写的插入逻辑，对 24 条流式条目一条没命中（已修）

补齐那 24 篇时，注入脚本假定知识点是块式（多行）。实际上除 S1 外的 24 条都是**流式单行写法**（`- {id: KP-0201, ...}`），
而流式里塞不进 `body: |` 这种多行块标量。结果脚本报「插入 0 篇」并退 1，文件一个字没改。

**这次没造成损失，靠的是脚本自带的后置校验**：它比对「预期插入数」与「实际插入数」，不一致就报错退出，
而不是写完就宣布成功。如果只打一行「处理完成」，这会变成一次静默的空跑。

### 4.4 一条测试把「内容有缺口」当成了前提（已改）

`tests/topic-notes.test.mjs` 里「没写讲义的知识点不进常量」这条，原来断言「主题包里应有还没写讲义的知识点」。
29 篇补齐后这个前提消失，测试变红。当时写的时候留了一句「若哪天补齐了全部知识点，这条测试要跟着改，而不是被删」——
改法就是照那句做的：用临时主题包构造一个「一有一无」的包，验证的是**跳过行为**，不再与内容完整度绑死。

教训是通用的：**测试可以依赖接口契约，不要依赖当前内容的完整度**，否则每次补内容都要回头改测试。

## 五、已知缺口

- **讲义已补齐 29 / 29**（2026-10-28 晚完成，S1 至 S6 全覆盖）。新增知识点仍可先不带 `note`，
  页面会显示「讲义待补」的灰字，不会被生成器拦住。
  讲义校验卡的是「三段齐全 + 一句话不超 60 字」，不设字数上限——长度交给写的人判断。
- **体积的实测值与我先前的估算不符，以实测为准**：
  29 篇生成物 `topic-notes.generated.ts` 为 **131 KB 源码、gzip 后 52 KB**。
  我此前写的「29 篇约 60 KB」是错的——中文按 UTF-8 一字三字节，而我又低估了单篇篇幅
  （实际区间 1179 到 2596 字，含 S1 五篇）。
- **切换阈值按实测重定**：现在只挂 `/learning/[topicId]` 这一条路由，52 KB（gzip）可接受。
  当主题增加到 **3 个左右**（gzip 会过 150 KB）时就该改成按主题动态 import，
  而不是等到「影响首屏」才动——那时已经影响完了。
- 讲义里 24 张表格靠 `MarkdownContent` 渲染，已实测表格边框、列表、行内加粗、多级标题都正常；
  **仍未验超长表格在窄屏（<375px）的横向溢出**。

## 六、2026-10-29 追改：讲义改全屏 + 大字号

原形态是右侧抽屉（`max-w-2xl`），讲义是 1200—2600 字的长文，挤在窄栏里读着费劲。
改成 `DrawerShell variant="fullscreen"`：铺满窗口、header 吸顶、正文居中 `max-w-4xl`。
**全屏时不挂遮罩点击关闭**（误触一下半篇就没了），只能 Esc 或右上「关闭（Esc）」；
正文滚到底还有「读完，返回学习计划」作为出口。

字号单独开一档 `MarkdownContent variant="reading"` → `.markdown-reading`：
正文 17px / 行高 1.9、h2 1.3rem、表格 15px。**没有直接调大 `.markdown-body`**，
因为解析（题干、选项、结论同屏）要的是密，讲义要的是松，同一个组件两种密度。

实测（Chrome + `localhost:3000`，登录态）：
① 全屏打开，标题 `五大过程组`、副标题 `知识点讲义 · 第9章`，表格与列表可读；
② header 的标题与正文对齐同一条竖线（改之前标题贴着左边缘、正文居中，一眼看出错位）；
③ 滚到底「读完，返回学习计划」在视口内（`btnTop 700 / btnBottom 737 / vh 769`）；
④ 窄屏 501px：今日计划两栏折成一栏，无横向溢出（`scrollWidth == innerWidth`）。

配套改的是今日计划卡（见提交 `feat(learning): 讲义改全屏大字号，今日计划分出主次`）：
左右两栏、「今天做」与「时间账」分开，差额按 `plan.status` 上色。
