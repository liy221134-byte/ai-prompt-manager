## 一、当前交互路径

入口只有一个：资产库顶部「采集台账」（`/external-sources`），与「公共资产／文档／代码」同级。

### 路径 1｜看整体进度，并追溯到落点

打开就是总览，不用先点任何东西：

- **一排统计卡**：「全部来源」+ 六个档位各一条（`—（未提炼资产）`／`未导入库（仅台账记录）`／
  `已进模板·规则层（非库内资产）`／`知识库资产（不编译进 AGENTS.md）`／`未编译·候选`／
  `已进编译候选（待确认发布）`）。当前为 0 的档位也显示，用意是让「还有哪几档空着」可见。
- **生态筛选条**：全部 + 十档（开源社区／腾讯／阿里／字节／OpenAI／Anthropic／Google／微软／
  本机／其他），每档后面带条数，0 条的置灰。点一下即筛。
- **台账表格**：六列——`#` / 生态 / 来源 / 类型 / 处置结论 / 是否编译。

点任意一行 → 右侧抽屉，把这条来源的全部信息摊开：类型、状态、来源链接（可点开原站）、
处置结论、**落到哪条资产**（库内资产会变成「打开资产：<标题>」按钮，点开跳到资产详情）、
核实日期、备注、是否编译（附一句推导说明：规则升到 active 才算进编译候选，文档类本就进知识库）、
人工确认（有就显示「已确认·谁」+ 日期 + 依据，没有就说明在资产里做确认才会写）。

抽屉底部两个按钮：「在资产库里打开」打开这条采集记录本身，「编辑」改它。
两个方向都留了口子——往落点去、往记录本身去。

空态两种情况分得清：一条都没有时提示「还没有采集记录。点右上角『新建采集』登记一条来源。」；
筛出来为空时提示「这个生态下还没有来源，换个生态看看。」。

### 路径 2｜登记 / 修改一条来源（这是台账「活」起来的那一步）

点「新建采集」→ 表单八个字段：

| 字段 | 填什么 |
| --- | --- |
| 来源名 | 必填，空着点保存会被拦（提示「请填写来源名。」） |
| 生态／厂商 | 下拉十档，与筛选条同一套值 |
| 类型 | Skills／MCP／Skill·MCP／资讯流／评审／其他，**可以自己写** |
| 处置结论 | 已采／已采（部分）／已入库／已安装／进行中／暂缓／不采，**可以自己写** |
| 来源链接 | 外部仓库或官方页；本机来源写「本机」 |
| 核实日期 | 如 `2026-09-29` |
| 落到哪条资产 | 写资产标题或 ID，保存时自动认出库内资产并挂上跳转 |
| 备注 | 为什么采、提炼角度、注意什么 |

保存 → 库里多一条 `documentType: 采集记录` 的文档资产（`role: source`、`authority: false`、
状态 `active`），列表立刻多一行，刷新后仍在。

改：抽屉里点「编辑」→ 同一张表单 → 保存后写一条版本记录（什么时候改的、改成什么都能回溯）。

> 类型和处置结论故意**不做枚举校验**，只给预设。台账历史值里有 `Skill/MCP`、
> `已采（部分）`、`评审 + Skills` 这类混合写法，强行归一会丢掉人写原话里的信息。

### 路径 3｜发起采集（A）：说需求 → 拿到可复制的话术

这是 M2.1 的第一条入口，解决的是「每次采集都要翻 README 第五节抄话术」。

点「生成采集任务单」→ 填三样：目标来源（仓库地址／官方页／名称，**必填**，不填时生成按钮是灰的）、
生态（可不选）、关注点（可不填，例「重点提炼设计规范类规则，不要安装相关的」）
→ 点「生成话术」→ 下面出现一段话术，按钮变「重新生成」→ 点「复制话术」变「已复制」→ 甩给智能体执行。

话术固定四段，缺什么不硬塞空行：

- **提炼要求**——逐条输出候选规则、区分「约束 AI 的规则」与「教操作者的方法」、
  每条给规则类型／适用项目规模／优先级／不适用场景；填了关注点才多一条「重点关注」。
- **去重口径**——对照现有工程资产清单去重，只输出真新增，并指出补强或冲突了哪个资产 ID。
- **合规硬约束**——默认 `status: candidate`、`confidence: hypothesis`、填好 `source_references`；
  先只输出候选清单，**不要写进 `AGENTS.md`、不要新建资产文件，等人工确认**；一次只处理这一个来源。
- **回填格式**——确认的条目写成资产文件；在采集台账登记这条来源，处置结论填「已采」。
  选了生态才会带上「（生态：开源社区）」这半句。

弹层里明写着「**产品本身不联网搜索**」——这条是刻意摆出来的，避免被读成「点一下就能自动抓」。
产品只负责把该说的话说清楚，执行交给有联网能力的智能体。

### 路径 4｜发起采集（B）：给压缩包 → 候选与采集记录一起落库

这是 M2.1 的第二条入口，复用的是 v2.1.1 就有的文档包导入链路，只多了一个「外部采集」模式。

点「给压缩包」→ 弹层标题是「给压缩包（外部采集）」→ 传 ZIP → AI 提取候选 → 预览页列出
识别出的候选，并要你填「**这条来源是谁**」（来源名 + 生态）。

和标准「导入文档包」的区别有两处，都在这一步体现：

- **不问「创建到哪个项目」**——外部采集一律落公共资产库（`default-project`），
  因为外部来源属于公共资产，不属于某个项目。
- **不填来源名点确认会被拦**（弹层不关），提示「外部采集要填来源名。」。

确认后落库三样东西，都在公共资产库：

1. 候选规则：`draft` + `confidence: hypothesis` + `sourceExcerpt`（正文前 200 字摘录）；
2. 候选文档：同样带来源信息；
3. **一条采集记录**：`collectedAssetIds` 指向这一批新资产，所以台账里点它就能跳到候选。
   另外原始 ZIP 仍留一条 `source_package` 资产，可追溯。

页面顶部提示「已从压缩包采集，采集记录与候选资产都已落在公共库。」，列表自动刷新。

### 路径 5｜把候选推到编译候选（这条流水线真正的终点）

这一步不新增页面，走的是既有界面，但它是 M2 立项验收标准第 4 条要的那条：

1. 采来的候选资产落在库里的形态是 `candidate`（规则）／`draft`（导入的规则）+ `hypothesis` + 带来源；
2. 你看过内容，在资产上做**确认动作**（记确认人、时间、依据）→ 资产升 `active`；
3. 规则编译抽屉里立刻能选到它，编出来的 `AGENTS.md` 草稿里含这条规则；
4. 回到采集台账，这一行的「是否编译」从「未编译／候选」变成「**已进编译候选（待确认发布）**」。

每一步都有人工确认点，没有任何一步是自动的——这是设计稿判断 2 定下的边界，也是产品里
「不做未经人工确认的自动入库」那条立项约束的落点。

### 路径 6｜把关：跑一次合规检查

点「运行采集合规检查」→ 展开一条提示条 → 复制 `npm run check:leads3-compliance` 到终端跑。

它扫全部外部来源资产，逐条核对 SOP 四条硬约束：默认候选／初始假设／必须带来源／
**未经确认不许升 active**。只读不改。

为什么要去终端跑：检查要读本机库，而云端模式下浏览器读不到库文件，所以这一步不放在界面上。
提示条里把这句话写清楚了，免得让人以为是按钮坏了。

## 二、用户故事（现状与验收状态）

台账现在覆盖 8 条用户故事，M1 与 M2 各 4 条。逐条对照当前实现：

| 出自 | 用户故事 | 现在满足吗 | 一次操作能验的判定 |
| --- | --- | --- | --- |
| M1 US-1 | 我想一眼看到「采到哪了」，不用翻 Markdown | 满足 | 打开台账，来源数 = 库内采集记录条数 |
| M1 US-2 | 我想从一条来源追到它落成的资产 | 满足 | 点一行 → 抽屉「落到哪条资产」出现可点按钮 → 跳资产详情 |
| M1 US-3 | 我想确认采集的四条硬约束没被破坏 | 满足 | 跑 `check:leads3-compliance`，0 违规；人为造一条「active 且无确认记录」能被抓出 |
| M1 US-4 | 我想知道哪条采集还没编译进去 | 满足 | 每行「是否编译」按五档标注，措辞与事实一致 |
| M2 US-1 | 我想在产品里直接新建／修改来源，不用手改 Markdown | 满足 | 点「新建采集」填完保存，行立刻出现；再点「编辑」改处置结论，有版本记录 |
| M2 US-2 | 我想按生态看采集分布，知道哪些生态还没碰 | 满足 | 点生态筛选，筛出行数与登记录数一致；「全部」不丢行 |
| M2 US-3 | 我想把一条真实外部技能从采集一路推到编译候选 | 满足 | 候选资产确认升 active 后出现在规则编译候选集；台账对应行变「已进编译候选」 |
| M2 US-4 | 我想给个压缩包或说句需求就能拿到该做的事，不用抄话术 | 满足 | 两个入口都试一遍：ZIP 能提候选 + 填来源名后落库；说需求能生成含四段的可复制话术 |

M2.1 相对 M2.0 只加了 US-4 这条的两个入口，其余七条是 M2.0／M1 已交付并已验的。
所以 M2.1 的验收标准（[`acceptance/leads-3-m2-1.md`](acceptance/leads-3-m2-1.md)）
只压在两件事上：**两条入口是否在场、是否正确**，加一条「不碰坏标准导入入口」。

## 三、M2.2 评估：双向同步

### 现状：现在是三条单向脚本，不是一套同步机制

| 脚本 | 方向 | 正本在哪 |
| --- | --- | --- |
| `scripts/sync-market-skills.ts` | `E:\AI资产市场\skills\*\SKILL.md` → 本机库 | 市场仓库 |
| `scripts/sync-new-project-templates.ts` | `templates/new-project/*` → 本机库 | 本仓库 |
| `scripts/sync-method-assets.ts` | `templates/methods/*` + `prompt-packs/*` → 本机库 | 本仓库 |

三个都是同一个形态：**正本是仓库文件，库是副本，改了正本跑一次脚本推下去**。
方向的缺口只有一个：在产品界面里改过的内容，回不到正本。

### 先问一句：这个缺口现在真的疼吗

我的判断是**还不疼**，理由是三条事实：

1. **产品里现在没有「编辑技能定义」这个动作**。技能类资产进库是同步脚本推下去的，
   界面上能改的是采集记录、规则正文这类资产，而它们的正本本来就在产品侧（不在市场仓库）。
   所以「库里的改动回不到正本」这个场景，目前**没有真实发生过的入口**。
2. **M2.1 之后，库承担的是「采集落点」，市场仓库承担的是「分发端」**——方向恰好相反。
   采集是「外 → 库」，同步是「库 ↔ 正本」。把这两件事塞进同一个里程碑，正是立项时
   「把手段写成目的」那个毛病的复发。
3. 立项验收里那条「同步脚本可重复执行，第二遍 0 差异」**已经被 T4 迁移脚本的幂等验收顶掉了**
   （幂等：真跑 23 → 二跑 0 新增、跳过 23，是实测过的）。所以 M2.2 没有承接一条悬空的验收。

### 如果要做，三个选项

**选项 A：真·双向同步（库 ↔ 正本，自动对齐）**——**我建议不做。**
它要解决冲突（两边都改过谁赢）、要防循环触发、要跨仓库写权限，而数据量是几十条、
没有合并 UI、也没有冲突规则。投入产出比最差，而且一旦自动覆盖，丢的是「正本」——
正是最不能丢的那份。

**选项 B：显式回写命令 + diff 预览（库 → 正本，人工触发）**——**真要做时做这个。**
一条 `npm run export:<x>` 命令，把库里的某类资产写回仓库文件，先打印 diff，人确认才落盘。
单向、显式、可审，与现有的 `sync` / `sync:from-cloud` 同构——两个方向各一条明确命令，
而不是一个会自动对齐的黑盒。成本：一个脚本 + 一次预览，没有冲突问题（因为单向且人工触发）。

**选项 C：先把「正本在哪」定死，不写新代码**——**我建议先做这个。**
现在三份同步脚本各自指向不同的正本位置，加上 README、设计稿里散落的描述，
「这份内容的正本到底是谁」其实没有一处集中的答案。这正是你之前修过一轮的
「同一件事多份载体」——它会在 M2.2 之前先咬人。一张表（每类资产 → 正本位置 → 现在有没有第二份副本）
比一个同步脚本更值。

### 建议与触发条件

**M2.2 维持「待评估」是对的，但把它的定义收窄**：从「双向同步」收窄成
「**正本归属盘点 + 需要时加一条显式回写命令**」。理由：真正的痛点不是「同步不双向」，
是「正本不清晰」；而后者用文档加一条命令就够，不需要一套同步机制。

**做的触发条件**（满足任一条再开）：

1. 你在产品里**真的改过一次技能定义类资产，并且希望它回到仓库**——也就是缺口第一次真实发生；
2. 或者出现了第二个消费方（别的项目／别的机器）需要在这份资产上改，两边开始打架。

在这两条出现之前，M2.2 的产出就是上面那张「正本归属表」，不做同步脚本。
