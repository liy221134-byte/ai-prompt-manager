# 2.0 需求草案

## 文档状态

- 状态：需求评审草案。
- 当前用途：整理方向、识别冗余、确定边界。
- 不进入当前 `v0.7.0` 开发。
- 正式开发前需要拆分版本、设计数据模型和验收标准。

## 产品定位

2.0 定位为：

> 面向零代码 AI 开发者的规则、模板与项目上下文编译器。

产品负责：

- 管理开发资产。
- 提取和确认规则。
- 管理规则范围、生命周期和冲突。
- 管理文档模板。
- 组合项目规则。
- 编译 Agent 可执行的规则文档。
- 管理需求、模块、数据、代码和测试之间的关联。
- 为后续 Agent 动态查询提供统一上下文源。

产品不负责：

- 替代智能体生成专业 PRD。
- 替代代码编辑器、GitHub 或项目管理工具。
- 自动执行代码。
- 自动批准 AI 规则。
- 自动修改外部仓库。

## 目标用户

### 主要用户

使用 AI 开发个人项目，但不直接阅读代码的产品经理或独立创作者。

### 用户核心问题

- 提示词、规则、模板和项目文档分散。
- `AGENTS.md` 混合了全局、项目和临时规则。
- 规则会过期、冲突，但缺少生命周期管理。
- 新项目每次都靠 AI 临时重组开发规范。
- 大型项目需求和数据模型是多级结构，关系容易断裂。
- Bug 出现时需要重新扫描代码，缺少上下文索引。
- 文档、代码、数据和测试之间没有追踪关系。

## 核心工作流

### 工作流一：开发资产提取规则

```text
上传或粘贴开发资产
-> AI 提取候选规则
-> 用户逐条确认
-> 分类、去重、冲突检测
-> 进入规则库
```

### 工作流二：创建项目开发体系

```text
创建项目
-> 选择文档模板
-> 选择全局规则包
-> 选择项目规则包
-> 添加项目专属规则
-> 添加临时任务规则
-> 检查优先级和冲突
-> 编译 AGENTS.md 和项目文档
```

### 工作流三：Agent 开发与反馈

```text
Agent 读取编译后的规则和上下文
-> 执行需求
-> 更新需求、模块、数据和测试关系
-> 提交规则或决策建议
-> 用户确认
-> 重新编译项目规则
```

### 工作流四：Bug 定位

```text
描述 Bug
-> 搜索需求
-> 找到相关模块
-> 找到数据表和数据流
-> 找到代码入口和测试
-> 找到最近变更和决策
-> 定位问题范围
```

## 四层领域模型

```text
来源资产
-> 规则
-> 项目规则集与模板
-> 编译交付物
```

### 来源资产

- Markdown、文本和后续 ZIP 资产包。
- 开发规范、项目规则、提示词、文档模板。
- 原始内容必须保留，不能被提取结果覆盖。

### 规则

规则是原子约束：

- 必须。
- 禁止。
- 建议。
- 流程。
- 验收。
- 技术约束。

### 项目规则集与模板

- 规则包是可复用规则集合。
- 项目规则集是当前项目选择的规则组合。
- 模板决定最终文档的结构，不决定规则内容。

### 编译交付物

- `AGENTS.md`
- `START_PROMPT.md`
- `README.md`
- 需求、架构、数据、测试和错误索引。
- 任务级临时规则。

## 规则范围

### 全局规则

适用于所有项目：

- 未经确认不得删除用户数据。
- 不得把密钥提交到 Git。
- 不得绕过权限检查。

### 项目规则

只适用于某个项目：

- 本项目使用 Next.js。
- 数据使用 Supabase。
- 页面文案使用中文。

### 任务临时规则

只适用于当前任务或会话：

- 本次不修改 UI。
- 这次只修复数据恢复问题。
- 暂时不引入新依赖。

临时规则必须有：

- 开始时间。
- 失效时间。
- 关联项目。
- 关联任务或会话。
- 是否允许被后续任务继承。

## 规则生命周期

生命周期只表示规则是否有效：

```text
待确认 -> 活跃 -> 已废弃
```

扩展状态：

```text
已拒绝
被替代
```

冲突不是生命周期，而是独立关系状态：

```text
冲突状态：无、待裁决、已解决
```

## 规则覆盖与优先级

推荐优先级：

```text
1. 不可覆盖的全局安全规则
2. 临时任务规则
3. 项目专属规则
4. 适用规则包
5. 全局普通规则
```

每条规则需要记录：

- 是否允许覆盖。
- 覆盖来源。
- 覆盖原因。
- 覆盖生效时间。
- 覆盖失效时间。

## 项目上下文图谱

树用于展示层级，关系图用于管理跨层级映射。

### 树结构

- 需求树。
- 模块树。
- 代码树。
- 数据库树。
- API 树。
- 测试树。
- 文档树。
- 决策树。

### 节点类型

```text

acceptance
module
code_file

database

column

document

bug

```

### 关系类型

```text

```

### 稳定标识

系统内部使用稳定 ID，界面展示用户友好编号：

```text
REQ-001.02
MOD-003.01
DB-public-prompts
DB-public-prompts-content
TEST-REQ-001-02
BUG-2026-001
ADR-0004
RULE-SEC-001
```

节点移动时内部 ID 不变，避免关系断裂。

## 关系可信度

每条关系必须记录：

- 关系来源。
- 创建方式：人工、代码分析或 AI 建议。
- 确认状态：待确认、已确认、已拒绝、已失效。
- 置信度。
- 最后验证时间。
- 证据或来源片段。

AI 推断关系默认不能作为确定事实。

## 编译原则

1. 规则组合和优先级由确定性逻辑处理。
2. AI 可以建议，不能静默裁决。
3. 编译前必须检查冲突。
4. P0 冲突阻止导出。
5. P1/P2 冲突显示警告，用户确认例外。
6. 编译结果带版本，可比较和回滚。
7. 生成文档必须可以追溯到规则和来源资产。

- 资产上传和粘贴。
- AI 提取规则。
- 规则确认。
- 全局、项目、临时范围。
- 生命周期。
- 冲突检测。
- 规则包。
- 文档模板。
- 项目规则组合。
- 编译 `AGENTS.md` 和 `START_PROMPT.md`。

### 2.0B：项目上下文图谱

## 非目标

- 不做完整 PRD 自动生成器。
- 不做 Notion 或 Confluence 替代品。
- 不做在线代码执行平台。
- 不做自动修改外部 GitHub 仓库。
- 不做完整项目管理系统。
- 不做公共提示词交易平台。
- 不让 AI 自动批准规则。
- 不让 AI 无确认覆盖文档。

## 科学性评估

### 科学合理的部分

- 从真实问题出发，不是凭空增加文档类型。
- 四层模型清晰：来源资产、规则、模板、编译交付物。
- 规则与模板职责分离。
- 项目规则可复用，不需要重复复制。
- 生命周期、冲突和覆盖权限分开设计。
- 树展示层级，关系图管理跨层映射。
- Agent 使用编译结果，而不是每次临时重组。
- 需求、代码、数据、测试和 Bug 可以追踪。
- 静态编译先落地，MCP 动态连接后置，技术风险可控。

### 需要控制的风险

- 领域模型过大，容易变成复杂知识图谱项目。
- 文档和代码可能失去同步。
- 人工维护映射成本过高。
- 自动提取关系可能产生错误。
- 规则、模板、文档和图谱的界面容易相互混淆。

### 科学性结论

方向科学，但不能作为单个版本一次开发完成。

必须拆成：

```text
2.0A 规则与模板编译器
2.0B 项目上下文图谱
2.0C Agent 动态连接
```

先验证规则编译是否真正减少管理成本，再投资复杂图谱和动态连接。

## 冗余检查

| 可能重复的设计 | 处理结果 |
| --- | --- |
| 规则中心与模板中心 | 保留两个领域，但在同一个“资产中心”入口管理 |
| 文档生成与模板管理 | 取消泛化文档生成，只保留模板编译 |
| 需求树与文档树 | 需求是独立节点，文档通过关系引用需求 |
| 数据库树与代码树 | 分别建模，通过关系连接 |
| AGENTS 与规则 | AGENTS 是编译结果，规则库才是源头 |
| 生命周期与冲突状态 | 必须分开 |
| 临时规则与项目规则 | 使用同一规则模型，通过范围和有效期区分 |
| 项目规则与规则包 | 规则包可复用，项目只保存选择关系 |
| 提示词与规则 | 提示词是执行资产，规则是约束资产，通过关系关联 |
| 文档与来源资产 | 文档可以同时是来源资产和编译结果，需要标记角色 |

## 核心验收场景

1. 上传开发规范并提取规则。
2. AI 提取结果全部进入待确认状态。
3. 用户确认规则后才会进入活跃规则集。
4. 创建项目并选择三个规则包。
5. 项目规则覆盖全局普通规则。
6. 项目规则不能覆盖全局安全规则。
7. 创建一条临时规则，设置到期时间。
8. 系统检测到一条 P0 冲突并阻止编译。
9. 用户解决冲突后成功编译 AGENTS.md。
10. 创建需求树和数据库字段树。
11. 建立需求、模块和数据的映射。
12. 修改字段后系统显示受影响的需求和模块。
13. 导出规则和项目上下文。
14. Agent 不得自动修改已确认规则。

## 放到一边的结论

2.0 需求方向合理，经过拆分后没有不可解决的冗余。

当前决定：

- 保留需求草案。
- 暂不实现 2.0。
- 不合并规则资产原型分支。
- 不执行规则资产 SQL。
- 先完成 `v0.7.0` AI 增强与合并。
- `v0.7.0` 完成并稳定后，再正式设计 2.0A。
