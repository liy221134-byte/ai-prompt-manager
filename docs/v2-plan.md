# 2.0 资产管理底座计划

## 文档状态

- 目标阶段：`2.0.0` 至 `2.0.3`。
- 当前主题：先把项目、文档、规则和提示词等资产管理做深做实。
- 暂不进入：规则冲突编译、协作路径生成、上下文图谱和 MCP 动态连接。
- 本文只写决定，不写实现步骤、SQL 和成段代码。

## 一、做什么与不做什么

### 做什么

- 建立项目工作区，所有资产必须有明确归属。
- 将提示词、规则、文档、模板、技术档案和来源包统一纳入资产模型。
- 保留每份来源资产的原文、来源、版本和导入记录。
- 支持上传 Markdown、文本和 ZIP 文档包。
- AI 识别文档包后生成项目创建草稿，由用户确认后才创建项目。
- 为规则维护完整元数据，包括用途、范围、层级、优先级和生命周期。
- 为文档维护类型、角色、来源、权威版本和更新关系。
- 将技术选型建立为项目的一级档案，而不是几条零散规则。
- 支持资产之间的引用、依赖、来源和替代关系。
- 支持版本快照、归档、恢复和关系追踪。
- 支持按项目、类型、状态、标签、技术栈和适用范围筛选。
- `2.0.0` 先完成提示词、规则和文档三种基础资产的管理闭环。
- 本地 SQLite 与云端 Supabase 保持行为一致。
- 升级备份格式，使项目、资产、元数据和关系可以完整导出和恢复。

### 不做什么

- 不由 AI 在后台自动创建项目，不自动批准资产或规则。
- 不在本阶段自动解决规则冲突。
- 不在本阶段生成最终 `AGENTS.md` 编译结果。
- 不在本阶段生成文档与规则的完整协作路径。
- 不建设完整需求、模块、代码、数据和 Bug 图谱。
- 不接入 MCP 动态查询。
- 不自动修改外部 GitHub 仓库。
- 不建设团队协作、评论、审批和多人权限。
- 不做实时价格比较、云资源采购或运维平台。

## 二、项目与资产模型

### 项目

项目是资产归属和后续编译的基础。

每个项目至少包含：

- 稳定项目标识。
- 项目名称和一句话目标。
- 项目状态和当前阶段。
- 项目规模。
- 运行环境。
- 数据敏感度。
- 预算和维护约束。
- 技术档案。
- 创建时间、更新时间和归档状态。

### 资产通用字段

所有资产共享一套基础字段：

| 字段 | 说明 |
| --- | --- |
| 资产标识 | 稳定标识，移动或改名后不变化 |
| 资产类型 | 提示词、规则、文档、模板、技术档案、来源包 |
| 标题与摘要 | 便于搜索和识别 |
| 所属项目 | 所有正式资产必须归属一个项目 |
| 来源 | 手工创建、文件导入、AI 提取或系统生成 |
| 来源证据 | 原文件、原文片段、导入批次和来源位置 |
| 标签 | 跨项目的检索维度 |
| 状态 | 草稿、待确认、活跃、已归档、已废弃 |
| 版本 | 当前版本和不可变的历史版本 |
| 关系 | 引用、依赖、来源、替代、实现和验证关系 |
| 时间 | 创建、更新、生效和归档时间 |

### 资产类型边界

- 提示词：用于执行的 AI 指令资产，继续遵循现有变量和复制规则。
- 规则：约束开发行为的原子规则，不是完整文档。
- 文档：PRD、ADR、验收、数据库说明、发布手册等成篇内容。
- 模板：定义未来文档或编译结果的结构，不直接代表项目事实。
- 技术档案：记录项目技术选型、约束、默认值和偏离理由。
- 来源包：用户上传的原始文件或 ZIP，保留导入前的完整内容。

`2.0.0` 只开放提示词、规则和文档的新增与管理入口。模板、技术档案和来源包先保留模型能力，分别由 `2.0.1` 和 `2.0.2` 接入正式界面。

## 三、文档包导入与项目草稿

### 用户触发

只有用户主动点击“创建项目”或“导入资产包”时，系统才开始分析。

### 导入流程

```text
选择文件或 ZIP
-> 保留原始包
-> AI 识别项目、文档、规则、模板和技术信息
-> 生成项目创建草稿
-> 用户检查和修改映射
-> 用户确认
-> 创建项目并写入资产
```

### 用户确认前不得发生

- 不创建正式项目。
- 不写入正式资产库。
- 不自动激活 AI 提取的规则。
- 不用 AI 摘要覆盖原始内容。

### 导入预览必须展示

- 建议的项目名称和目标。
- 识别到的资产数量和类型。
- 每个文件的资产分类建议。
- 识别到的技术栈和约束。
- 识别到的候选规则。
- 无法识别或存在冲突的文件。
- 用户可以合并、拆分、改类型或跳过资产。

## 四、元数据设计

### 规则元数据

规则内容之外，至少维护以下维度：

| 维度 | 示例 |
| --- | --- |
| 规则类型 | 必须、禁止、建议、流程、验收、技术约束 |
| 规则用途 | 安全、协作、开发、测试、发布、数据管理 |
| 适用范围 | 全局、项目、任务临时 |
| 作用层级 | 项目、模块、功能、文件、数据类型 |
| 技术上下文 | Next.js、Supabase、PostgreSQL、Vercel |
| 执行阶段 | 立项、开发、测试、发布、运维 |
| 优先级 | P0 不可覆盖、P1 冲突警告、P2 普通建议 |
| 生命周期 | 待确认、活跃、已废弃、已拒绝、被替代 |
| 覆盖权限 | 是否允许项目和任务规则覆盖 |
| 来源与证据 | 来源资产、原文片段、导入批次 |
| 关系 | 引用、依赖、替代、冲突、验证 |
| 编译去向 | AGENTS、README、协作路径或模板 |
| 验证方式 | 人工确认、测试、发布门禁或运行时检查 |
| 版本原因 | 创建、修改、替代、失效和恢复原因 |

核心字段必须填写，扩展字段可以后续补齐。规则内容变更必须产生新版本，不能直接覆盖历史版本。

### 文档元数据

文档至少维护：

- 文档类型。
- 文档角色：来源、工作稿、权威版、编译结果、证据、参考资料。
- 是否为权威来源。
- 所属项目和模块。
- 当前版本和生效版本。
- 来源文件和原文位置。
- 关联规则、提示词、需求和验收。
- 更新触发条件。
- 新鲜度和最后验证时间。

### 技术档案

技术档案至少维护：

- 项目规模。
- 运行环境。
- 预算约束。
- 数据敏感度。
- 默认技术栈。
- 已选技术栈。
- 禁止使用的技术。
- 允许替代的条件。
- 需要 ADR 的偏离项。
- 维护责任和长期维护风险。
- 关联技术规则和决策记录。

## 五、关系与版本

### 关系

资产关系需要记录：

- 来源资产和目标资产。
- 关系类型。
- 创建方式：人工、导入或 AI 建议。
- 确认状态：待确认、已确认、已拒绝、已失效。
- 创建时间和最后验证时间。
- 来源证据。

本阶段先支持资产之间的稳定关联，不建设完整代码和数据库图谱。

### 版本与生命周期

- 内容变化产生不可变版本。
- 状态变化单独记录，不覆盖旧状态。
- 归档和废弃不等于删除。
- 删除进入垃圾箱，恢复和永久删除沿用现有数据安全原则。
- 现有提示词的合并和优化快照必须继续可恢复。

## 六、数据与备份影响

- 新模型需要项目和统一资产作为一级对象。
- 现有提示词迁移到默认项目，提示词标识保持不变。
- 现有合并、优化和垃圾箱语义不能丢失。
- 本地 SQLite 与 Supabase 使用同一套资产语义。
- 备份格式升级为可包含项目、资产、元数据、关系和版本的版本。
- 旧版提示词备份必须可以导入，并自动归入默认项目。
- 数据库结构变化必须先设计迁移、备份和回滚顺序。

## 七、验收标准

- 现有提示词迁移后全部出现在默认项目，数量和内容不丢失。
- 用户可以创建项目，也可以取消项目创建。
- 用户上传 Markdown、文本或 ZIP 后先看到导入预览，确认前不创建项目和资产。
- 原始文件被完整保留，AI 摘要不能覆盖原文。
- 用户可以确认、合并、拆分、改类型或跳过导入资产。
- 规则可以保存用途、范围、层级、优先级、生命周期和来源。
- 文档可以区分来源、权威版、工作稿和编译结果。
- 技术档案可以记录环境、规模、预算、技术选择和偏离理由。
- 资产之间可以建立和查看已确认关系。
- 资产可以搜索、筛选、归档、恢复和查看版本。
- 可以新增、编辑、查看和归档规则与文档。
- 正式保存会产生不可变版本，恢复历史版本会产生一个新版本。
- 版本内容不可被静默覆盖。
- 本地和云端行为一致。
- 新备份可以完整导出和恢复项目与资产。
- 旧提示词备份可以导入默认项目。
- `npm run check` 全部通过。

## 九、关键决定

1. 使用统一资产主模型，提示词作为其中一种资产类型；旧提示词表只保留迁移前快照，不承担双写。
2. 现有提示词归入默认项目，原标识不变化。
3. AI 只生成项目创建草稿，正式项目由用户确认创建。
4. 规则元数据完整存储，但界面只强制填写核心字段。
5. 技术选型是项目一级档案，偏离默认选型需要 ADR。
6. `2.0.0` 先交付项目、提示词、规则、文档和版本管理闭环；导入、深度元数据、技术档案和备份升级分别在 `2.0.1`、`2.0.2` 完成。
7. `2.0.3` 作为资产管理 MVP 的加固和验收版本，不新增功能。
8. 规则编译、协作路径、图谱和 MCP 在资产管理 MVP 稳定后再评估。

## 十、后续再评估

- 规则包、优先级和冲突裁决。
- 文档模板和规则组合编译。
- `AGENTS.md`、`README.md` 和 `START_PROMPT.md` 生成。
- 协作路径生成。
- 需求、模块、数据、代码、测试和 Bug 图谱。
- MCP 动态查询和文档新鲜度检查。

这些能力必须建立在项目、资产和元数据稳定之后，不能与资产管理底座同时开发。
