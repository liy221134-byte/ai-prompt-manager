# 用户故事与线上自测清单

## 用途

这份文件把「当前产品实际能做的事」写成一条条可手工验证的用户故事，给产品负责人
逐条走查用。它不描述代码，也不预测未来功能；每条故事都对应已经在版本里交付、
并有验收记录的行为。

怎么用：

1. 打开线上域名，按下面的顺序走。
2. 每条故事下面是可以勾的验证步骤，看到的结果和写的不一样就记下来。
3. 发现问题时记三样：在哪一步、你点了什么、屏幕上出现了什么（报错原文）。

验证步骤只写「看什么算对」，证据本身已经记录在对应的验收清单里（见每条的「依据」），
不在本文件重复。

## 一、线上自测须知

| 项目 | 内容 |
| --- | --- |
| 地址 | `https://ai-prompt-manager-liyunqi.vercel.app` |
| 应用账号 | `liyunqi233@163.com`（密码是你自己设的那个） |
| 部署保护 | 仍然开着，先用自己的 Vercel 账号过一层保护页，再进应用登录页 |
| 数据模式 | 线上强制云端模式（Supabase），不走本机数据库 |

自测前先做两件事：

1. 进「数据管理」导出一次备份文件，留一份自测前的线上数据快照。
2. 心里有数：**线上就是生产库**，你点的每一次保存都会写进去。测试用的提示词和项目，
   用完移进垃圾箱（30 天后自动清理），别把生产库当草稿纸反复造数据。

只能在本机验证、线上验不了的两处：

- 「导入工程」里的**分析代码目录**（线上读不到你电脑的目录，这一栏会禁用并写明原因）。
- **MCP 服务**（`npm run mcp`，只在开启了本机服务的电脑上能用）。

会遇到的已知行为，不是 bug：

- 提示词属于默认项目。切到别的项目时，如果停在「提示词」标签，界面会自动切回「全部」，
  这是为了避免你看到一个空列表以为数据丢了。
- 「智能采集」「AI 合并」「新增提示词」三个按钮只在默认项目 + 提示词标签下出现。
- 归档和垃圾箱里的资产不进图谱、不进备份，这是设计如此。

AI 相关功能（智能采集、AI 优化、AI 合并）需要线上环境变量里有 AI 密钥。如果点了报错，
记下报错原文再交给开发查，不要反复点。

## 二、故事清单

### A. 访问与登录

#### US-01 登录进自己的资产库

**卡片**：作为使用者，我想用邮箱密码登录，以便在任意设备上打开自己的资产库。

**在哪验**：线上，`/login`。

**验收步骤**

- [ ] 未登录直接访问首页，会跳到登录页。
- [ ] 用应用账号密码登录后进入资产库，能看到项目名和资产数量。
- [ ] 刷新页面仍然是登录状态，不会被踢回登录页。
- [ ] 点「退出登录」后回到登录页，再访问首页仍然被拦。

**依据**：[第 5 周验收](acceptance/week-05.md)、[v1.0.0 整体验收](acceptance/v1.0.0.md)

#### US-02 忘记密码时能自己找回

**卡片**：作为使用者，我想在忘记密码时重置，以便不依赖开发帮我把密码改回来。

**在哪验**：登录页的「忘记密码」。

**验收步骤**

- [ ] 登录页能看到「忘记密码」入口。
- [ ] 填自己的邮箱提交后，提示已发送（不必真的改密码，看到提示即可）。

**依据**：`src/app/auth/reset-password`、`src/app/auth/update-password`

#### US-03 手机和电脑看到同一份数据

**卡片**：作为使用者，我想在手机上也能看到电脑上存的资产，以便随时取用。

**在哪验**：电脑端和手机浏览器分别打开同一个域名，登录同一个账号。

**验收步骤**

- [ ] 电脑上新建一条测试提示词。
- [ ] 手机浏览器登录同一账号，能看到这条提示词。
- [ ] 手机上改标题保存，电脑刷新后标题同步变了。
- [ ] 自测完把这条测试提示词移入垃圾箱。

**依据**：[云端架构决策](decisions/0005-cloud-architecture.md)

### B. 提示词核心闭环（找 → 填 → 复制）

#### US-04 找到我要用的提示词

**卡片**：作为使用者，我想按分类、标签、关键词找到提示词，以便不用从头再写一遍。

**在哪验**：资产库列表上方的搜索框和筛选。

**验收步骤**

- [ ] 搜索框能按标题、分类、标签、正文命中。
- [ ] 类型、状态、标签、关系目标四个条件能叠加筛选。
- [ ] 清空筛选后回到默认的活跃资产列表。
- [ ] 归档或垃圾箱里的资产默认不出现。

**依据**：[v2.1.2 验收](acceptance/v2.1.2.md)

#### US-05 填变量并一键复制

**卡片**：作为使用者，我想把模板里的变量填好、一键复制，以便直接拿到最终内容。

**在哪验**：打开一条带 `{{变量}}` 的提示词详情抽屉。

**验收步骤**

- [ ] 正文里的 `{{变量名}}` 自动变成输入框，同一个变量只出现一个输入框。
- [ ] 变量名两侧的空格不影响识别。
- [ ] 变量没填完时复制按钮点不动，并写明还缺几个。
- [ ] 填完后预览区实时更新，复制出来的内容与预览完全一致。
- [ ] 没有变量的提示词不显示变量区，复制按钮直接可用。

**依据**：[产品范围 · 变量与复制](product-brief.md)、[第 2 周验收](acceptance/week-02.md)

#### US-06 新增和编辑提示词

**卡片**：作为使用者，我想用 Markdown 写提示词并预览，以便排版清楚、长期可维护。

**在哪验**：默认项目 + 提示词标签下的「新增提示词」。

**验收步骤**

- [ ] 标题、分类、标签、正文、适用场景都能填。
- [ ] 正文支持 Markdown 编辑与预览。
- [ ] 保存后立刻出现在列表里，刷新后仍在。
- [ ] 再次编辑保存生效，资产列表跟着刷新。

**依据**：[产品范围 · 提示词数据结构](product-brief.md)

#### US-07 整理识别出来的变量

**卡片**：作为使用者，我想把多余或叫法不准的变量改掉，以便复制出来的内容更贴我自己的用法。

**在哪验**：详情抽屉的「整理变量」，或编辑器里的变量清单。

**验收步骤**

- [ ] 变量清单随正文实时更新。
- [ ] 改名会同步改掉正文里全部出现位置。
- [ ] 降级为正文后占位符语法消失，里面的文字保留。
- [ ] 能把正文选区设为变量，也能在光标处插入变量。
- [ ] 空名、重名、花括号、名称超过 30 字或超过 20 个变量时保存被拦下。

**依据**：[变量管理设计](superpowers/specs/2026-09-21-variable-management-design.md)

#### US-08 误删后能从垃圾箱找回来

**卡片**：作为使用者，我想恢复误删的提示词，以便不担心手滑。

**在哪验**：工具栏「垃圾箱」。

**验收步骤**

- [ ] 删除提示词时先弹确认，确认后才移入垃圾箱。
- [ ] 垃圾箱里能看到被删的提示词，并知道是手动删的还是合并归档的。
- [ ] 恢复后回到正常列表。
- [ ] 永久删除单条、清空垃圾箱前都有确认提示。
- [ ] 界面上写明默认保留 30 天。

**依据**：[产品范围 · 管理垃圾箱](product-brief.md)

### C. AI 采集、优化与合并

#### US-09 粘贴原文让 AI 识别结构

**卡片**：作为使用者，我想粘一段原文让 AI 拆出标题、正文、分类、标签，以便采集不用手抄。

**在哪验**：默认项目 + 提示词标签下的「智能采集」。

**验收步骤**

- [ ] 粘贴原文后点识别，出现结果草稿，没有直接保存。
- [ ] 草稿里的标题、分类、标签、正文、适用场景都能改。
- [ ] 识别出的变量可以逐个确认、改名或降级。
- [ ] 只有点确认保存才会写进库，取消就什么都没留下。

**依据**：[产品范围 · 采集提示词](product-brief.md)

#### US-10 让 AI 优化一条提示词

**卡片**：作为使用者，我想让 AI 整理这条提示词的结构，以便它更好用，同时不改变原意。

**在哪验**：提示词详情的「AI 优化」。

**验收步骤**

- [ ] 生成后先给草稿和优化说明，不直接覆盖。
- [ ] 能看到正文行级差异和变量变化清单。
- [ ] 默认锁死变量集合，勾「允许调整变量」后才能增删改名。
- [ ] 正文明显变短或变长时有提醒。
- [ ] 确认保存后 30 天内可以「回到优化前」。

**依据**：[提示词 AI 优化设计](superpowers/specs/2026-09-20-ai-prompt-optimize-design.md)

#### US-11 把几条提示词合并成一条

**卡片**：作为使用者，我想把几条重复的提示词合成一条，以便库里不冗余。

**在哪验**：默认项目 + 提示词标签下的「AI 合并」。

**验收步骤**

- [ ] 选 2 至 5 条才能开始；少于 2 条按钮不可用。
- [ ] 第一条默认是目标，保存前可以改目标。
- [ ] 可以填可选的合并要求。
- [ ] AI 给的是可编辑草稿加合并说明，确认后才保存。
- [ ] 保存后：目标更新为合并结果，来源进垃圾箱，目标旧内容存成恢复快照。
- [ ] 快照能一键恢复到合并前。

**依据**：[AI 合并与垃圾箱设计](superpowers/specs/2026-09-20-ai-prompt-merge-design.md)

### D. 项目与资产

#### US-12 管理我的项目

#### US-13 用统一资产库看全部类型的资产

**卡片**：作为使用者，我想在一个列表里看提示词、规则、文档、模板、图谱节点、技术档案，

- [ ] 每条资产能打开详情，看到结构化元数据而不是一坨原文。
- [ ] 新建「规则」时能填规则类型和适用范围。

#### US-14 每次保存都留下版本，能恢复历史

**卡片**：作为使用者，我想在改坏内容后回到上一版，以便敢改、不怕丢。

**在哪验**：任意资产的详情抽屉 → 版本记录。

**验收步骤**

- [ ] 每次正式保存产生一个新版本，历史版本不能改写。
- [ ] 恢复历史版本会生成新版本，而不是抹掉记录。
- [ ] 版本列表里能看到每次改动时间和改动原因。
- [ ] 界面上写明「历史版本不在备份里」。

**依据**：[v2.1.2 验收](acceptance/v2.1.2.md)、[备份与恢复](operations/backup.md)

#### US-15 一个项目一份技术档案

**卡片**：作为使用者，我想记下项目的技术栈，以便编译产物和后续会话都知道这个项目用什么。

**验收步骤**

- [ ] 一个项目只有一份技术档案，第二次点开的是编辑，不是新建。
- [ ] 能填技术栈清单。
- [ ] 选型偏离默认时，不挂 ADR 文档会被拦下并说明原因。
- [ ] 编译产物的头部会带上一行技术栈摘要。

**依据**：[v2.1.2 验收](acceptance/v2.1.2.md)

#### US-16 给资产建关系，也知道被谁引用

**卡片**：作为使用者，我想把资产之间的关系记下来，以便改一条之前先知道会牵动谁。

**在哪验**：资产详情的「关系」区域。

**验收步骤**

- [ ] 四类关系都能建：引用、依赖、替代、实现。
- [ ] 关系目标的下拉里不会出现自己。
- [ ] 详情里既能看到「这条指向谁」，也能看到「被谁引用」。
- [ ] 目标已归档或在垃圾箱里时，有「目标已归档」之类的标注。

**依据**：[v2.1.2 验收](acceptance/v2.1.2.md)

- [ ] 「导出这个包」能把库里的包导成文件，重复成员只导一次。

#### US-19 把规则编译成 AGENTS.md 草稿

- [ ] 五类节点都能建：需求、模块、数据、接口、测试。
- [ ] 同一个项目、同一类型里编号不能重复，重复会被拦下并给出提示。
- [ ] 父节点只能选同类型的节点。
- [ ] 改编号不影响已经建好的引用。

**依据**：[v2.5.0 验收](acceptance/v2.5.0.md)

#### US-24 看项目图谱和影响分析

**卡片**：作为使用者，我想点开一个节点就知道它牵动谁，以便改之前先判断影响范围。

**在哪验**：工具栏「项目图谱」。

**验收步骤**

- [ ] 顶部五类可切换，并显示每类数量。
- [ ] 左边是树（父子缩进、按编号排序），右边是选中节点的编号、完整路径、说明和备注。
- [ ] 三块清单：这个节点指向谁、谁指向它、间接影响；间接那条写清是通过谁串起来的。
- [ ] 清单里每条都能点开对应资产或节点，也能一键跳到编辑器补关系。
- [ ] 归档和垃圾箱里的节点不出现；父节点被归档时，子节点按根显示而不是消失。

**依据**：[v2.5.0 验收](acceptance/v2.5.0.md)

#### US-25 从 SQL 建表语句导入数据节点

**卡片**：作为使用者，我想把建表语句变成图谱里的数据节点，以便数据库结构不用手敲。

**在哪验**：工具栏「导入工程」→「数据库 Schema」。

**验收步骤**

- [ ] 能粘贴建表语句，也能选 `.sql` 文件。
- [ ] 解析结果先出草稿（编号形如 `TBL-表名`），勾选确认后才写资产。
- [ ] 节点正文是字段清单（类型、非空、默认值、主键），备注写明来源。
- [ ] 外键在库里已有同编号节点时自动连成「依赖」关系。
- [ ] 编号已存在的默认标「已存在」且不勾选，导入只补新节点、不覆盖你改过的正文。

**依据**：[v2.6.0 验收](acceptance/v2.6.0.md)

#### US-26 从本机代码目录导入模块和接口（只能本机验）

**卡片**：作为使用者，我想让它读一遍我的代码目录，以便模块和接口节点自动进图谱。

**在哪验**：本机启动 `npm run dev` 后，工具栏「导入工程」→「分析代码目录」。

**验收步骤**

- [ ] 线上打开这一栏是禁用的，并写明原因；本机模式下可用。
- [ ] 一层目录生成一个「模块」节点，按目录层级挂父子。
- [ ] API 路由生成「接口」节点，正文列支持的 HTTP 方法。
- [ ] 依赖目录、构建产物、点开头的目录都跳过；符号链接不跟。
- [ ] 单文件超过 400 KB 只进清单不读内容；一次最多 3000 个文件。

**依据**：[v2.6.0 验收](acceptance/v2.6.0.md)

### H. 质量等级、验收与发布

#### US-27 按项目质量等级看我还缺什么

**卡片**：作为使用者，我想知道这个等级的项目该有哪些工程文档、该关注哪些规则方向，
以便交付前心里有底。

**在哪验**：工具栏「工程基线」。

**验收步骤**

- [ ] 四个质量等级可选：个人工具、低风险生产、涉及用户数据、高敏感。
- [ ] 必须有的工程文档列出「已有／还缺」，缺的点一下直接进新建文档（标题和类型已填好）。
- [ ] 建议关注的规则方向列出来。
- [ ] 发布前必须完成的检查按等级列出。
- [ ] 面板只做对照和跳转，不自动创建任何东西。

**依据**：[v2.8.0 验收](acceptance/v2.8.0.md)

#### US-28 用验收记录串起证据链

**卡片**：作为使用者，我想把「需求 → 验收条件 → 测试步骤 → 结果与证据 → 提交版本」
记在一条记录里，以便验收结论有出处。

**在哪验**：新建「验收记录」资产；工程基线的「验收覆盖」。

**验收步骤**

- [ ] 正文能写验收条件、测试步骤、实际结果和已知问题。
- [ ] 元数据能填对应需求节点、提交版本和证据清单（说明 + 链接或文件路径）。
- [ ] 新建和 AI 提交的记录一律先是「待确认」。
- [ ] 改成「通过」只能在界面上由人点，AI 的写入通道里根本没有这一项。
- [ ] 工程基线列出还没通过验收的需求，点「新建验收记录」进编辑器时标题和需求节点已填好。
- [ ] 「例外」算未覆盖，只有「通过」才算这条需求验收过。

**依据**：[v2.9.0 验收](acceptance/v2.9.0.md)

#### US-29 上线前用发布记录管门禁

**卡片**：作为使用者，我想上线前有一张必须做完的检查清单，以便不靠记性。

**在哪验**：工程基线里的「最近一次发布」／「新建发布记录」。

**验收步骤**

- [ ] 门禁清单按项目质量等级自动带出（个人工具 2 项、低风险生产 5 项、涉及用户数据 6 项、高敏感 7 项）。
- [ ] 每一项能勾「做完了」并写一句证据说明。
- [ ] 记录里能填版本号、发布日期、结果（进行中／已发布／已回滚）和回滚目标。
- [ ] 标题按版本号自动生成，例如「v2.10.0 发布记录」。
- [ ] 工程基线显示最近一次发布的版本、结果、门禁完成情况和还没完成的那几项。
- [ ] AI 写不了发布记录，调用会被参数校验拒绝。

**依据**：[v2.10.0 验收](acceptance/v2.10.0.md)

### I. 备份与外部接入

#### US-30 导出和导入备份

**卡片**：作为使用者，我想定期导出一份数据，以便出事时有东西可恢复。

**在哪验**：工具栏「数据管理」。

**验收步骤**

- [ ] 说明里写清备份范围：项目、各类资产、资产关系。
- [ ] 说明里写清不在备份里的东西：每个资产的历史版本、来源包上传的原始文件。
- [ ] 导出得到一个 JSON 文件，并记录「上次备份」时间。
- [ ] 导入只新增不覆盖；同名项目合并到已有项目。
- [ ] 旧版（只有提示词的）备份仍然能导入，进默认项目。

**依据**：[备份与恢复](operations/backup.md)、[v2.11.0 验收](acceptance/v2.11.0.md)

#### US-31 让 AI 通过 MCP 查资产（只能本机验）

**卡片**：作为使用者，我想让 AI 直接查库里的资产，以便不用我手动复制粘贴背景。

**在哪验**：本机 `npm run mcp`。

**验收步骤**

- [ ] 六个查询工具可用：列项目、搜提示词、取资产、列规则、列图谱节点、算影响分析。
- [ ] 三个写入工具只做新增和编辑，没有任何删除类工具。
- [ ] 写入的资产来源标成「AI」，界面上一眼能分辨。
- [ ] 每次写入产生一条不可变版本，可以从界面恢复到旧版本。
- [ ] 设 `MCP_READ_ONLY=1` 时只注册查询工具。

**依据**：[本机 MCP 服务](operations/mcp-server.md)、[v2.7.0 验收](acceptance/v2.7.0.md)

## 三、资产效用验证（本次重点）

前面 31 条证明「功能能用」。这一节证明「积累的资产真的能派上用场」——链条走通一次，
比逐条看功能更能说明问题。

#### US-32 用规则包到编译产物走一遍完整交付

**卡片**：作为使用者，我想从现成的规则包出发，产出一份能直接放进新项目的规则文件，
以便下次开项目不用从零写规则。

**验收步骤**

- [ ] 选一个项目，装一个规则包（例如工程方法种子资产包或操作者训练包）。
- [ ] 打开「规则编译」，确认参与编译的规则条数，看一眼冲突候选是否需要裁决。
- [ ] 选一个模板，生成产物，检查项目名、项目说明、技术栈是否自动填好。
- [ ] 把产物保存成文档资产，打开详情确认内容和版本记录都在。
- [ ] 用「数据管理」导出一次备份，确认这份产物在备份文件里。

**依据**：[v2.2.0](acceptance/v2.2.0.md)、[v2.3.0](acceptance/v2.3.0.md)、[v2.4.0](acceptance/v2.4.0.md) 验收清单

#### US-33 用图谱和关系回答一次「改这里会影响什么」

**卡片**：作为使用者，我想在改一条规则或一个模块之前，看到它会牵动谁，以便不做连环破坏。

**验收步骤**

- [ ] 在项目图谱里选一个已有节点，看「这个节点指向谁 / 谁指向它 / 间接影响」。
- [ ] 从影响清单点开对应资产，确认跳转正确。
- [ ] 打开一条规则或文档，在关系区看「被谁引用」，确认与图谱对得上。

**依据**：[v2.5.0 验收](acceptance/v2.5.0.md)、[v2.1.2 验收](acceptance/v2.1.2.md)

#### US-34 用工程基线和验收记录回答一次「这个项目能发布吗」

**卡片**：作为使用者，我想一眼看到这个等级的项目还缺哪些工程文档、哪些需求还没验收，
以便决定能不能发布。

**验收步骤**

- [ ] 打开「工程基线」，看必须有的工程文档「已有／还缺」。
- [ ] 看「验收覆盖」里还没通过验收的需求清单。
- [ ] 给其中一条需求建验收记录，填上条件和证据，把结论改成「通过」。
- [ ] 回到工程基线，确认这条需求从缺口里消失。
- [ ] 建一条发布记录，看门禁清单是否按当前质量等级带出来。

**依据**：[v2.8.0](acceptance/v2.8.0.md)、[v2.9.0](acceptance/v2.9.0.md)、[v2.10.0](acceptance/v2.10.0.md) 验收清单

## 四、自测结束后的收尾

1. 把自测结论写进本文对应条目的勾选框；发现的问题单独列一份清单，别混进故事里。
2. 测试数据（新建的提示词、项目、节点）移入垃圾箱或归档；线上库不要留实验数据。
3. 再导出一次备份，与自测前那份对比，确认资产数量变化符合预期。
4. 有问题回到对话里说「第几条 + 你点了什么 + 看到什么」，由开发按修 bug 四步走处理。
