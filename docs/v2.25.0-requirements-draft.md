## 一、评审 P0 第 3 条：`product-brief.md` 停在 v1

### 现状（实测）

`docs/product-brief.md` 共 155 行，整篇只讲提示词库：定位是「AI 提示词资产管理工具」，
必做能力列到变量、合并、垃圾箱为止，数据结构一节讲的是 `prompts` 表字段。
「项目」「资产」「图谱」「规则编译」「质量等级」「验收证据链」「发布门禁」这些 2.0 才有的东西，
全文一个都没有。

### 为什么这条严重

它在 `docs/INDEX.md` 的「阅读顺序」里排第 4 条（前三条是 `AGENTS.md`、`README.md`、`INDEX.md`）。
也就是说，**任何一个新会话、任何一个接手的人，读到的第一份产品文档就是错的范围**——
会以为这个产品只管提示词。

### 同类发现（评审没提，这次核对到的）

`docs/roadmap.md`（111 行）也停在 v1：8 周路线图 + v1.0.0 收尾 + 「更后面（未排期）」，
没有任何 2.0 的内容。它在阅读顺序里排第 5，**紧跟在 `product-brief.md` 后面**。

结论：只改 `product-brief.md`，等于把误导往后挪一格。要么一起改，要么在 `product-brief.md`
里明确写一句「后续路线见 roadmap（未更新，以 `v2-plan.md` 为准）」。见第八节待拍板 1。

## 三、口径：每类载体只干一件事

这是本草案要你确认的核心决定（与评审裁决一致：定义只留资产那一处）。

| 载体 | 唯一职责 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| **规则／方法资产**（`seed-packs/**/assets/`，公共资产库里的正本） | **术语与判据的唯一正本** | 定义表、判据、红线、失败模式、验证证据、使用条件 | 填空表格、给 AI 的角色话术 |
| **方法模板**（`templates/methods/`） | 填空骨架 | 表头、占位符、一行「对应规矩 + 资产 id」 | 术语定义（一句话引用即可） |
| **提示词**（`prompt-packs/`） | 可直接粘贴的执行指令 | 角色／背景／任务／约束／输出格式；定义压成一句话短语 | 完整定义、判据表 |
| **技能**（`E:\AI资产市场\skills\`） | 触发与编排 | `description` 触发条件、步骤、不适用场景；指向资产 id | 规则正文副本、模板正文副本 |

统一引用写法：`RULE-PREMORTEM-001`（一句话说明这条资产管什么）。

## 四、做什么 / 不做什么

### 做

1. **重写 `docs/product-brief.md`**：从「提示词库」升到当前真实范围——定位、目标用户、
   核心流程（采集／使用／项目立项／规则编译／图谱／验收证据链／发布门禁／沉淀回流）、
   不做清单（多租户、团队协作、自动部署执行）、当前阶段与后续（v3 零代码交付线是待确认支线）。
2. **五组主题按第三节口径收口**：资产留定义、模板留骨架、提示词留指令、技能留编排。
3. **给「需求改写成三种格式」补一条定义正本**（新建资产，id 待定，例如
   `MTH-REQ-FORMAT-001`），把三份模板里重复的「三种格式的公式与验收条件」收进这一条。
4. **技能仓库 `references/` 去副本**（跨仓库，要先经你同意）：删掉「规则-xxx.md」这类副本，
   `SKILL.md` 里改成指向资产 id；模板副本保留（它就是骨架，属于该写的那一层）。
5. **本机库同步**：新增一个「按 id 精确更新方法模板与提示词」的脚本
   （现在只有起步模板和技能两个同步脚本，方法模板和提示词还没有），把改动同步进本机库。
6. **先写一条能挡住复发的检查**（见第六节第 5 条），再动内容。

### 不做

- 不改任何规则的**判据内容**。这次只动副本，不动定义本身；定义哪里写得不清楚，另开一版。
- 不碰云端生产库（要同步是另一次「一次一议」）。
- 不动 `prompt-packs/development-rules.md` 那 5 条（评审说它口径偏浅，属于另一件事）。
- 不动 `templates/engineering/` 的 9 份工程文档模板。
- 不合并资产类型，不改产品界面（界面看不到变化）。

## 五、数据与产品行为影响

1. **产品代码零改动**：改的是内容文件和文档，`src/` 一行不动，界面上看不到任何变化。
2. **本机库**：涉及约 20 条资产正文更新 + 1 条新增（4 条规则、6 份模板、5 条提示词、5 个技能）。
   资产 id 不变，所以**已经引用它们的项目不受影响**；每次更新带一条版本记录，可回退。
3. **技能仓库**：`references/` 文件数减少，`SKILL.md` 增加资产 id 引用。四家工具的挂载不受影响
   （挂载的是 `SKILL.md`，frontmatter 的 `name`／`description` 不动）。
4. **风险**：模板和提示词变短后，如果资产那边的定义本身不够清楚，会显得「说了等于没说」。
   所以第三节的口径要你确认，且第 3 条任务（补定义正本）必须先做。

## 六、验收标准（每条都能用一次命令或一次手工验证判定）

1. `docs/product-brief.md` 里搜得到「项目」「规则编译」「质量等级」「发布门禁」「图谱」；
   「第一版范围」一节不再只讲提示词库。
2. 五组主题的定义句只在资产文件里出现：逐组 grep（例如「房间里的大象」「Kill criterion」
   「ASCII 线框」），命中只落在 `seed-packs/engineering-foundations/assets/` 下。
3. 6 份方法模板每份首部都有「对应规矩 + 资产 id」行，5 个 id 都能在资产目录里找到同名文件。
4. 提示词包 5 段每段都能对上至少一条资产 id。
5. **新检查能挡住复发**：把任意一句定义句复制回模板后跑检查 → 变红；删掉 → 变绿（先红后绿）。
6. 本机库里对应资产的正文与仓库正本逐字一致（同步脚本 `--dry-run` 报 0 差异）。
7. `npm run check:fast` 通过（纯内容改动，按 `AGENTS.md` 可以只跑测试，但要说明跑了什么）。
