# 线索 3 M2.2 需求草案：采集产出自动落库

- **状态**：**已确认（2026-09-30）**，实现见 [M2 设计稿第十四节](leads-3-m2-design-and-tasks.md)
  （`docs/leads-3-m2-design-and-tasks.md`）。下面三个问题的答案：**① 全自动**——话术驱动，
  采完即落库，不等口令；**② 不加 `--dry-run`**——默认真跑；**③ 话术按执行环境分两支**。
- **由来**：M2.1 实测（含产品负责人 2026-09-30 本人试用）暴露两件事——采集产出件回流台账要
  手动走 UI 导入，且智能体交件时没说清台账怎么更新；云端路线下「没进库的资产怎么落库」
  没有明确答案。话术没写清产出物格式这条已在 v2.28.1 修复，不在本版范围。

## 目标（用户故事）

- **US-A**：我把采集话术交给本地智能体（Codex / WorkBuddy），它采集完**自动把候选资产写进
  本机库**——台账立刻多一行采集记录，不用我手动导入；云端靠 `npm run sync -- --push` 跟上。
- **US-B**：没进库的资产有明确落库路径——本地路线走 US-A 的命令，云端路线走
  「给压缩包」UI 导入（云端模式下直接写云端，已验通）。
- **US-C**：每类资产的「正本在哪」有一张定死的表（原 M2.2 收窄方向，并入本版一起交付）。

## 三条路线

| 路线 | 做法 | 结论 |
| --- | --- | --- |
| A. UI 导入（现状） | 产出件 .md / .zip → 台账「给压缩包」→ AI 提炼 → 落库 | **已跑通，保留当兜底**；缺点是最后一步要手动点 |
| B. 落库命令（M2.2 主体） | `npm run collect:land -- <产出件目录> --source "…" --ecosystem "…"`：读目录里的 .md（每文件一条，格式契约见 v2.28.1 话术），直读成候选资产（draft + hypothesis + 来源摘录）+ 自动生成采集记录，写**本机库**；之后 `sync -- --push` 推云端 | **推荐**。复用 `planSourcePackageCreation`（external-collection 模式）+ 现有本地写库链路——2026-09-30 回流实验已端到端跑通，风险低 |
| C. 智能体直写云端 | 调线上 API / 直连 Supabase | **不做**：要凭证、要网络，还绕过产品落库规则 |

路线 B 的格式契约已经由 v2.28.1 话术定死：每个 .md 一条候选规则、`# 标题` 起头、
无 frontmatter、无元信息——正是为了让命令可以**直读**，不用再过一遍 AI 提炼。

## 边界（不做什么）

- **不自动转正**：落库仍是 draft / candidate，转正走人工确认（合规硬约束不变）。
- **不做双向同步**：维持 2026-09-30 已定方向（正本归属表 + 需要时加显式回写命令）。
- **不改数据模型**：source_references 不进库，维持 M2.1 的结论。

## 验收口径（草案）

1. 给一个真实来源生成话术 → 本地智能体产出 .md → 跑 `collect:land` → 本机台账多一行
   （采集记录 + 候选资产带 hypothesis 与来源摘录）；**重复跑幂等**（0 新增）。
2. `sync --push` 后线上台账与本机一致。
3. 不跑命令时，产出件仍可走「给压缩包」UI 导入——兜底不断。

## 待产品负责人确认（确认后进设计稿）

1. **B 命令由话术驱动全自动跑**（采集完即落库），还是产出后等你一句「落库」再跑？
   ——建议前者，这才符合「自动更新本地数据库」。
2. `collect:land` 沿用 `import:leads3-records` 惯例：默认真跑、带 `--dry-run` 先看清单——同意？
3. 话术要不要按执行环境分两支：本地智能体（能碰仓库 → 产出后直接跑命令）/
   云端或无文件系统智能体（只交产出件 → 走 UI 导入）？——建议要，否则话术对两种
   环境各说一半。
