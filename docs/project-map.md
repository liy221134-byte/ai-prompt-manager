# 生产级项目指南地图

## 这份文档解决什么

它只回答四个问题，不解释怎么做：

1. 这个项目是什么规模和形态？
2. 现在处于哪个阶段？
3. 这个阶段必须读什么、必须产出什么、必须过哪道门禁？
4. 什么可以跳过？

流程细节在工程种子资产包里（`seed-packs/engineering-foundations/`），本文只做路由，
不重复内容。当前项目进度看 `docs/roadmap.md`。

## 四份文档的分工

| 文档 | 职责 | 什么时候读 |
| --- | --- | --- |
| `AGENTS.md` | 规矩：怎么做、不能怎么做 | 每次会话自动加载 |
| 本文 | 立项路由：定规模、环境和阶段，指出该读什么、该过什么门禁 | 五个事件触发时 |
| `seed-packs/engineering-foundations/` | 方法库：某件事具体怎么做 | 按本文的必读列去查 |
| `docs/` 其余文档 | 本项目实例：需求、设计、验收、运维 | 日常开发时读 |

判断有没有写错位置的唯一标准：**规矩放 `AGENTS.md`，路由放本文，方法放资产包，
本项目的事实放 `docs/` 其余文档。**

## 怎么用这份地图

这份地图是**方法层**文档，项目自己的规则文档是**实例层**。区别很重要：地图只在一个
项目或版本的少数几个时刻被读，其余时间躺在库里。

| 事件 | 读地图做什么 |
| --- | --- |
| 立项 | 定规模、环境和阶段，编译出项目自己的规则文档 |
| 标签变化 | 规模、环境或阶段标签变了，补跑对应阶段的门禁 |
| 阶段跳跃 | 例如直接要交付内网，回头补阶段 3 的门禁 |
| 交付移交 | 产出交付包和运维手册 |

**开新版本不算触发事件。** 版本号大小不是判据：0.8 到 0.9 这种小版本升级，只要三个标签
没变，就只瞄一眼 README 里的标签，不读地图。反过来，小版本也可能触发——比如加了一个
处理用户上传文件的功能，数据敏感度就变了。判据是**标签有没有变、阶段有没有跳**，
判定成本就是对比三行字。

**按节读，不必整份读完**：判定规模只看「第一步」，选技术只看「第二步」，排活只看
「第四步的门禁」，内网交付只看「第五步的环境差异」。所以这些章节的标题和层级要保持稳定。

立项阶段的编译产物：

1. 项目自己的 `AGENTS.md`：把选定的门禁和规则写进去，起步模板在 `templates/new-project/`。
2. 需求边界一页纸：做什么、不做什么、验收标准。
3. **规模、运行环境、当前阶段三个标签**：写进项目 README 第一段或 `AGENTS.md` 开头。
   日常不读地图，复判时直接从这三个标签读，不重新推导。

规模升级或阶段跳跃时，回到地图重跑一次编译，并把新标签写回项目文档。

## 第一步：给项目定性

### 规模（决定流程密度）

| 级别 | 判定信号 |
| --- | --- |
| 个人工具 | 只有自己或少量可信的人用；坏了能快速重建；数据不敏感 |
| 中型产品 | 有账号和数据库；有备份和发布要求；模块数量有限 |
| 大型平台 | 多模块、多团队、多系统集成；有可用性和性能指标 |
| 监管或高敏 | 涉及重要数据；内网或专网；有等保、审计、信创要求 |

判定步骤见 `assets/001-project-scale-classification.md` 的七步检查。

### 运行环境（决定部署和运维打法）

| 环境 | 判定信号 |
| --- | --- |
| 全托管 | 部署和数据库都用云服务，例如 Vercel + Supabase |
| 自建云主机 | 有服务器和公网，自己装、自己运维 |
| 公司托管 | 有内部平台和审批，只能提交不能直连 |
| 内网隔离 | 物理隔离或专网，进出要摆渡，远程基本用不上 |

### 阶段（决定这一次该做什么）

| 阶段 | 标志 |
| --- | --- |
| 0 立项 | 还没写代码，或只有想法 |
| 1 骨架 | 端到端能跑通一条最短链路 |
| 2 迭代 | 按版本加功能 |
| 3 加固 | 有真实用户，或者准备交付 |
| 4 发布与运维 | 上线之后的日常 |
| 5 交付与移交 | 交给客户运维接手 |

## 第二步：技术选型基线（按约束取默认值）

立项时最该做的不是比较技术，而是**缩小可选范围**。默认直接选，偏离默认才需要理由。

> 状态：**未验证假设。** 目前只有 1 个个人工具加全托管项目的一手经验，下面四行是起点
> 不是结论。做完第一个内网交付项目后回来修正，并标出哪些默认值被实践推翻过。

| 约束 | 默认选型 | 明确不要选 |
| --- | --- | --- |
| 个人工具 + 全托管 | 单体应用 + 托管数据库 + 托管部署 | 微服务、K8s、自建消息队列 |
| 中型产品 | 单体 + 托管 Postgres + 对象存储 + 托管队列 | 多语言多栈、自研网关、自建缓存集群 |
| 内网隔离 | 单体 + Docker Compose + 自建数据库 | 任何需要公网的服务或依赖 |
| 高敏或信创 | 同上，加国产数据库与操作系统、离线依赖包 | 公网依赖、非信创组件、需要联网授权的东西 |

选任何技术之前先过三问：

1. 目标环境能不能装上、能不能离线跑？
2. 出问题时谁来维护它？只有你会维护的组件，等于把项目绑在你自己身上。
3. 三年后还有人维护它吗？停止维护的组件是负债。

**偏离默认要写一条 ADR**（放在 `docs/decisions/`），默认选择不用写。这样选型记录不会
变成流水账。

## 第三步：可用性三个数字

高可用不是一个立项开关，而是从承诺倒推出来的结果。立项只写三个数字：

> 状态：**未验证假设。** RTO 分档是从通用经验推出来的，还没有在真实故障里验证过。

| 数字 | 要回答的问题 |
| --- | --- |
| 可用性目标 | 向谁承诺了什么？没有对外承诺，就等于不需要高可用 |
| RTO | 出故障后多久必须恢复 |
| RPO | 最多能接受丢多少数据 |

然后用 RTO 倒推架构档位：

| RTO | 档位 | 成本 |
| --- | --- | --- |
| 秒级 | 多副本加自动故障转移 | 最高，个人和小团队一般扛不住 |
| 分钟级 | 主备加自动切换 | 高 |
| 小时级 | 备份加一键重建脚本 | 低，大多数小项目应该选这一档 |
| 天级 | 备份加手工恢复 | 最低 |

一条经验：**「能快速重建」通常比「永不停机」划算得多**。一台机器、定时快照、一个重建
脚本，RTO 可能只有十几分钟，成本是真正高可用方案的零头。

两条提醒：RPO 靠备份频率决定，和可用性档位是两件事，要分开定；只做主备却从不演练，
等于假高可用——切换没演练过，真出事的时候切不过去。

## 第四步：每个阶段的门禁

门禁必须可判定：说不清"拿什么证明过了"，这条门禁就是装饰。

| 阶段 | 必读资产 | 必产出 | 门禁 |
| --- | --- | --- | --- |
| 0 立项 | 001 规模分级、003 需求边界、本文第二和第三步 | 一页纸：做什么、不做什么、验收标准；技术选型基线；可用性三个数字；规模与环境标签 | 边界写清楚；选型落在默认档；可用性数字有出处 |
| 1 骨架 | 005 架构基线、006 端到端最小链路、008 接口与数据归属 | 能跑的最短链路、数据归属说明 | 端到端真的跑通，且留下证据 |
| 2 迭代 | 004 指标冲突、007 模块分解 | 每版一份《设计 + 任务清单》 | 一版只做一个子系统；测试先于实现；`npm run check` 通过 |
| 3 加固 | 009 质量画像、010 验收证据链 | 验收清单和证据 | 安全、备份、回滚、限额逐条有证据 |
| 4 发布运维 | 011 发布回滚、012 故障演练 | 发布操作单、回滚演练记录 | 在演练里真的回滚成功过一次 |
| 5 交付移交 | 011、本文第五步的环境差异表 | 离线制品包、部署手册、回滚手册、诊断脚本、部署台账 | 客户运维照着手册独立部署一次 |

## 第五步：环境差异（同一条流程，四种打法）

| | 全托管 | 自建云主机 | 公司托管 | 内网隔离 |
| --- | --- | --- | --- | --- |
| 代码怎么进 | 推分支，平台自动构建 | 推分支，流水线拉取 | 提交工单或流水线 | 离线包摆渡 |
| 依赖怎么进 | 平台托管 | 公网或公司私服 | 公司私服 | 离线镜像包 |
| 迁移怎么执行 | 自动或手动调用函数 | 流水线执行 | 审批后执行 | 人工执行，备份先行 |
| 回滚怎么做 | 平台切换版本 | 镜像回滚加 SQL 回滚 | 走审批 | 软链接切回加 SQL 回滚 |
| 故障怎么响应 | 远程 | 远程 | 远程加工单 | 现场为主，争取 VPN |
| 谁有生产权限 | 我 | 我 | 平台或运维 | 客户运维，或我持账密 |

操作细节见 `docs/operations/` 下的迁移、发布回滚和备份文档。

## 第六步：可以跳过什么

按规模和阶段砍流程，不要一刀切：

- 个人工具：跳过发布门禁、跨账号验证、故障演练；保留需求边界、最小链路、验收证据。
- 不涉及数据结构变化：跳过迁移相关的全部动作。
- 纯界面和文案调整：按 `AGENTS.md`，不需要设计文档。
- 没有真实用户之前：跳过 SLA、值班、监控告警。

## 立项只定不可逆的决定

「既完整又不冗余」的边界，只用一条判据：**这个决定如果要改，代价是「重写」还是「替换」**。

| 类别 | 什么时候定 | 例子 |
| --- | --- | --- |
| 重写级 | 立项时必须定死 | 数据存在哪、运行环境、主语言和框架族、可用性三个数字、合规边界 |
| 替换级 | 需要的时候再说 | 具体库、目录结构、CI 工具、监控方案、缓存 |

立项时把重写级定死，替换级留白。想把替换级也提前定完，是立项阶段最常见的时间浪费。

## 什么时候重新看这份地图

- 每次开新版本时复判一次规模、环境和阶段，成本是一行字。
- 规模升级时（个人工具变成有别人用）补跑对应阶段的门禁。
- 阶段跳跃时（例如直接要交付内网）回头补阶段 3 的门禁。

## 已知缺口

种子资产定义了四级规模，但只写了三个画像，**缺少「监管或高敏」画像**（内网、信创、
等保这一类）。目前由本文的「环境差异」表覆盖，建议后续补一份
`profiles/regulated-intranet.md`。

技术选型基线现在只有四行，覆盖不了数据库、前端框架、身份认证这些每年都要重新比较的
选择。**不现在写**的原因：这类资产的价值来自实战反馈，只有 1 个项目的一手经验时写出来
的大多是未验证假设。触发条件写清楚——**做完第一个内网交付项目后**，整理成独立资产
`MTH-STACK-001`，并记录哪些默认值被实践推翻过。

还有一处缺口是**换环境时的零代码边界**。现在这条链路是 GitHub → Vercel → Supabase 云端，
每换一个环节都有一块必须手工补的能力，靠改配置换不过去。

| 环节 | 换到内网或自建环境后 | 能不能靠配置解决 |
| --- | --- | --- |
| 代码托管 | 公司 GitLab 或客户内网 GitLab | 能，换 remote 即可 |
| 自动部署 | GitLab CI/CD 加内网 Runner | 不能，Vercel 的 Git 集成没有替代物 |
| 应用托管 | 客户服务器上的 Docker 加反代 | 不能，要装环境、编排、配证书 |
| 认证 | 自建实例的认证或客户统一认证 | 不能，用户表和会话签发方变了 |
| 数据库 | 自建 Postgres，或达梦、人大金仓 | 前者可原样搬迁移文件；后者表结构、函数、策略都要重写 |
| 文件存储 | MinIO 或客户对象存储 | 不能，云存储的调用方式不通用 |
| 邮件 | 客户的 SMTP | 不能，自建实例不带邮件通道 |
| 证书 | 内网自签 CA | 不能，还要做根证书分发 |
| 观测 | 客户监控或自建 | 不能，云端日志面板没有替代物 |
| 备份 | 脚本加定时任务 | 不能，从"控制台点一下"变成"自己写" |

关于 MCP 的位置要单独说清楚：CircleCI、GitLab 这类 MCP 只是让智能体能读流水线状态、
触发重跑、看失败原因，**真正执行部署的是 Runner 或服务器上的脚本**。MCP 替代不了执行
引擎，也替代不了内网可达性——物理隔离环境里再多的 MCP 都连不上。

触发条件：**第一个内网或自建环境交付项目立项时**，把这张表展开成清单，逐项确认是
"配置能解决"还是"要补能力"。

## 文档淘汰规则

只增不减的体系一定会膨胀，所以每次立项或复盘时问三句：

1. 这份文档现在还有人读吗？没有 → 移到 `docs/archive/`。
2. 这份文档的内容能不能被另一份替代？能 → 合并，不留两份。
3. 这条规则有没有对应的证据？没有 → 要么补证据，要么删掉。

## 这份地图的边界

它防的是「一开始选错路线」，不替代阶段内的判断。
它不重复流程细节；一旦发现它在解释「怎么做」，那段内容应该挪回资产包。
