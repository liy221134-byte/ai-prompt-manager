# 工程能力学习计划

## 定位

这份计划独立于产品功能开发，用于学习如何作为产品负责人管理一个生产级 AI 项目。
目标不是自己写代码，而是能够理解关键链路、提出正确问题、识别风险、验收结果，
并在系统出问题时知道如何恢复。

## 学习原则

1. 一次只训练一个能力，避免把产品需求和工程学习混在一起。
2. 每项能力都必须包含解释、实际操作、证据和复盘。
3. 优先使用本地、Preview 和测试数据，不在唯一生产数据上制造故障。
4. 破坏性演练前先备份，并明确恢复路径。
5. 通过学习是否减少失联感来判断效果，不以看过多少概念为标准。

## 能力地图

| 能力 | 需要能回答的问题 | 当前项目的练习 | 证据 |
| --- | --- | --- | --- |
| 系统架构 | 浏览器、Vercel、Supabase 和 AI 分别负责什么 | 画出并解释三条请求链路 | 架构与链路说明 |
| Git 与版本 | 代码如何从本地进入生产，如何找到上一版 | 从分支、提交、标签追踪一次发布 | 提交和标签记录 |
| 工程门禁 | 什么情况下允许部署，失败后在哪里看原因 | 观察一次 `npm run check` 和 Vercel 构建 | 检查与构建结果 |
| 数据与迁移 | 表结构怎么变化，迁移和部署谁先谁后 | 记录一次测试迁移的顺序和结果 | 迁移验证记录 |
| 权限与安全 | 谁会看到数据，密钥放在哪，配置错误会怎样 | 检查 RLS、环境变量范围和失败关闭行为 | 安全检查记录 |
| 备份与恢复 | 数据丢了如何恢复，多久能恢复 | 使用测试提示词完成一次恢复演练 | 恢复前后对比 |
| 发布与回滚 | 上线失败时怎么退回正常版本 | 通过 Vercel 回滚一次 Preview 或生产演练 | 回滚与基础验收记录 |
| 可观察性 | 怎么知道系统正常，出错后先看哪里 | 使用 Vercel 日志和健康接口定位一次问题 | 问题时间线 |
| 成本与性能 | 免费额度和性能边界在哪里，什么会触发成本 | 学习 QPS、慢查询、存储和调用额度概念 | 基线和风险清单 |

## 演练顺序

### 演练一：理解系统

- 从浏览器访问 `/` 开始，追踪页面保护、数据读取和 AI 采集链路。
- 说明每一步由谁执行、失败时会看到什么。
- 不需要修改代码。

### 演练二：发布门禁

- 阅读一次 `npm run check` 的结果。
- 查看 Vercel 的构建日志和上次正常部署。
- 说明缺少哪项检查时不能上线。

### 演练三：配置失败

- 在隔离环境制造一次 Supabase 配置错误。
- 验证页面和 API 安全关闭，而不是降级到本机 SQLite。
- 恢复配置并复验。

### 演练四：备份恢复

- 导出一份只含测试数据的备份。
- 修改测试提示词。
- 按恢复流程导入，核对标题、正文、标签和变量。

### 演练五：发布回滚

- 选择上一个正常 Ready 部署完成回滚。
- 验证登录、数据读取和 AI 采集。
- 记录从发现问题到恢复完成的时间。

### 演练六：安全边界

- 检查 Preview 与 Production 的环境变量范围。
- 确认浏览器可见变量和服务端密钥的边界。
- 确认不同账号无法读取彼此的数据。

### 演练七：成本与性能

- 了解 Vercel 和 Supabase 免费层的限制及暂停条件。
- 学习请求次数、存储、慢查询和 AI 调用量如何影响成本。
- 列出触发升级或迁移服务器前必须满足的条件。

## 生产交付能力路线（2026-09-20 结论）

产品开发完成之后，还需要补上"内网和自建环境交付"的能力。路线是先走 C，再走 A，不跳步。

### 路径 C：方案 + 标准 + 验收（先走这条）

- 我负责：离线制品包、一键部署脚本、部署手册、回滚手册、诊断脚本、验收清单。
- 客户负责：按手册执行部署的运维人员。
- 我负责指挥、验证和问题定位，不亲手敲生产环境的命令。

### 路径 A：自己能独立部署（长期目标）

| 层级 | 内容 | 达到什么程度 |
| --- | --- | --- |
| 必须会 | Linux 基础命令、Docker、看日志、改配置、重启服务、数据库备份恢复、Nginx、HTTPS 证书 | 能独立把一套应用从零部署到客户服务器，出问题能自己救回来 |
| 应该会 | shell 脚本、基础 SQL、看监控指标、按清单排障 | 能定位常见故障 |
| 交给别人 | 数据库调优、高可用架构、信创深度适配 | 明确边界，不硬扛 |

### 手工交付演练（暂缓）

- 触发条件：产品功能基本完成之后再做，不占用功能开发的时间。
- 做法：用独立的练习项目或项目副本，在本地模拟一台服务器，从零部署一遍，包含数据库迁移和回滚。
- 安全红线：绝不在当前项目的生产代码和唯一生产数据上做演练。
- 为什么推迟：把产品交付和能力训练混在一起，两边都做不好，这和 v0.8 复盘中"一个版本塞三套东西"属于同一类问题。

### 内网交付的现实约束

- 物理隔离环境下 AI 无法远程接入。替代方案是进现场之前准备好完整工具箱：离线制品包、一键诊断包脚本、常见故障对照表；出故障后把日志带出来分析。
- 客户给生产账密、没有审批流程、没有 DBA 时，用个人最小门禁补上：先备份、写变更清单、挑低峰窗口、执行、验证留档。
- 动手之前必须书面确认责任边界：备份责任人、停机窗口、故障响应时限、操作权限范围。
## 生产交付要补的知识（2026-09-21 记录）

下面四块是换到内网或自建环境后一定要会的东西。不在当前项目上练，等产品功能迭代完，
按顺序一块一块补，每块都留证据。

| 知识块 | 要能回答的问题 | 最小可练的版本 |
| --- | --- | --- |
| 数据库搭建与使用 | 怎么装、怎么连、怎么建表、怎么备份、怎么恢复 | 本地起一个 Postgres 容器，建表、写入、导出备份、删掉数据、再恢复回来 |
| 证书与 HTTPS | 证书从哪来、怎么续、内网怎么让浏览器不报红 | 用自签 CA 签一张证书，配到本地反向代理，把根证书导入浏览器 |
| 文件存储 | 附件放哪里、怎么控权限、怎么备份 | 本地起一个 MinIO，上传下载一个文件并配好访问策略 |
| 邮件接入 | 用谁的 SMTP、怎么验证发件域名、投递失败怎么看 | 用测试邮箱服务发一封验证邮件，看到成功投递 |

顺序建议是数据库、证书、文件存储、邮件。数据库决定应用能不能起来，证书决定能不能被访问，
后两块是功能性补充，晚一点影响不大。

这四块对应"靠改配置换不过去"的具体位置，清单在 `docs/project-map.md` 的「已知缺口」。

## 完成标准

- 能用自己的话解释页面、数据、AI 和安全链路。
- 知道什么情况允许部署，失败后先查什么。
- 能完成一次备份恢复和一次版本回滚。
- 能识别密钥、RLS、免费额度和慢查询的基本风险。
- 每次演练都留下可复查的结果，不只依赖 AI 口头说明。
