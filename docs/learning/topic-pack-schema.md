# 主题包 schema（唯一正本）

版本：**2.1**（2026-10-28，随 v4 M3 知识点讲义定稿）
上游：`docs/requirements/v4-learning-system-prd.md` · `docs/learning/v4-plan.md`
实例：`docs/learning/topics/rk-mid-integration.yaml`
导入器：`scripts/import-topic-pack.mjs`

**这份文件定的是 AI 与产品之间的接口契约。** AI 出主题包必须按这里写，导入器按这里校验。
两边任何一方自行加字段，都算破坏契约。

---

## 一、两层模型（先理解这个，字段才有意义）

主题包同时携带两个维度，**不能混为一谈**：

| 维度 | 是什么 | 在哪定义 | 数据结构 |
| --- | --- | --- | --- |
| **内容模块**（`modules`） | 学哪块知识。按教材章节归并，6 个左右 | 主题包里定义 | `learning_modules` 表 |
| **能力层级**（`level`） | 对这块知识能到什么程度，L1—L5 | **结构是产品常量；每层的名字与判据由主题包的 `level_definition` 提供** | `practice_questions.level` + `learning_topics.level_definition` |

### 为什么「五层结构」写死、「五层内容」随主题（v2 改动）

v1 的写法是「层级是产品常量，主题包里不定义」。这条在只有一个考试目标时成立，
但目标类型一多就不成立了：**用考试型的判据去量 Python 会量错**——能背出装饰器的定义
不等于会写；反过来用技能型的判据量中项也会漏——会写一段代码不等于能在四个选项里挑对法规条款。

所以拆成两件事：

| 什么 | 归谁定 | 理由 |
| --- | --- | --- |
| **五层这个结构**（必须 5 层、逐层递进、每层判据必须可观察） | 产品常量 | 诊断矩阵、历史趋势、跨模块对比全靠这个骨架对齐 |
| **每一层叫什么、怎么判** | 主题包的 `level_definition` | 考试看「答对需要什么」，技能看「能不能写出东西」，体系看「能不能互相支撑」，行为看「能不能稳定复用」 |

**v1 那句真正要保护的东西仍然成立，只是收窄了范围：同一主题内，层级定义不可变。**
今天的 L3 和三个月后的 L3 必须是同一件事，否则趋势就没法看。所以：

- `level_definition` 只在**首次导入**时写入；
- 重导入时若与库中已存的定义不一致，**导入器直接拒绝**，要改判据就得新开主题 id。

### 内置四类阶梯模板（`kind` 决定用哪套）

`kind` 只有四个取值。选哪一套不看你想要什么，看**这个目标拿什么判成败**。

| 层 | `exam` 考试型<br>中项 · 系统架构设计师 | `skill` 技能型<br>Python · SQL | `system` 体系型<br>AI coding · 品牌体系 | `behavior` 行为型<br>向上管理 |
| --- | --- | --- | --- | --- |
| 1 | **认得**：给选项能挑对，说不出为什么 | **看得懂**：读别人的代码能说出它在干嘛 | **有框架**：知道这个领域分哪几块 | **知道有这回事**：能复述概念 |
| 2 | **说得出**：不看资料，用自己的话讲清是什么、几个要素 | **改得动**：在现有代码上改一行并跑通 | **能分类**：任给一条素材能归到某块 | **能识别处境**：能判断自己现在处在哪种情形 |
| 3 | **算得出**：套公式、走流程，能一次做对 | **写得出**：给需求能独立写出可运行的代码 | **能填满**：每块都有实际素材，不空着 | **能设计动作**：能写出一次具体要说什么、做什么 |
| 4 | **判得准**：给没见过的场景，判断落点与流程 | **调得通**：报错能定位、能改对、能说清原因 | **能互相支撑**：块与块之间能引用、能解释关系 | **做过有反馈**：真做过，并拿到对方的反应 |
| 5 | **迁得动**：错题能归因到哪个概念；能拿自己项目讲一遍 | **能设计**：能自己拆结构、选方案，不只跟着教程 | **能教人**：能讲给不懂的人听懂 | **稳定复用**：换了场景还能用同一套做法 |

中项沿用 `exam` 那套（与 v1 的五层定义完全一致，属于同一套判据换了个归类）。

**其他类别的阶梯不是拍脑袋定的，判据全部遵守同一条规则：看「做到这件事需要什么」，不看「难不难」。**
一张表填不出的层级，说明这一层对这类目标不成立——宁可换模板，不要硬凑五层。


**给题目打 level 的判据**：看「答对这道题需要什么」，不是看「题目难不难」。
同一个知识点，「SV 小于 0 意味着什么」是 L2，「给定四个数算 SV」是 L3，
「给他一个项目场景判断进度状态并说明依据」是 L4。

## 二、顶层结构

```yaml
schema_version: 2        # 必填，正数。允许小数（1 → 1.1 → 2 → 2.1）
topic:    { ... }        # 必填，主题元信息（含 kind）
level_definition: [ ... ] # v2 起：五层的名字与判据。缺省时按 kind 用内置模板
modules:  [ ... ]        # 必填，内容模块（顺序即学习顺序）
knowledge_points: [ ... ] # 必填，知识点树
question_policy: { ... } # 可选，出题策略
questions: [ ... ]       # 可选，随包带的题
```

`schema_version` 只写主版本号也能过（`2` 与 `2.0` 等价）。判据只看值的大小，
不做「新版本才有的字段必须有」这种推断——主题包会先升版、数据后补。

## 三、字段定义

### 3.1 `topic`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 全局唯一，小写连字符。导入幂等的依据（同 id 重复导入不产生重复行） |
| `name` | string | ✅ | 主题全名 |
| `kind` | string | ✅（v2） | `exam` / `skill` / `system` / `behavior`。决定用哪套阶梯模板、进度怎么判。缺省按 `exam` 处理 |
| `goal` | string | ✅ | 一句话目标，**要能验证**。「一次通过，两科同次均 ≥45 分」可以；「学好」不行 |
| `deadline` | date | ✅ | `YYYY-MM-DD`。`deadline` 与 `exam_date_predicted` 的区别见下 |
| `exam_date_predicted` | date |  | 推算的考试日（官方未发布时用） |
| `registration_expected` | string |  | 报名窗口，如「2027-03下旬」。**这是全旅程里唯一不可挽回的节点**，必填建议 |
| `total_hours` | number | ✅ | 计划总投入。**必须等于各模块 `planned_hours` 之和** |
| `start_date` | date |  | 开始学习日 |
| `exam_facts` | object |  | 考试事实：科目、满分、合格线、形式、费用、教材。纯展示，不参与计算。**另含 `milestones`，见下** |

#### `exam_facts.milestones`（关键节点，塞在 exam_facts 里）

主题页靠它显示倒计时。**这是约定出来的键，不是新建的表列** —— 理由见 M1 设计文档第三节：
新建列要写迁移，而迁移在本环境得人工去 SQL Editor 执行，不值得。

```yaml
exam_facts:
  milestones:
    - { name: 报名开放, date: "2027-03-20", note: "山东窗口约 10-20 天，无补报" }
    - { name: 准考证打印, date: "2027-05-10" }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | ✅ | 节点名，显示在主题页 |
| `date` | ✅ | `YYYY-MM-DD`。**必须是能解析的日期**，写「2027-03下旬」这种描述会被导入器拒绝 |
| `note` |  | 补充说明 |

导入器会校验 `name` 与 `date`，因为写错不会报数据库错误、只会让倒计时静默算错，这种错最难查。

#### `level_definition[]`（v2 新增：五层的名字与判据）

**不写也能导**——按 `kind` 用内置模板（见第一节的四类模板）。写了就以包里的为准。
五个元素，`level` 必须是 1 到 5 各一次，顺序不限。

```yaml
level_definition:
  - level: 1
    name: 认得
    criteria: 给选项能挑对，但说不出为什么
    evidence: 单选 easy
  - level: 2
    name: 说得出
    criteria: 不看资料，用自己的话讲清它是什么、几个要素
    evidence: 判断 / 简答
  # …L3—L5
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `level` | ✅ | 1—5，各出现一次 |
| `name` | ✅ | 两个字最好，超过 6 个字表格列头会挤。如「认得」「看得懂」 |
| `criteria` | ✅ | **必须可观察**：能出题验证、或能看出做没做到。「理解深刻」不行 |
| `evidence` |  | 拿什么证明达到了这层，如「单选 easy」「能跑通的脚本」 |

**校验规则（导入器强制执行）**：

1. 恰好 5 条，`level` 覆盖 1—5 且不重复；
2. `name` 非空且不重复（两层的名字一样，说明没想清区别）；
3. `criteria` 非空，且**不得出现「理解」「掌握」「熟悉」这类不可判的词**——
   和 `entry_criteria` 同一条规矩：写不出可观察行为，就等于没定标准。

### 3.2 `modules[]`（内容模块，不是能力阶梯）
| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 主题内唯一，如 `S1`。跨主题可重复（表用复合主键） |
| `order` | integer | ✅ | 学习顺序，从 1 开始，**不允许重复** |
| `name` | string | ✅ | 模块名 |
| `scope_chapters` | int[] |  | 对应教材章节号，用于核对覆盖度 |
| `weight` | number | ✅ | 占分权重，**各模块之和必须为 1.0**。**当前是估算值，须标 `estimate`** |
| `expected_gap` | 1—5 | ✅ | 预判缺口（1=很熟 5=空白）。**首次诊断后必须用真实结果覆盖** |
| `planned_hours` | number | ✅ | 计划投入，**之和必须等于 `topic.total_hours`** |
| `entry_criteria` | string | ✅ | 进入条件。**必须写「能做什么」，不能写「学完 S1」** |
| `exit_criteria` | string | ✅ | 达标标准。同样必须是可观察的行为 |
| `common_mistakes` | string[] | ✅ | 常见错误，诊断归因时直接引用 |
| `min_project` | string |  | 最小产出物。**这是区分「学过」和「会用」的唯一字段**，建议必填 |
| `note` | string |  | 备注，如「分值不高但缺口最大」 |

> **`entry_criteria` 写成「S1 达标」是错的做法**，那是模块依赖，不是能力标准。
> 正确写法是「给一个场景能判断落在哪个过程组」——它是可观察的行为，能出题验证。
> 原型的主题包里 S2/S4/S6 三处都是这种错例，**M0 已被导入器校验拦下并改正**；
> 校验规则保留，因为它挡住的是往后每一份新主题包。

### 3.3 `knowledge_points[]`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 主题内唯一，建议 `KP-<模块号><两位序号>` |
| `module_id` | string | ✅ | 必须存在于 `modules[].id` |
| `parent` | string \| null | ✅ | 上级知识点 id，可空。**只用于错题向上归因，不要求每层都填** |
| `name` | string | ✅ | 知识点名 |
| `ref` | string |  | 教材章节，如「第13章」 |
| `note` | object |  | 讲义。**可选**——没写就是「讲义待补」，页面显示成灰字，不影响导入。**只存在主题包里，不落库**（见本节末） |
| `note.summary` | string | ✅（写 note 时） | 一句话定义，≤ 60 字。超过上限会被拒：这里放的是「一句话」，写长就是摘要 |
| `note.body` | string | ✅（写 note 时） | 讲义正文（markdown）。**固定含三段：`### 要素` `### 例题` `### 怎么考`**，缺一段直接拒 |

`parent` 允许为空是刻意的：中项 29 个知识点里只有 2 个有父级。强求层级只会逼着人编层级。

**讲义为什么强制三段**：这四个字段各答一个问题，缺一个讲义就变味——

| 段 | 回答什么 | 缺了会怎样 |
| --- | --- | --- |
| `summary` | 这东西一句话是什么 | 读完不知道重点，只记住一堆细节 |
| `### 要素` | 它由哪几部分组成、怎么判 | 变成一句口号，考到细节就答不上 |
| `### 例题` | 长什么样、错在哪 | 变成题解，只会这一道 |
| `### 怎么考` | 卷面上以什么形态出现 | 学完了不知道在哪用，遇到题还是懵 |

校验器只查小标题在不在，不规定每段多少字——长度交给写的人判断，机器去管它只会逼出凑字数的填充段。

**讲义允许渐进补，但中项这个主题已补齐**：29 个知识点 29 篇全有（2026-10-28 完成，覆盖 S1 至 S6）。导入器与生成器都允许 `note` 缺省，是为了新加知识点时可以先只有骨架，不必等讲义写完才能跑通。

**讲义不进数据库**（2026-10-28 晚定，取代原先「加两列」的做法）。`knowledge_points` 表里没有 `summary` / `note_md` 列，也没打算加：

| | 存数据库 | 编译成常量（现方案） |
| --- | --- | --- |
| 真源 | 库里一份 + 主题包一份，**两份要对齐** | 主题包一份 |
| 改讲义后 | 要重导一次库，漏了就是页面显示旧内容且看不出异常 | 改 yaml → `npm run gen:topic-notes` → 提交 |
| 运行时 | 一次查询（本来就要查知识点，讲义顺带） | 零请求，随 bundle 走 |
| 迁移依赖 | 要一次 DDL | 无 |

判据是「它是什么」：讲义是随主题包分发的**静态内容**，有读无写，不参与判分也不参与统计。给只读内容建副本，等于给自己多养一份必须同步的真源。

实现：`scripts/build-topic-notes.mjs` 扫 `docs/learning/topics/*.yaml`，生成 `src/lib/learning/topic-notes.generated.ts`；前端经 `src/lib/learning/topic-notes.ts` 取用。生成物与主题包不一致时 `npm run check:topic-notes` 与 `tests/topic-notes.test.mjs` 都会拦下。

**补讲义时要先看这条**：主题包里的知识点很多是**流式写法**（整条压在一行花括号里，如 `- {id: KP-0201, module_id: S2, parent: null, name: 启动过程组, ref: "第10章"}`）。流式里塞不进 `body: |` 这种多行块标量，所以加 `note` 时必须把该条**先转成块式**再挂。转的时候别手拼引号——名称里有全角括号与斜杠，交给 `js-yaml.dump` 单条对象再缩进最稳。2026-10-28 第一次补那 24 篇时就栽在这：按块式写的插入逻辑对 24 条流式条目一条都没命中，脚本报「插入 0 篇」，文件倒是一个字没改。

### 3.4 `question_policy`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `source_policy` | string[] | 允许的题目来源，取值 `ai` / `web` / `manual` |
| `per_kp_min` | integer | 每个知识点最少题数。**v4 起改用「每层至少 1 题」，本字段仅作参考** |
| `types` | string[] | 适用题型 |
| `require_open_question_per_kp` | boolean | 每个知识点至少 1 道非选择题，否则诊断会退化成「认题」 |

### 3.5 `questions[]`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 全局唯一，如 `RK-S1-001` |
| `module_id` | string | ✅ | 必须存在 |
| `kp_id` | string | ✅ | 必须存在 |
| `category` | string | ✅ | 题库分类名，与现有 `/practice` 的分类一致才能混排 |
| `type` | string | ✅ | `单选` / `多选` / `判断` / `实操` |
| `difficulty` | string | ✅ | `easy` / `medium` / `hard`（旧口径，保留兼容） |
| `level` | 1—5 | ✅ | **能力层级，新口径**。与 `difficulty` 并存，`difficulty` 表达「题目难」，`level` 表达「答对它需要什么」 |
| `title` | string | ✅ | 题目标题 |
| `body_md` | string | ✅ | 题干（markdown）。**见下方硬约束** |
| `options` | string[] | ✅ | 选项。实操作答给空数组 `[]` |
| `answer` | string | ✅ | 答案。单选写 `"B"`，多选写 `"ABD"`，实操写参考答案文本 |
| `explanation_md` | string | ✅ | 解析（markdown）。**见下方硬约束** |
| `source` | string | ✅ | `ai` / `web` / `manual` |
| `source_url` | string |  | 来源链接，`source=web` 时应填 |

## 四、三条硬约束（踩过才知道）

### 1. markdown 字段必须用 block scalar（`|`）

```yaml
# ✅ 对
body_md: |
  下列关于项目与运营的说法，正确的是？

# ❌ 错——正文里出现 **加粗**、`冒号: 空格`、引号时，YAML 解析器会直接报错
body_md: 下列关于项目与运营的说法，正确的是？
```

原型的主题包第一版就是这样炸的，修了 19 处。**导入器遇到这类错误必须给人话报错，
不能只抛 YAML 堆栈**——要指出「第几行、哪个字段、大概什么原因」。

### 2. 三个合计必须自洽

导入器在写库**之前**校验，不通过直接退出、不写半份数据：

- `sum(modules[].weight)` == 1.0（浮点容差 1e-6）
- `sum(modules[].planned_hours)` == `topic.total_hours`
- 每道题的 `module_id` / `kp_id` 都能在包里找到
- `modules[].order` 不重复且从 1 连续

### 3. `id` 前要留前缀

`S1` 这种 id 只在主题内唯一。**不要指望跨主题唯一**——表用 `(topic_id, id)` 复合主键，
这是设计决策，不是疏漏。

## 五、导入器的校验与报错口径

导入失败时，报错必须让人**不用读代码就知道改哪**。最低要求：

| 场景 | 报错应包含 |
| --- | --- |
| YAML 语法错 | 文件路径 + 行号 + 列号 + 原始提示（不吞掉 js-yaml 的 message） |
| 缺必填字段 | 字段路径（如 `modules[2].exit_criteria`）+ 该模块 id |
| 合计对不上 | 实际值 + 期望值 + 差值（如「weight 合计 1.02，应为 1.00，多 0.02」） |
| 引用不存在 | 引用方 id + 被引用 id + 期望它属于哪个集合 |
| `level` 越界 | 题目 id + 实际值 + 允许范围 |

**不做的事**：不自动修复、不猜测意图、不「先导进去再说」。校验不过就整份拒绝。

## 六、版本演进

| 版本 | 变化 | 何时 |
| --- | --- | --- |
| 1 | 初版：`modules` 命名（原 `stages`）、题目带 `level` | 2026-10-27（M0） |
| 1.1 | `weight` 用真题/错题分布校准、`expected_gap` 用首次诊断结果覆盖、`order` 按「缺口×分值」重排、`entry_criteria` 从「S1 达标」改成可观察行为 | M0.5 |
| 2 | 新增 `topic.kind`（四类目标性质）与 `level_definition`（五层的名字与判据随主题走）；「层级是产品常量」收窄为「同一主题内层级定义不可变」 | 2026-10-28（M2） |
| 2.1 | `knowledge_points[].note`：知识点讲义（summary + 要素 / 例题 / 怎么考三段） | 2026-10-28（M3） |

**导入器必须同时接受 1、1.1、2、2.1**，因为主题包会先升版、数据后补。判据只看 `schema_version` 的值，
不做「新版本才有的字段必须有」这种推断。缺 `kind` 按 `exam`，缺 `level_definition` 按 `kind` 的内置模板。

**v2 的兼容边界**：`schema_version < 2` 的包导入时，`level_definition` 用内置模板补齐并写库；
写成 v2 却给了不合规的 `level_definition`，整份拒绝——不降级、不猜测。

**v2.1 的兼容边界**：`note` 全程可选，没有「版本到了 2.1 就必须每个知识点都有讲义」这条规则——
讲义是内容，内容不该成为导入的前提条件。判据只有一条：写了 `note` 就必须合规。
