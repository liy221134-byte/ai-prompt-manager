# 主题包 schema（唯一正本）

版本：**1.0**（2026-10-27，随 v4 M0 定稿）
上游：`docs/requirements/v4-learning-system-prd.md` · `docs/learning/v4-plan.md`
实例：`docs/learning/topics/rk-mid-integration.yaml`
导入器：`scripts/import-topic-pack.mjs`

**这份文件定的是 AI 与产品之间的接口契约。** AI 出主题包必须按这里写，导入器按这里校验。
两边任何一方自行加字段，都算破坏契约。

---

## 一、两层模型（先理解这个，字段才有意义）

主题包同时携带两个维度，**不能混为一谈**：

| 维度 | 是什么 | 在哪定义 | 数据结构 |
| --- | --- | --- | --- |
| **内容模块**（`modules`） | 学哪块知识。按教材章节归并，6 个左右 | 主题包里定义 | `learning_modules` 表 |
| **能力层级**（`level`） | 对这块知识能到什么程度，L1—L5 | **产品常量，主题包里不定义**，只给题目打标 | `practice_questions.level` |

**层级是产品常量，理由**：层级一旦可以由主题包自定义，诊断矩阵和历史数据就全部失效——
今天的「L3」和三个月后的「L3」不是同一件事，趋势就没法看。

### 五层的定义（判分口径）

| 层 | 名字 | 判定标准 | 典型题型 |
| --- | --- | --- | --- |
| 1 | 认得 | 给选项能挑对，说不出为什么 | 单选 |
| 2 | 说得出 | 不看资料，用自己的话说清它是什么、几个要素 | 判断 / 简答 |
| 3 | 算得出 | 套公式、走流程，能一次做对 | 计算 / 流程默写 |
| 4 | 判得准 | 给**没见过的**场景，判断属于哪个过程组、该走哪条流程 | 场景题 / 案例 |
| 5 | 迁得动 | 错题能归因到哪个概念错；能拿自己的项目对着讲一遍 | 实操 / 案例改写 |

**给题目打 level 的判据**：看「答对这道题需要什么」，不是看「题目难不难」。
同一个知识点，「SV 小于 0 意味着什么」是 L2，「给定四个数算 SV」是 L3，
「给他一个项目场景判断进度状态并说明依据」是 L4。

## 二、顶层结构

```yaml
schema_version: 1.1      # 必填，正数。允许小数（1 → 1.1 → 1.2）
topic:    { ... }        # 必填，主题元信息
modules:  [ ... ]        # 必填，内容模块（顺序即学习顺序）
knowledge_points: [ ... ] # 必填，知识点树
question_policy: { ... } # 可选，出题策略
questions: [ ... ]       # 可选，随包带的题（M0 阶段用来验证链路）
```

## 三、字段定义

### 3.1 `topic`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 全局唯一，小写连字符。导入幂等的依据（同 id 重复导入不产生重复行） |
| `name` | string | ✅ | 主题全名 |
| `goal` | string | ✅ | 一句话目标，**要能验证**。「一次通过，两科同次均 ≥45 分」可以；「学好」不行 |
| `deadline` | date | ✅ | `YYYY-MM-DD`。`deadline` 与 `exam_date_predicted` 的区别见下 |
| `exam_date_predicted` | date |  | 推算的考试日（官方未发布时用） |
| `registration_expected` | string |  | 报名窗口，如「2027-03下旬」。**这是全旅程里唯一不可挽回的节点**，必填建议 |
| `total_hours` | number | ✅ | 计划总投入。**必须等于各模块 `planned_hours` 之和** |
| `start_date` | date |  | 开始学习日 |
| `exam_facts` | object |  | 考试事实：科目、满分、合格线、形式、费用、教材。纯展示，不参与计算。**另含 `milestones`，见下** |

#### `exam_facts.milestones`（关键节点，塞在 exam_facts 里）

主题页靠它显示倒计时。**这是约定出来的键，不是新建的表列** —— 理由见 M1 设计文档第三节：
新建列要写迁移，而迁移在本环境得人工去 SQL Editor 执行，不值得。

```yaml
exam_facts:
  milestones:
    - { name: 报名开放, date: "2027-03-20", note: "山东窗口约 10-20 天，无补报" }
    - { name: 准考证打印, date: "2027-05-10" }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | ✅ | 节点名，显示在主题页 |
| `date` | ✅ | `YYYY-MM-DD`。**必须是能解析的日期**，写「2027-03下旬」这种描述会被导入器拒绝 |
| `note` |  | 补充说明 |

导入器会校验 `name` 与 `date`，因为写错不会报数据库错误、只会让倒计时静默算错，这种错最难查。

### 3.2 `modules[]`（内容模块，不是能力阶梯）
| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 主题内唯一，如 `S1`。跨主题可重复（表用复合主键） |
| `order` | integer | ✅ | 学习顺序，从 1 开始，**不允许重复** |
| `name` | string | ✅ | 模块名 |
| `scope_chapters` | int[] |  | 对应教材章节号，用于核对覆盖度 |
| `weight` | number | ✅ | 占分权重，**各模块之和必须为 1.0**。**当前是估算值，须标 `estimate`** |
| `expected_gap` | 1—5 | ✅ | 预判缺口（1=很熟 5=空白）。**首次诊断后必须用真实结果覆盖** |
| `planned_hours` | number | ✅ | 计划投入，**之和必须等于 `topic.total_hours`** |
| `entry_criteria` | string | ✅ | 进入条件。**必须写「能做什么」，不能写「学完 S1」** |
| `exit_criteria` | string | ✅ | 达标标准。同样必须是可观察的行为 |
| `common_mistakes` | string[] | ✅ | 常见错误，诊断归因时直接引用 |
| `min_project` | string |  | 最小产出物。**这是区分「学过」和「会用」的唯一字段**，建议必填 |
| `note` | string |  | 备注，如「分值不高但缺口最大」 |

> **`entry_criteria` 写成「S1 达标」是错的做法**，那是模块依赖，不是能力标准。
> 正确写法是「给一个场景能判断落在哪个过程组」——它是可观察的行为，能出题验证。
> 原型的主题包里 S2/S4/S6 三处都是这种错例，**M0 已被导入器校验拦下并改正**；
> 校验规则保留，因为它挡住的是往后每一份新主题包。

### 3.3 `knowledge_points[]`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 主题内唯一，建议 `KP-<模块号><两位序号>` |
| `module_id` | string | ✅ | 必须存在于 `modules[].id` |
| `parent` | string \| null | ✅ | 上级知识点 id，可空。**只用于错题向上归因，不要求每层都填** |
| `name` | string | ✅ | 知识点名 |
| `ref` | string |  | 教材章节，如「第13章」 |

`parent` 允许为空是刻意的：中项 29 个知识点里只有 2 个有父级。强求层级只会逼着人编层级。

### 3.4 `question_policy`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `source_policy` | string[] | 允许的题目来源，取值 `ai` / `web` / `manual` |
| `per_kp_min` | integer | 每个知识点最少题数。**v4 起改用「每层至少 1 题」，本字段仅作参考** |
| `types` | string[] | 适用题型 |
| `require_open_question_per_kp` | boolean | 每个知识点至少 1 道非选择题，否则诊断会退化成「认题」 |

### 3.5 `questions[]`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | 全局唯一，如 `RK-S1-001` |
| `module_id` | string | ✅ | 必须存在 |
| `kp_id` | string | ✅ | 必须存在 |
| `category` | string | ✅ | 题库分类名，与现有 `/practice` 的分类一致才能混排 |
| `type` | string | ✅ | `单选` / `多选` / `判断` / `实操` |
| `difficulty` | string | ✅ | `easy` / `medium` / `hard`（旧口径，保留兼容） |
| `level` | 1—5 | ✅ | **能力层级，新口径**。与 `difficulty` 并存，`difficulty` 表达「题目难」，`level` 表达「答对它需要什么」 |
| `title` | string | ✅ | 题目标题 |
| `body_md` | string | ✅ | 题干（markdown）。**见下方硬约束** |
| `options` | string[] | ✅ | 选项。实操作答给空数组 `[]` |
| `answer` | string | ✅ | 答案。单选写 `"B"`，多选写 `"ABD"`，实操写参考答案文本 |
| `explanation_md` | string | ✅ | 解析（markdown）。**见下方硬约束** |
| `source` | string | ✅ | `ai` / `web` / `manual` |
| `source_url` | string |  | 来源链接，`source=web` 时应填 |

## 四、三条硬约束（踩过才知道）

### 1. markdown 字段必须用 block scalar（`|`）

```yaml
# ✅ 对
body_md: |
  下列关于项目与运营的说法，正确的是？

# ❌ 错——正文里出现 **加粗**、`冒号: 空格`、引号时，YAML 解析器会直接报错
body_md: 下列关于项目与运营的说法，正确的是？
```

原型的主题包第一版就是这样炸的，修了 19 处。**导入器遇到这类错误必须给人话报错，
不能只抛 YAML 堆栈**——要指出「第几行、哪个字段、大概什么原因」。

### 2. 三个合计必须自洽

导入器在写库**之前**校验，不通过直接退出、不写半份数据：

- `sum(modules[].weight)` == 1.0（浮点容差 1e-6）
- `sum(modules[].planned_hours)` == `topic.total_hours`
- 每道题的 `module_id` / `kp_id` 都能在包里找到
- `modules[].order` 不重复且从 1 连续

### 3. `id` 前要留前缀

`S1` 这种 id 只在主题内唯一。**不要指望跨主题唯一**——表用 `(topic_id, id)` 复合主键，
这是设计决策，不是疏漏。

## 五、导入器的校验与报错口径

导入失败时，报错必须让人**不用读代码就知道改哪**。最低要求：

| 场景 | 报错应包含 |
| --- | --- |
| YAML 语法错 | 文件路径 + 行号 + 列号 + 原始提示（不吞掉 js-yaml 的 message） |
| 缺必填字段 | 字段路径（如 `modules[2].exit_criteria`）+ 该模块 id |
| 合计对不上 | 实际值 + 期望值 + 差值（如「weight 合计 1.02，应为 1.00，多 0.02」） |
| 引用不存在 | 引用方 id + 被引用 id + 期望它属于哪个集合 |
| `level` 越界 | 题目 id + 实际值 + 允许范围 |

**不做的事**：不自动修复、不猜测意图、不「先导进去再说」。校验不过就整份拒绝。

## 六、版本演进

| 版本 | 变化 | 何时 |
| --- | --- | --- |
| 1 | 初版：`modules` 命名（原 `stages`）、题目带 `level` | 2026-10-27（M0） |
| 1.1 | `weight` 用真题/错题分布校准、`expected_gap` 用首次诊断结果覆盖、`order` 按「缺口×分值」重排、`entry_criteria` 从「S1 达标」改成可观察行为 | M0.5 |

**导入器必须同时接受 1 和 1.1**，因为主题包会先升版、数据后补。判据只看 `schema_version` 的值，
不做「新版本才有的字段必须有」这种推断。
