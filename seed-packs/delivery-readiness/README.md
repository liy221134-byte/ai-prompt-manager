# 交付就绪包

## 用途

工程方法种子资产包管「AI 该守什么规矩」，操作者训练包管「人怎么指挥 AI」；
这个包管的是**从代码到能访问的服务之间那段**——也就是换环境交付时，
哪些事必须提前判定、哪些东西必须提前写下。

它服务的是一个具体场景：本机用 AI 写完代码，推到公司仓库，过流水线，
最后落到客户给的一台服务器上（可能是内网、可能要摆渡），数据库是自建 MySQL 或 PostgreSQL。
这段路每一环都有一块「配置解决不了、必须补能力」的地方，不提前判定，到了现场才发现。

来源：本项目的 `docs/project-map.md` 第五步「环境差异」那张表（那份表自己标了「未验证假设」），
以及 2026-09-25 与豆包那次 CI/CD 与 MCP 预研的核对结果（核对记录见
`docs/v3-requirements-draft.md`）。

## 这个包不做什么

- **不碰部署执行**：怎么把服务跑起来仍然由流水线或服务器上的脚本负责，
  这个包只管「交付前该确认什么、该留下什么文档」。
- **不重复已有的两件事**：回滚的结构用工程包的 `PLAYBOOK-RELEASE-001`（发布、回滚与恢复），
  数据库迁移的做法用 `CASE-MIGRATION-001`（迁移历史与对齐）。这个包只补它们没覆盖的
  交付段：环境本身的登记、摆渡与部署手册。

## 当前版本

- 版本：`0.1.0`
- 状态：`candidate`，在一个真实交付项目里跑过一轮、按现场反馈改过之后，再升 `active`
- 可信度：`hypothesis`——**这个包还没有在真实交付里用过**，现在的内容是从文档和一次
  预研推出来的。跑完一轮不修正，等于白写。

## 怎么装进产品

```bash
npm run pack:delivery
```

生成的 `delivery-readiness.pack.json` 在产品的「公共资产 → 更多 → 导入规则包」里导入。

## 怎么用

1. 立项或换环境时，按 `MTH-DLV-001` 把目标环境的差异逐项判定，产出那份清单。
2. 每个目标环境填一份 `TPL-DLV-001` 环境档案（一台机器一份，凭据只写引用名）。
3. 交付前用 `TPL-DLV-002` 把部署手册写完；回滚那节套工程包的发布与回滚
   （`PLAYBOOK-RELEASE-001` 与 `templates/engineering/release-rollback.md`）。
4. 交付完成后，把现场和清单对不上的地方改回这个包——这一包的价值来自现场反馈，
   不来自一次写得多全。
