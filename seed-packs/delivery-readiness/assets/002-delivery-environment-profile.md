# 交付环境档案模板

## 核心结论

**一台目标环境一份档案。** 它回答的是「我到底在往哪里交付」：
怎么进、跑的是什么版本、上一次谁动了它、出问题找谁。

没有这份档案的时候，这些答案散在聊天记录、几个 `.env` 和记忆里，
换个会话就得重新问一遍，也说不清「线上现在到底是哪一版」。

## 使用条件

- 第一次往一台机器上交付之前。
- 环境换代、搬迁、或者换了运维接手人时更新。
- 每次交付完成后，至少回来更新「当前版本」和「上一次交付」两行。

## 不适用场景

- 只在本地跑的开发机不用建档案。
- 托管平台上的预览环境不用逐台建，建档的是**要长期存在**的那几台。

## 一条红线

**档案里不写任何密码、密钥、连接串。** 只写「用哪个引用名」——
本体的存放位置由人记住或另行约定。这份档案会进资产库、会进备份、
也可能被贴进对话里，写进去的密钥就等于泄露了。

## 档案结构

### 一、基本

| 字段 | 填写要求 |
| --- | --- |
| 环境名称 | 自己认得出的名字，例如「客户 A 生产」「公司测试机」 |
| 环境类型 | 全托管／自建云主机／公司托管／内网隔离 |
| 谁维护 | 客户运维、公司运维还是我；出问题先找谁 |
| 网络边界 | 能不能从外面连进来；要不要过堡垒机或网闸；有没有 VPN |

### 二、怎么进

| 字段 | 填写要求 |
| --- | --- |
| 访问方式 | 直连 SSH、跳板机、平台控制台，还是只能现场 |
| 登录账号 | 用户名和角色，例如 `deploy`（只用于部署，不给 root） |
| 凭据引用名 | **只写名字**，例如「凭据管理器里的 clientA-deploy」 |
| 落地目录 | 服务装在哪个路径，日志在哪个路径 |

### 三、跑什么

| 字段 | 填写要求 |
| --- | --- |
| 当前部署版本 | 现在这台机器上是哪个版本号 |
| 回滚目标 | 上一版是什么、怎么切回去 |
| 运行方式 | Docker Compose、裸进程、还是平台托管 |
| 数据库 | 类型与版本、库名、只读账号与写账号分别是谁在用 |
| 迁移状态 | 已执行到哪个迁移编号 |

### 四、记录

| 字段 | 填写要求 |
| --- | --- |
| 上一次交付 | 时间、版本、谁做的、结果 |
| 已知问题 | 现在还带着的毛病，以及绕法 |
| 变更历史 | 重装、搬迁、换证书这类大动作各记一行 |

## 最低内容

第一次建档至少填这七项，其余可以标「待补」，但要写清补的时间和负责人：

1. 环境类型。
2. 网络边界（能不能从外面连进来）。
3. 访问方式与登录账号。
4. 凭据引用名。
5. 当前部署版本与回滚目标。
6. 数据库类型、库名、账号角色分工。
7. 谁维护。

## 失败模式

- 把密码或密钥直接写进档案。
- 只写「生产服务器」，不写具体是哪台、怎么进。
- 交付完不回来更新版本号，档案很快变成错的，比没有更危险。
- 不写谁维护：出事时现场没人认领。

## 验证证据

- 填好的环境档案本身。
- 一次照着档案进机器、确认版本号对得上的记录。
- 换环境时的差异清单（`MTH-DLV-001` 的产出）。
