# 客户环境部署手册模板

## 核心结论

**部署手册是写给「不是你、也不能问你」的人看的。** 交付那天要么是客户运维照着做，
要么是三个月后的你照着做。手册的目的只有一个：照着走能装上、能验、能退回去。

## 使用条件

- 每次往客户环境交付前写一份，交付时带上。
- 内网摆渡场景必须先写完手册再打包，包里带的是手册的定稿版。

## 不适用场景

- 自己云上的日常发版用不上，那是流水线的事。
- 一次性演示环境可以只写「怎么起、怎么停、找谁」三行。

## 手册结构

### 一、这次交付什么

- 项目与版本号：
- 这次包含哪些改动：
- 涉及数据变更：有／没有（有就列出迁移文件编号和执行顺序）
- 目标环境：（引用环境档案 `TPL-DLV-001` 里的名字，不在这里重抄地址和账号）

### 二、交付前必须完成

- [ ] 环境适配体检做完，判成「要补能力」的项全部落地（`MTH-DLV-001`）
- [ ] 工程检查通过（类型检查、自动化测试、代码检查、生产构建）
- [ ] 数据库迁移已在隔离环境跑过一遍
- [ ] 备份已生成，并且确认备份文件能打开
- [ ] 回滚目标与回滚方式写清楚（套 `PLAYBOOK-RELEASE-001`）
- [ ] 制品包清单与校验和对过，文件不缺

### 三、制品怎么进去

| 字段 | 填写要求 |
| --- | --- |
| 进去的方式 | 摆渡、私服拉取、还是现场直接拷 |
| 制品清单 | 逐个文件写清，附校验和 |
| 进去之后放哪 | 绝对路径 |
| 谁有权限放 | 客户运维还是我 |

### 四、部署步骤

| 顺序 | 动作 | 谁执行 | 预期结果 | 失败怎么办 |
| --- | --- | --- | --- | --- |
| 1 |  |  |  |  |
| 2 |  |  |  |  |

要求：每一步都要写「预期能看到什么」。写不出预期结果的步骤，等于没写。

### 五、数据库迁移怎么执行

- 迁移脚本是仓库里的哪几个文件：
- 执行人：
- **执行前先备份**，备份文件放哪、怎么确认能用：
- 迁移失败怎么办（回滚 SQL 在哪 / 或者向前修复）：
- **红线：不让智能体直接连生产库改表**，只走仓库里的迁移文件。

### 六、部署后验证

- [ ] 服务起来了（怎么看：端口、容器状态、健康检查地址）
- [ ] 登录流程正常
- [ ] 本次改动的功能走一遍（逐条列出「点什么、看到什么」）
- [ ] 关键数据读写正常
- [ ] 日志里没有新的报错

### 七、出事怎么办

- 回滚目标版本与回滚步骤：套 `PLAYBOOK-RELEASE-001` 与
  `templates/engineering/release-rollback.md`
- 数据要不要跟着退、退到什么程度：
- 找谁：客户运维 / 我 / 厂商（写清联系方式在哪，不写具体号码）

### 八、交接清单

- [ ] 环境档案更新到最新版本号和迁移编号
- [ ] 手册定稿归档，现场改过的部分回填
- [ ] 待办与已知问题交接清楚

## 失败模式

- 手册里直接写明文密码。
- 只写命令不写「预期看到什么」，执行的人分不清成功还是卡住。
- 迁移那节没写备份，出问题两头空。
- 回滚只写「有问题再说」，没写回到哪个版本。
- 交付完不更新环境档案，下一次交付从错的起点开始。

## 验证证据

- 手册本身，加上一份照着它走完的部署记录。
- 客户运维照着手册独立装过一次——这是最硬的证据。
- 现场发现和手册对不上的地方，已经回填。
