# 项目规模与复杂度分级

## 核心结论

项目级别不能只看预算或页面数量。应综合业务关键性、模块数量、外部集成、
数据敏感性、团队规模、可用性要求和合规要求判断。

推荐使用四级画像：

| 级别 | 典型特征 |
| --- | --- |
| 个人工具 | 少量用户、低风险、可快速重建、无需强合规 |
| 中型产品 | 有账号、数据库、备份和发布要求，模块数量有限 |
| 大型平台 | 多模块、多团队、多系统集成、强非功能要求 |
| 监管或高敏项目 | 涉及重要数据、云网隔离、等保、审计和可信计算 |

## 使用条件

- 在任何路线选择、架构设计和工期承诺之前。
- 项目范围发生变化时重新评估。
- 同一个项目中不同模块可以具有不同风险等级。

## 不适用场景

- 不能把分级当作技术炫耀或团队扩编理由。
- 不能仅因为使用微服务、AI 或区块链就自动判定为大型项目。
- 不能把预算规模直接等同于工程复杂度。

## 判断步骤

1. 列出业务关键性和故障影响。
2. 统计独立业务模块与子系统数量。
3. 统计外部系统和历史系统集成数量。
4. 识别数据分级、个人信息和跨域流通要求。
5. 明确团队人数、驻场要求和交付周期。
6. 明确可用性、性能、恢复、审计和合规目标。
7. 判断是否属于多个团队或多个供应商协作。

## 失败模式

- 用“个人工具”方法管理省级平台。
- 用“大型平台”方法过度建设个人工具。
- 只按合同金额安排人员和治理。
- 忽略外部接口和数据安全带来的复杂度。

## 验证证据

- 项目画像记录。
- 复杂度评分和判断依据。
- 对应路线、质量等级和阶段门禁。
