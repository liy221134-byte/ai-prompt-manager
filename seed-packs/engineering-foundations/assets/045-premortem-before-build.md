# 动手前先做一次事前验尸

## 核心结论

排期、定档、开工之前，先做一次**事前验尸**：假定「14 天后这个版本已经失败了」，倒推为什么。

风险分三类，缺一类就等于没做：

| 类别 | 是什么 |
| --- | --- |
| **真问题** | 我自己看得见、有依据或合逻辑的风险——要动手处理 |
| **纸老虎** | 别人担心、但我不信的——写下来对齐，不往这里投资源 |
| **房间里的大象** | 没人说出口、也没人去验证的那种担心——**这一类价值最高**，上线前必须去查 |

三条硬话：

1. **拿不准就默认当「真问题」**——早处理比漏掉便宜。
2. **每条上线阻断项要有「缓解动作 + 负责人 + 截止日」**，三样缺一样就等于没分派。
3. **上线（或交付）前 2～3 周再看一遍**，确认缓解措施还在轨。

## 使用条件

- 定档、承诺工期、动手实现之前。
- 一个版本接近上线或交付时（复核那一遍）。

## 不适用场景

- 一次性的小改动、已经验证过的局部调整。
- 纯文档、纯文案改动。
- 拿「纸老虎」当工作重点去投入资源。

## 判断步骤

1. 先把那份计划、需求文档或实现规格读一遍——没有它就没有可验尸的对象。
2. 想「14 天后已经失败了，发生了什么」。
3. 逐条列出来，按三类归位；某一类真的没有就写明「没有」，不要空着。
4. 真问题再分三档：**上线前必须解决** / **30 天内跟进** / **观察**。
5. 每条「上线前必须解决」补齐缓解动作、负责人、截止日。
6. 结果写进已有的设计文档或验收清单里——不额外造一份新文档。
7. 上线前 2～3 周复核一遍，写清哪条仍在轨、哪条变了。

## 失败模式

- 只列自己看得见的问题，没有「房间里的大象」这一类。
- 把风险写成一句口号（「性能可能有风险」），没有缓解动作和截止日。
- 反过来：所有担心都写成「纸老虎」而不写理由——那是自我安慰，不是分类。
- 当成一次性仪式，做完再也没人看。
- 用「我们有备份」这类没验过的说法当缓解动作。

## 验证证据

- 三类风险各有条目（或写明「没有」）。
- 每条上线阻断项都带缓解动作、负责人、截止日。
- 上线前那次复核的记录：哪条仍在轨、哪条变了。
