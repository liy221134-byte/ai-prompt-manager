# 梯子前的外部查询：先问外面有没有轮子

## 核心结论

动手写代码之前，先问一句"这个方向 / 这个功能，外面有没有成熟的轮子"。有，就优先复用或借，而不是闷头自己造。这一条把"不重复造轮子"从骨架期（定技术栈用 Vben+若依这类底座）下沉到了功能开发期：每做一个模块功能，都先去生态里找现成方案。它接在七层梯子之前，是梯子的"第 0 步"。

两种口径并存（先观察命中效果，再决定是否固化）：

- **大迭代口径**：每次进大迭代，主动启动一次外部查询——去 GitHub / npm / MCP registry / 官方文档搜这个方向的成熟方案。
- **功能开发口径**：每个功能先判"是不是已被成熟解决的通用问题"，是才启动外部查询；产品特有逻辑（如本产品线索 3 这类）不搜。

搜到候选后按 L1 一手源核：维护状态、许可证、有没有生产案例；想引入仍走 L5 同意门（引入第三方库须明确同意）。这既接住"胶水编程法"的思路，又用 L5 守住"不随便加依赖"。

## 使用条件

- 启动一个大迭代、要选方向或技术栈时（大迭代口径）。
- 开发一个具体功能、且判断它是通用问题时（功能开发口径）。

## 不适用场景

- **产品特有逻辑**：只有我们这个产品才有的流程 / 规则（如线索 3 的采集回流），外面没有对应轮子，不搜，老老实实走梯子复用项目内 + 零依赖。
- **项目内已有可复用实现**：直接走梯子的第 2 / 5 阶（复用既有代码、已装依赖），不必外搜。
- **纯文档、纯内容改动**：不涉及功能开发。

## 判断步骤

大迭代口径：

1. 列清这一轮要做的方向 / 技术点。
2. 对每个点，去 GitHub / npm / MCP registry / 官方文档搜一遍成熟方案，记录候选与版本。
3. 按 L1 核候选：是否还在维护、许可证是否允许我们的交付形态（含内网 / 信创）、有没有真实生产案例。
4. 评估通过且确实省事 → 走 L5 引入；否则自己写最小胶水。

功能开发口径：

1. 动手前先判：这个功能是不是"已被成熟解决的通用问题"？
2. 是 → 走上面大迭代口径的第 2–4 步。
3. 不是（产品特有）→ 跳过外部查询，直接走七层梯子。

## 失败模式

- **该搜不搜**：自己造了一个轮子，事后发现生态里早有成熟方案，白做还更难维护。
- **搜了不核 L1**：拉了个年久失修或许可证不兼容的库，埋下交付 / 合规坑。
- **随手拉库违背 L5**：没经你同意就加依赖，增加内网 / 信创交付成本（胶水编程法默认"能借就借"，对我们的成本敏感产品要加这道闸）。
- **什么都搜**：每个琐碎功能都外搜，反而拖慢节奏——所以功能级要"先判通用问题"。

## 验证证据

- 后续几轮真实开发中，对"外部查询"两口径的实际命中做记录：是真搜到了可复用轮子，还是大多判定为产品特有逻辑而跳过。
- 记录进 rule-hits.md 的命中台账（按可信度三档），够了再决定固化成常驻还是收紧。
