# 技术档案模板

## 核心结论

技术档案把项目的技术选择一次写清：约束是什么、选了哪些技术、禁止用什么、什么条件下
可以替代、哪些偏离必须写决策记录。它是项目的一级档案，不是几条零散规则。

## 使用条件

- 项目立项时创建，作为技术选型的落地载体。
- 更换运行环境、换技术、可用性目标或维护人手变化时更新。
- 把一个项目的资产导入新项目时，作为默认技术档案模板。

## 不适用场景

- 一次性原型可以只填语言、运行环境和数据存放三项。
- 简化不等于留空：没要求也要写"暂无要求"和原因。
- 技术档案不是技术栈清单，缺少禁止项和替代条件时不算填完。

## 档案结构

| 字段 | 填写要求 |
| --- | --- |
| 项目规模 | 个人工具、中型产品、大型平台或监管高敏，以及判断依据 |
| 运行环境 | 云托管、内网自建或物理隔离；是否允许依赖公网服务 |
| 预算约束 | 可接受的持续成本上限和触发复核的条件 |
| 数据敏感度 | 数据类型、是否含个人信息、是否可以出内网 |
| 可用性三个数字 | 可用性档位、恢复时间目标、恢复点目标；只有对外承诺才提高档位 |
| 默认技术栈 | 如果没有特殊约束，项目按什么技术起步 |
| 已选技术栈 | 实际选择，逐项对应上面推导出的能力要求 |
| 禁止使用的技术 | 明确不能引入的组件或做法，以及原因 |
| 允许替代的条件 | 什么情况下可以换实现，替换的代价和边界 |
| 需要决策记录的偏离项 | 偏离默认选型的每一项，附决策记录编号 |
| 维护责任 | 谁维护、维护到什么程度、超出边界时交给谁 |
| 关联技术规则与决策 | 相关规则资产和决策记录的标识 |

## 最低内容

重写级或立项就必须定死的项目，档案至少要有七项：

1. 项目规模。
2. 运行环境。
3. 数据存放位置。
4. 主语言与框架族。
5. 可用性三个数字。
6. 禁止使用的技术。
7. 维护责任人。

其余字段可以标注"待补"，但要写明补的时间和负责人。

## 失败模式

- 只写用了什么，不写为什么用。
- 换了运行环境却不更新档案，实际打法和档案不一致。
- 偏离默认选型不写决策记录。
- 只列技术栈，没有禁止项、替代条件和维护责任。
- 维护责任人空缺，出问题时没人认领。

## 验证证据

- 填写完整的技术档案本身。
- 与偏离项对应的决策记录。
- 换环境时的差异对照表。
- 可用性目标与恢复演练记录。
