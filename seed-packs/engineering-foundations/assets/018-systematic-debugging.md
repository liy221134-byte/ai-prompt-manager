# 系统化调试：先复现，再定位根因

## 核心结论

改 bug 的顺序比改得快更重要：**先复现，再定位根因，然后最小修复，最后回归同类路径**。
跳过复现直接动手，等于在猜；猜中的那次是运气，猜不中的那次会顺手改坏别的地方，
几天后换个路径又冒出来。

## 使用条件

- 任何"能观察到、但还没解释清楚"的行为异常，包括报错、卡住、数据不对、结果时好时坏。
- 用户报的问题、AI 自己发现的问题、发布后暴露的问题，都走同一条流程。
- 一眼可见的一行笔误可以压缩成两步：先复现确认，再补回归检查。

## 不适用场景

- 需求本身没定清楚：那是需求问题，先回到「需求边界」澄清，不当作 bug 修。
- 本地环境复现不出来、线上偶发的：先补观测和日志（第 1 步的变体），不要靠猜改代码。
- 影响面已经扩大、正在止血：先按发布回滚或故障演练处置，止血后再回到这条流程。

## 四阶段流程

1. **复现**：把"怎么让它再出现一次"写清楚——操作步骤、用到的数据、环境、报错原文。
   复现不了就先加观测，不动业务逻辑。
2. **定位根因**：先搜这个函数的**全部调用方**，再决定改哪一层；找到共享函数一次改对，
   不只补报告里提到的那一条路径。结论要能解释"为什么之前会那样"。
3. **最小修复**：只改根因那一处；顺手重构、顺手加抽象留到单独一次提交。
4. **回归**：补一条能挡住同类问题的检查（优先自动化测试，不好测就写手工检查步骤），
   再按交付门跑一次检查，确认别的路径没被打坏。

每一步都留下可复查的东西：复现步骤、根因结论、改动的文件和检查结果。

## 失败模式

- 没复现就改：改完"好像好了"，换个路径又出现。
- 只改报告提到的那条路径，没搜全部调用方：同一个 bug 在别处还在。
- 把"加日志、加 try/catch、加空值判断"当成修复：症状盖住了，根因还在。
- 修完不回归：修好的地方好了，别的地方坏了，下次才发现。
- 让 AI 改 bug 时只说现象、不给复现步骤：AI 只能猜，越改越远。

## 验证证据

- 复现步骤和根因结论（写进交付说明或验收记录）。
- 挡住同类问题的检查（测试用例或手工检查步骤）。
- 交付门检查的通过结果。

首次采用后回填：一次真实 bug 的复现记录、根因结论和回归检查，
用于把可信度从 `hypothesis` 升到 `provisional`。
