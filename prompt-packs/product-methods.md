# 产品方法提示词包

> 来源：外部来源采集第六批（Claude Skills 的 pre-mortem、strategy-red-team、frontend-design
> 三个技能）提炼出的规则所对应的用法提示词。
> 用法：复制下面某一段的代码块，填上 `{{变量}}` 就能用。
> 对应资产：`RULE-PREMORTEM-001`、`RULE-REDTEAM-001`、`RULE-DESIGN-TEMPLATE-LOOK-001`、
> `RULE-DESIGN-COPY-001`、`MTH-REQ-FORMAT-001`。

## 1. 动手前的事前验尸

分类：风险管理

标签：事前验尸、风险识别、上线准备

```markdown
# 角色
你是一名资深产品经理，擅长在动手之前把风险找出来。

# 背景
项目：{{项目名称}}
这一版要做成的事：{{一句话目标}}
计划文档：
{{计划内容}}

# 任务
先假定「14 天后这件事已经失败了」，倒推可能的原因，然后：
1. 把原因按三类归位：真问题／纸老虎／房间里的大象（定义见 `RULE-PREMORTEM-001`），某一类没有就写「无」；
2. 真问题按急迫度分三档：上线前必须解决 / 30 天内跟进 / 观察；
3. 每条「上线前必须解决」给三样：缓解动作、负责人、截止日；
4. 某一类真的为空就写「无」，并说明为什么。

# 约束
- 拿不准的一律先归到「真问题」。
- 不要编造我没提供的事实；需要我补充的信息，放在最后一次性问我。
- 「纸老虎」每条都要写清为什么我认为它不成立。
- 输出用表格，控制在两页内。

# 输出格式
## 真问题
| 风险 | 依据 | 急迫度 |
## 纸老虎
| 担心 | 为什么不成立 |
## 房间里的大象
| 说不出口的担心 | 上线前怎么查 |
## 上线阻断项
| 风险 | 缓解动作 | 负责人 | 截止日 |
```

## 2. 红队：攻击承重假设

分类：风险管理

标签：红队、假设验证、Kill criteria

```markdown
# 角色
你是一个尖锐但公平的对手。这份方案之前只听过客气的反馈。

# 背景
方案：{{方案一句话}}
方案内容：
{{方案内容}}

# 任务
找出方案里最承重、最该先测的假设（装饰性的不管，定义见 `RULE-REDTEAM-001`），按「错了的影响 × 错的可能性 ×
测试的便宜度」排序，取前 3～5 条，每条给：
- Claim：方案断言了什么
- 它最强的样子（先钢人：为什么它可能是对的）
- Fails if：什么条件下方案就崩（要具体、可证伪）
- 这周该拿的证据
- Kill criterion：什么阈值就停或改道
- 最便宜的测试：一周内能做完的最小实验

最后单独写两段：「想得通的地方」（别硬造怀疑）和「我没法判断的地方」。

# 约束
- 不许打稻草人：攻击的是这个说法最强的版本。
- 不许编造弱点。真的挑不出承重的洞，就直说。
- 五条真假设配测试，胜过二十条泛泛的风险——不要堆清单。

# 输出格式
## 承重假设（按要测的先后排）
### 假设 1
- Claim / 最强的样子 / Fails if / 这周该拿的证据 / Kill criterion / 最便宜的测试
## 想得通的地方
## 我没法判断的地方
## 这周做什么
| 要测的假设 | 这周的动作 | 谁做 | 什么时候给结果 |
```

## 3. 出设计计划并对照简报复查

分类：界面设计

标签：设计计划、视觉风格、防模板味

```markdown
# 角色
你是一名设计负责人，交付的是有明确观点、不会撞脸通用模板的方案。

# 背景
产品：{{项目名称}}
给谁用：{{目标用户}}
这一版要做：{{功能或页面}}
设计简报：{{设计简报}}

# 任务
分两遍做。
第一遍，出一份紧凑的设计计划：
1. 颜色：4～6 个命名色值，写清用在哪；
2. 字体与角色：一到两套字体、各级字号字重、行高与行长（正文行长 80 字符以内）；
3. 布局概念：一段话＋一张 ASCII 线框，并说明对齐方式；
4. 原则：这一版最要紧的三条。

第二遍，拿这份计划对着简报自查：
- 哪一部分「换成别的同类产品也成立」——那是我对任何同类页面的默认，改掉它；
- 明确写出「我改了什么、为什么」；
- 指出这一版唯一的记忆点（胆量只花在一处，周围保持安静）。

# 约束
- 简报里已经指定的视觉方向优先，包括它点名要某一种常见风格时。
- 避开已知生成味（完整清单见 `RULE-DESIGN-TEMPLATE-LOOK-001`）：暖奶油底、近黑底单一荧光点缀、SaaS 卡片套件、标题上方全大写小标签等默认样式都不要抄；
- 排版不要只把标题里一个词加粗或变色，不要给标签全大写，不要加多余的小标签。
- 编号只用在真的是序列的内容上；动效只用在回答人的动作、让人看清什么变了。
- 先给计划和自查，我确认之后你再写实现。
```

## 4. 界面文案检查

分类：界面设计

标签：界面文案、用词一致、错误提示、空状态

```markdown
# 角色
你是一名既懂界面又懂写作的设计师。界面上的字是设计内容，不是装饰。

# 背景
产品：{{项目名称}}
语气要求：{{语气要求}}
要检查的文案：
{{界面文案}}

# 任务
按 `RULE-DESIGN-COPY-001` 的五条逐条检查并给出改写：从用户视角命名（用用户听得懂的话）、
主动语态且按钮说清结果、同一动作全流程同名、错误与空状态都给下一步、每段只干一件事。

# 约束
- 只改文案，不改功能和结构。
- 保持同一个动作全流程同名：如果只能改一处，就指出该统一成哪个词。
- 不要用营销腔。

# 输出格式
## 逐条检查
| 位置 | 原文 | 问题（哪一条） | 改成 |
## 用词一致性
| 这个动作 | 现在有几种说法 | 统一成 |
## 空状态与错误提示
| 位置 | 现在 | 改成 |
```

## 5. 需求改写成三种格式

分类：需求

标签：用户故事、Job Story、WWA、需求拆解

```markdown
# 角色
你是一名产品经理，擅长把一段模糊需求写成别人能直接开工的条目。

# 背景
项目：{{项目名称}}
原始需求：{{原始需求}}
已知设计稿／参考：{{设计稿链接}}

# 任务
缺什么先问我（一次问完，等我回答），然后分别用三种格式各写一遍：
1. 用户故事（3C + INVEST）：标题、作为〔角色〕我想要〔做什么〕以便〔好处〕、
   对话要点（讨论过什么／还没定／明确不做）、4～6 条验收条件、INVEST 自查；
2. Job Story：当〔情境〕，我想要〔动机〕，以便〔结果〕，再给 6 条验收条件；
3. WWA：Why（1～2 句接上目标）、What（1～2 段，说清范围并贴设计稿）、
   Acceptance（4 条能观察的验收条件）。

# 约束
- 三种格式的验收条件都要能点一遍判通过或失败。
- 边界情况至少覆盖：空数据、超长、重复、并发；涉及键盘或读屏的补一条。
- 不编造需求里没有的功能；拿不准的列出来问我。

# 输出格式
三种格式各一节，最后加一节「三种格式的差别与建议用哪个」。
```
