# 新项目启动提示词

## 使用方式

1. 创建一个新的空项目文件夹。
2. 在 Codex 中打开这个文件夹。
3. 复制下面的提示词，把 `{{...}}` 内容替换成你的项目信息。
4. 先让 AI 建立项目规则和基础文档。
5. 确认项目范围后，再开始开发第一个功能。

## 可直接复制的提示词

```text
我是产品经理，不直接阅读代码。你负责协助我完成这个新项目。

在开始写功能代码之前，请先完成项目初始化，并遵守以下核心原则。

【项目信息】
项目名称：{{项目名称}}
一句话目标：{{这个项目解决什么问题}}
目标用户：{{谁使用这个产品}}
当前阶段：{{原型 / MVP / 内测 / 已上线}}
核心流程：{{用户完成核心任务的主要步骤}}
本阶段要做：{{本阶段范围}}
本阶段不做：{{明确排除的范围}}
验收标准：{{什么结果算完成}}

【技术底座】
技术栈：{{前端 / 后端 / 数据库 / 部署方式；还没定就写「待定，先给我候选和取舍」，不要默认替我选}}
不要从零开发的功能（用现成模板或已有实现，不要让 AI 重写）：
1. {{例如：登录、注册、密码重置}}
2. {{例如：角色与菜单权限}}
3. {{例如：用户管理、操作日志}}
4. {{例如：文件上传下载}}
{{还有哪些现成能力要直接用，继续往下列；不确定就写「待确认」，先让 AI 列清单再问我}}

【与我交互的规则】
1. 开始修改前，先说明准备改什么、为什么改、用户可见效果和影响范围。
2. 遇到会影响数据结构、产品行为、外部依赖、成本或安全性的决定，必须先问我。
3. 普通实现细节可以自行决定，但要解释。
4. 重要代码块和复杂逻辑写中文注释，不给每一行代码加注释。
5. 每次完成后说明修改了哪些文件、每个文件改了什么、如何验收、有什么风险。

【开发规则】
1. 先明确需求和验收标准，再写代码。
2. 一次只完成一个清晰目标，不进行无关重构。
3. 先复用现成实现：模板自带功能、标准库、框架自带、已装依赖，都不重复写。
4. 未经确认，不引入第三方依赖、外部服务或部署环境。
5. 不提交带 TODO 的占位功能和无法运行的代码。
6. 所有用户可见文案使用中文。
7. 功能必须覆盖正常、空数据、错误和边界状态。
8. 修改后执行代码检查、类型检查、测试和构建验证。

【数据与安全规则】
1. 未经确认，不删除文件，不删除或覆盖用户数据。
2. AI 生成或修改内容前必须先预览，不能静默覆盖用户内容。
3. API 密钥、密码和敏感信息不得写入前端或提交到 Git。

【Git 规则】
1. main 分支始终保持可运行。
2. 功能开发从 main 创建功能分支。
3. 一次提交只处理一个清晰目标。
4. 提交信息使用 feat:、fix:、docs:、test:、chore: 前缀。
5. 每个稳定阶段创建版本标签。
6. 未经确认，不创建远程仓库、不推送、不部署，不执行破坏性 Git 操作。

【本次初始化任务】
暂时不要开发业务功能，请先完成：
1. 在项目根目录创建 README.md，说明项目目标、协作原则、开发原则、交付原则、Git 原则和固定工作流程。
2. 在项目根目录创建 AGENTS.md，写入给 Codex 执行的强制规则。
3. 创建 docs/product-brief.md，记录产品定位、用户、核心流程、范围和验收标准。
4. 创建 docs/roadmap.md，拆分从原型到生产版本的阶段路线。
5. 创建 docs/acceptance/，为当前阶段建立验收清单。
6. 检查当前目录是否已经是 Git 仓库；如果没有，等待我确认后再初始化。
7. 把本次确定的技术底座写进 `docs/decisions/` 第一条决策记录：选了什么、放弃了哪些候选、为什么。

请先告诉我：
1. 你准备创建哪些文件和目录
2. 每个文件的作用
3. 当前项目信息中还有哪些不清楚的地方
4. 初始化完成后的验收方式

暂时不要创建文件，等我确认后开始。
```
