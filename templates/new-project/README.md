## 我的角色

我是产品经理，不直接阅读代码。我负责定义产品范围、确认验收标准、测试用户流程和决定是否发布。技术方案、代码实现和工程检查由 AI 协助完成。

## 核心协作原则

1. 开始修改前，先说明准备改什么、为什么改、修改后的用户可见效果，以及可能影响的功能。
2. 重要代码块和复杂逻辑写中文注释，不给每一行代码加注释。
3. 未经明确确认，不删除文件、不删除数据、不执行破坏性 Git 操作。
4. 未经确认，不引入新的第三方依赖、外部服务或部署环境。
5. 优先修改指定范围，不进行无关重构。
6. 遇到会影响数据结构、产品行为、成本或安全性的决定，必须先询问我。
7. 普通实现细节可以自行决定，但要解释结果。
8. AI 生成或修改内容时不得静默覆盖用户数据，必须先预览并让我确认。

## 开发原则

- 先明确需求和验收标准，再开始写代码。
- 一次只完成一个清晰目标。
- 优先使用简单、稳定、容易维护的方案。
- 功能要覆盖正常流程、错误状态、空状态和边界情况。
- 不提交带 `TODO` 的产品占位功能。
- 不提交无法运行的代码。
- 所有用户可见文案使用中文。
- 每次修改后至少执行一次代码检查、类型检查和构建验证。
- 有测试时，优先用自动化测试覆盖核心逻辑。

## 交付原则

每次完成后必须说明：

1. 修改了哪些文件。
2. 每个文件改了什么。
3. 用户可见效果是什么。
4. 如何预览和验收。
5. 有哪些未完成事项或已知风险。

## Git 原则

- `main` 分支始终保持可运行。
- 功能开发从 `main` 创建独立功能分支。
- 一次提交只处理一个清晰目标。
- 提交信息使用 `feat:`、`fix:`、`docs:`、`test:`、`chore:` 前缀。
- 每个稳定阶段创建版本标签，例如 `v0.1.0`。
- 未经确认，不创建远程仓库、不推送代码、不部署生产环境。
- 未经确认，不执行 `git reset --hard`、强制推送或删除 Git 历史。

## 固定工作流程

1. 我描述目标、范围和验收标准。
2. AI 先阅读项目文档并给出实施计划、风险和影响范围。
3. 我确认方案后，AI 再开始修改。
4. AI 小步实现，并在完成后运行检查。
5. 我从用户角度验收，AI 修复发现的问题。
6. AI 提交 Git 版本并给出变更清单。
7. 阶段完成后合并到 `main` 并创建版本标签。
