# 项目方法正本

> 这份文件是**本项目的做事方法正本**：三道门判据、交付门细则、防过度设计梯子、技能使用规则的正文都在这里。
> `AGENTS.md` 只留指针与读取时机，**不复制正文** —— 复制必然漂移。
>
> 它在项目初始化时从起步模板复制过来，**复制即脱钩**：此后本项目自持，改它不用回头问母本。
> 母本更新**不会**自动回灌到已经在跑的项目 —— 这是有意的，改一个跑着的项目要单独决定。

**总纲一句话：一个版本、一份文档、三道门。** 本节覆盖三道门里的**需求门与设计门**；
交付门的判据在 `AGENTS.md` 的「交付门」与本文第三节。

---

## 一、需求门

- 需求模糊、涉及新方向或存在多种做法时，先对话确认，不写代码。
- 需求清晰时直接进入设计门。

---

## 二、设计门

设计门有**两条并行的线**：技术设计和界面设计。两条都判过（走完或判定不触发），才进交付门。

### 技术设计线

- 触发条件：满足任意一条时，先写一份《设计 + 任务清单》文档，等产品负责人确认后再开发。
  1. 会留下长期痕迹：数据表、字段、迁移、恢复或回滚语义。
  2. 会改变对外约定：接口输入输出、优化与合并规则、鉴权与数据隔离。
  3. 会引入外部依赖、外部服务或持续成本。
- 不触发：界面、文案、样式、局部实现调整，以及已有测试覆盖的重构。这些只需在动手前用
  自然语言说明改什么、为什么改、影响哪些文件、怎么验收。
- 这份文档放 **`docs/specs/`**，**那里是设计文档的唯一正本**：不要再开第二个规格目录，
  也不要另起一套计划文档体系。
- 文档只写决定，只保留四块内容：
  1. 做什么 / 不做什么。
  2. 数据和产品行为影响。
  3. 验收标准，每条都能用一次测试或一次手工验证判定。
  4. 任务顺序，以及每个任务改哪些文件。
- 不写自检章节和覆盖率对照表 —— 自己证明自己的内容无效。
- 只写决定，不写实现步骤、完整 SQL 和成段代码，那些属于实施过程。
- 篇幅以「把事情说明白」为准，在此基础上尽量精简。允许为了说清楚而写长，不允许为了
  写短而留下含糊表述：没说清楚的地方，后续实现会自行脑补，比文档长更危险。
- **收口**：一版交付时回看那一版的设计文档。规格已不成立、或已被实现推翻的，按「设计偏差」
  单独列出，由产品负责人决定改设计还是改实现；**裁定后回写规格**（改设计文档或改验收标准），
  并注明哪一份是当前有效的。

### 界面设计线

- **先判档，再决定做多少。** 判档依据：这一版有没有新的用户可见界面；前端底座是不是
  已经把布局和组件定死。
  1. **定稿档**：首次定整体风格，或要改整体风格——出设计稿。
  2. **沿用档**：已有风格，这版只加页面或交互——不出稿，按已有风格做，验收只查风格一致性。
  3. **配置档**：界面锁在固定前端底座里（中后台模板这类）——不出稿，
     出「主题与布局配置清单」，只补底座没有的页面。
- 三档都不出稿的例外：改文案、调间距、换图标、单个组件的局部样式——直接改。
- 分寸按「够用」定，不追精致：固定 UI 风格，保证整个产品前端**风格一致**、交互体验顺；
  **把交互说清楚**，做简洁；水平线上拔高留给后面客户提定制化视觉需求时再做。
- 验收：定稿档按设计稿对比验收；沿用档和配置档查风格一致性。都先对齐视口与状态再比，
  别把缩放差异报成设计不一致。总体以**能用、好用**为主，风格新潮即可。
- 技术选型时如果选了会锁死界面的底座，写进技术档案：**接受界面设计自由度受限**，
  设计工序走配置档。
- 这条线和上面那条**并行**，不是串行：不必等技术设计定稿才开始设计，也不必等稿子
  画完才动手写代码。

## 三、交付门细则

每轮必做的动作（跑检查、交付说明四要素、「本次规则命中」一行、「本轮新增依赖／新增工具位」一行、收口）
留在 `AGENTS.md` 的「交付门」，不在这里重复。以下是做法细则：

1. 先写或更新测试，再写实现；验证失败时先用测试复现问题。
2. 做一轮独立自查，发现的问题直接修进当前任务的提交里，不额外制造 fix 提交。
3. 证据只记一处：同一次发现只写进验收清单或决策记录中的一处，其他文档放链接引用，不重复叙述。
4. 凡 AI 产出或外部输入，先用 schema（如 zod）校验再进业务逻辑；结构拿不准时显式停下来问，不让 AI 自己脑补。

## 四、写代码的规矩（防过度设计）

AI 默认会多写：加抽象、装依赖、顺手重构。动手写代码前，按顺序停在第一个成立的台阶上：

1. 这件事需要做吗？不需要就不做。
2. 项目里已经有能复用的实现吗？有就复用，不重写。
3. 标准库、框架自带的能做吗？能就用。
4. 平台原生能力能做吗（例如浏览器自带的日期选择）？能用就用。
5. 已经装过的依赖能做吗？能做就用。
6. 能一行写完吗？一行写完。
7. 以上都不成立，才写满足需求的最小实现。

**梯子前的一步：外部查询（胶水编程思路）。** 梯子判的是「项目里 / 依赖树里有没有现成」，
不覆盖「生态里有没有成熟方案」。动手前按两个口径启动一次外部查询：

- **大迭代口径**：每次进入一个大迭代（新版本 / 新子系统）时，先问「这个方向外面有没有轮子」，
  主动去成熟生态（GitHub / npm / 官方文档）搜一遍候选。
- **功能开发口径**：每次开发一个功能时，先判断「这是不是个已被成熟解决的通用问题」
  （拖拽、日期解析、表单、状态管理、图表、鉴权…）；是才启动外部查询，不是（产品特有逻辑）就不搜。

外部查询到的候选核一手源（维护状态、许可证、生产案例），评估通过想引入仍走 `AGENTS.md`
「数据与安全」第 2 条同意门；不引入或过度复杂就回到梯子写最小实现。

梯子是在看懂问题和整条链路之后才爬，不能用「简化」的名义跳过理解。

- 不加没人要的抽象、脚手架和依赖。
- 修 bug 按四步走：
  **先复现**（写清操作步骤、数据、报错原文；复现不了就先加观测，不改业务逻辑）
  → **定位根因**（先搜这个函数的全部调用方，改共享函数一次，不只补报告里提到的那条路径；
  结论要能解释「为什么之前会那样」）→ **最小修复**（只改根因那一处，顺手重构另开一次）
  → **回归**（补一条能挡住同类问题的检查，再按交付门跑一次检查）。
- 简化不许砍掉：校验、错误处理、安全、无障碍、防数据丢失和真实边界条件。
- 有意留下的简化，要在代码里注明它的上限和以后怎么升级。
- 非平凡逻辑留下一个能运行的检查；一行小改不强制写测试。
- 做完主动说明「这次省掉了什么」，不默默省。

两条边界优先于上面的规矩：

1. 设计门不变。涉及数据表、对外接口、新依赖时，仍然先写设计文档等确认，「先做最简版再问」不适用。
2. 删除规矩不变。删文件、删数据、删功能仍要先得到确认；「简化优先」只限本次任务自己新增或直接改动的代码。

## 五、技能使用规则

### 默认使用

- 需求模糊时：先把上下文和约束问清楚，再动手。
- 涉及逻辑、数据或接口时：先给出验收标准或测试。
- 交付前：实际验证一遍再报完成。

### 默认不使用

- 写计划／执行计划类技能：由《设计 + 任务清单》替代。
- 并行子代理：个人项目默认不启用，除非明确要求。
- 独立工作区（worktree）：串行开发时，**新功能**在项目目录内建功能分支；**修 bug
  不用单开分支**，直接在主分支上用 `fix:` 提交。多个会话并行时必须用独立工作区隔离，
  否则会出现提交落到别人分支上的情况。
- 合并前评审类技能：合并为交付门里的那一轮自查。

### 使用边界

- 只读取本次真正要用到的技能说明，不批量加载技能文件。
- 技能文档与 `AGENTS.md` 冲突时，按 `AGENTS.md` 执行，并在交付说明里指出冲突点。
