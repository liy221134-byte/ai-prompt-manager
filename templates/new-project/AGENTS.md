## 关于我

我是产品经理，不直接阅读代码。所有结论用中文说明，用变更清单和验收步骤让我理解结果。

## 规则分三层，读哪份按动作定

| 层 | 文件 | 性质 | 怎么生效 |
| --- | --- | --- | --- |
| 方法层 | `docs/method.md` | 三道门判据、交付门细则、防过度设计梯子、技能使用规则（正本） | **不自动注入**，按下面这张表在对应动作前主动读 |
| 项目层 | 本文件 | 本项目的规则与事实 | 每次会话自动注入 |
| 文档规范层 | `docs/DOCUMENT_SYSTEM.md` | 本项目文档组织规范（最小文档集合、AI 读取顺序、需求链路四段） | 动 `docs/` 前主动读 |
| 命中台账 | `docs/rule-hits.md` | 规则有没有真在起作用 | 每轮交付追加一节 |

**按动作的读取时机**：

| 接下来要做什么 | 先读 |
| --- | --- |
| 有新想法、需求模糊 | `docs/method.md` · 需求门 |
| 要改数据表 / 对外接口 / 引新依赖 | `docs/method.md` · 设计门（技术线） |
| 要动界面、定视觉方向 | `docs/method.md` · 设计门（界面线）；本文件「界面改动的验证」 |
| 要写代码 | `docs/method.md` · 写代码的规矩（防过度设计，含「梯子前的外部查询」） |
| 一版要收尾 | 本文件「交付门」；细则见 `docs/method.md` · 交付门细则 |
| 要提交、合并、推送 | 本文件「版本与提交」 |
| 在 `docs/` 下新增、移动、改名文档 | `docs/DOCUMENT_SYSTEM.md` |
| 记录这一轮的规则命中 | `docs/rule-hits.md` |

**一个取舍**：判据类只留指针（漏读的代价可控，正本随时可查）；**硬边界类保留现场可见的短句**
（删数据、写生产库、密钥、不可逆 Git 操作）—— 这类漏读的代价不可逆，不靠指针兜。

## 每次开始工作前

1. 先读 `README.md` 和 `docs/INDEX.md`（入口与阅读顺序）。
2. 涉及代码改动时，先看工程地图类文档定位要改的文件，再精读那几个文件，不要整篇读大文件。
3. **框架自带的规则也要读**（这条只在用 Next.js 的项目里成立，不是通用规则）：写 Next.js
   代码前先读 `node_modules/next/AGENTS.md`。它写明这个版本的 API、约定和目录结构都可能
   和训练数据不一样，要求先读它指向的文档再动手，并留意废弃提示。只引用那份文件，
   不把它的内容抄进来。
4. 动手前先用自然语言说明：准备改什么、为什么改、我会看到什么变化、可能影响哪些文件或功能。
5. 在 `docs/` 下建、移、改文档前，先读 `docs/DOCUMENT_SYSTEM.md` 确认放哪、叫什么。

## 交付门

判据与做法细则（先写测试再写实现、独立自查、证据只记一处、AI 产出先过 schema）在
`docs/method.md` 第三节。这里只列**每轮必做的动作**：

1. **按档位跑检查，报真实结果**，不能只说「应该没问题」：
   - 日常任务：`{{日常检查命令，例如 npm run check:fast}}`
   - 合并或推送前：`{{完整检查命令，例如 npm run check}}`
   - 纯文档、纯内容改动可以只跑测试，但要说明实际跑了什么。
2. **交付说明四要素**：改了哪些文件、每个文件改了什么、如何预览或验证、未完成事项和风险。
3. **固定一行「本次规则命中」**：没有就写「无」，有就写清违反了哪条、发生了什么。
   命中只有一种口径——本文件或 `docs/method.md` 里已经写过的规则，我没照做、被你指出来了。
   你临时改主意、需求变了、规则里根本没写过的，都不算命中。命中记进 `docs/rule-hits.md`。
4. **固定一行「本轮新增依赖／新增工具位」**：没有就写「无」。
5. **收口**：一版交付时回看那一版的设计文档。规格已不成立、或已被实现推翻的，按「设计偏差」
   单独列出，由我决定改设计还是改实现；**裁定后回写规格**，并注明哪一份是当前有效的。

## 界面改动的验证（浏览器与运行时）

界面改动不能只看类型检查和测试通过就报完成，要看到真实渲染结果。判断按「这次改了什么」
来定，不按对话来定：默认自动执行，不逐次询问。

**自动执行（不问）**

- 改了页面上看得见的东西（组件、样式、界面文案）：起本机开发服务，打开对应页面确认渲染正常。
- 报的是「白屏／点了没反应／显示不对」这类现象：先用浏览器复现，看到现象再改代码。
- 动了核心流程（登录、下单、提交、支付这类）：真实操作一遍。
- 任何界面改动收尾前：读一次运行时错误和编译问题，确认是干净的。

**不执行（不问，也不用）**

- 纯文档、纯内容改动。
- 只改数据层或工具函数，且日常检查能覆盖。
- 类型、构建、代码检查配置类改动。

**停下来找我（只有两种情况）**

1. 要进的页面需要登录态、且没有保存的登录会话——需要我登录一次；不许拿我的账号去操作登录。
2. 操作会写入真实数据（提交表单、删除、确认保存）——先确认再动。

**工具**

- 默认用浏览器工具（本机装了 `agent-browser`：打开页面、看文本、截图、点按）。
- 需要框架层答案（哪个文件渲染了这个路由、为什么没渲染出来、编译有没有问题）时，问框架
  自己的诊断入口（Next.js 有 `/_next/mcp`）。
- 用本机数据模式起服务验证界面，不用云端模式。

## 版本与提交

- 一个版本只做一个子系统；需要同时改数据和界面、或涉及多条链路时，拆成两次发布。
- 一次提交只处理一个清晰目标，提交信息使用 `feat:`、`fix:`、`docs:`、`test:`、
  `chore:`、`release:` 前缀（`release:` 只用于版本发布准备，如升版本号、写 CHANGELOG）。
- 每次提交前确认当前分支和工作区状态。工作目录可能被其他会话切走，提交落到错误分支
  是实际发生过的错误。
- 开新版本前，先确认上一个版本的验收清单已经签完。有未签项就先补验收，不开新功能。
- 多个会话并行开发时用独立工作区隔离（`git worktree` 或第二个目录）；只有串行开发
  才共用同一个目录。
- `main` 分支始终保持可运行，每个阶段完成后记录提交和版本标签。
- 未经确认，不执行 `git reset --hard`、强制推送或删除 Git 历史。
- 改本文件或 `docs/method.md` 时必须说明删掉或合并了哪条规则：规则只增不减，最后没人会读。

## 数据与安全（硬边界，现场可见）

1. 未经明确确认，不删除文件、不删除或覆盖数据、不改动生产库、不执行破坏性 Git 操作。
   生产库的写入先说清改什么、为什么、怎么回滚，我同意后再做，做完登记一条事实记录。
   同意一次一议，只在对话里给，不存在「以后这类都可以」。
2. 未经确认，不引入第三方库、外部服务、远程仓库或部署环境。
3. 只有我主动点击后才把内容发送到 AI 服务；密钥不进入浏览器代码和 Git。
4. 优先修改指定范围，不做无关重构；只有我明确要求时才重写整个文件。
5. 普通实现细节可以自行决定，但要在交付说明里解释。
6. AI 生成、优化、合并的结果**必须先给草稿**，我确认后才写进库，并保留可回退的版本。
   不许静默覆盖我的内容。

## 代码与文案

1. 重要代码块、复杂逻辑和容易误解的地方写中文注释，不给每一行代码加注释。
2. 所有用户可见文案使用中文。
3. 不提交无法运行的代码，不提交带 `TODO` 的占位功能。
