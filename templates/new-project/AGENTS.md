# 项目规则

## 关于用户

用户是产品经理，不直接阅读代码。请通过中文说明、变更清单和验收步骤让用户理解结果。

## 开始工作前

1. 先阅读根目录 `README.md`、`docs/product-brief.md`、路线图和最近的验收文档。
2. 确认当前 Git 分支和工作区状态。
3. 先用自然语言说明准备改什么、为什么改、修改后的用户可见效果，以及影响范围。
4. 涉及产品行为、数据结构、外部依赖、成本或安全性的决定，必须先询问用户。
5. 只有用户明确要求重构时，才可以重写整个文件。

## 工作原则

1. 重要代码块和复杂逻辑写中文注释，不给每一行代码加注释。
2. 未经明确确认，不删除文件，不删除或覆盖用户数据，不执行破坏性 Git 操作。
3. 未经确认，不引入新的第三方依赖、外部服务或部署环境。
4. 优先修改指定范围，不进行无关重构。
5. 普通实现细节可以自行决定，但要在交付说明中解释。
6. 页面和功能必须覆盖正常、空数据、错误、加载和边界状态。
7. 所有用户可见文案使用中文。
8. 不提交带 `TODO` 的产品占位功能。
9. 不提交无法运行的代码。

## 交付规则

每次完成后必须列出：

- 修改了哪些文件。
- 每个文件改了什么。
- 如何预览或验证。
- 已执行的检查结果。
- 未完成事项和已知风险。

## 验收规则

1. 每个功能必须对应可观察、可测试的验收标准。
2. 功能完成后至少验证正常流程和边界情况。
3. 修改后运行代码检查、类型检查、测试和生产构建。
4. 存在用户数据时，必须验证刷新、重新进入和错误恢复流程。

## Git 规则

1. `main` 分支始终保持可运行。
2. 功能开发从 `main` 创建 `feat/` 或 `fix/` 分支。
3. 文档更新使用 `docs/` 分支。
4. 一次提交只处理一个清晰目标。
5. 提交信息使用 `feat:`、`fix:`、`docs:`、`test:`、`chore:` 前缀。
6. 每个稳定阶段合并到 `main` 并创建版本标签。
7. 未经确认，不创建远程仓库、不推送、不部署。
8. 未经确认，不执行 `git reset --hard`、强制推送或删除 Git 历史。
