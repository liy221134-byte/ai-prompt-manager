## 关于我

我是产品经理，不直接阅读代码。所有结论用中文说明，用变更清单和验收步骤让我理解结果。

## 每次开始工作前

1. 先读 `README.md` 和 `docs/` 里的入口文档（入口是哪份，见 `docs/DOCUMENT_SYSTEM.md`）。
2. 涉及代码改动时，先看工程地图类文档定位要改的文件，再精读那几个文件，不要整篇读大文件。
3. **框架自带的规则也要读**（这条只在用 Next.js 的项目里成立，不是通用规则）：写 Next.js
   代码前先读 `node_modules/next/AGENTS.md`。它写明这个版本的 API、约定和目录结构都可能
   和训练数据不一样，要求先读它指向的文档再动手，并留意废弃提示。只引用那份文件，
   不把它的内容抄进来。
4. 动手前先用自然语言说明：准备改什么、为什么改、我会看到什么变化、可能影响哪些文件或功能。

## 开发流程：一个版本、一份文档、三道门

### 需求门

- 需求模糊、涉及新方向或存在多种做法时，先对话确认，不写代码。
- 需求清晰时直接进入设计门。

### 设计门

设计门有**两条并行的线**：技术设计和界面设计。两条都判过（走完或判定不触发），才进交付门。

#### 技术设计线

- 触发条件：满足任意一条时，先写一份《设计 + 任务清单》文档，等我确认后再开发。
  1. 会留下长期痕迹：数据表、字段、迁移、恢复或回滚语义。
  2. 会改变对外约定：接口输入输出、优化与合并规则、鉴权与数据隔离。
  3. 会引入外部依赖、外部服务或持续成本。
- 不触发：界面、文案、样式、局部实现调整，以及已有测试覆盖的重构。这些只需在动手前用
  自然语言说明改什么、为什么改、影响哪些文件、怎么验收。
- 文档只写决定，只保留四块内容：做什么／不做什么；数据和产品行为影响；验收标准
  （每条都能用一次测试或一次手工验证判定）；任务顺序，以及每个任务改哪些文件。
- 不写自检章节和覆盖率对照表——自己证明自己的内容无效。只写决定，不写实现步骤、
  完整 SQL 和成段代码。篇幅以把事情说明白为准：没说清楚比写长更危险。
- 实现和设计不一致时，单独列出「设计偏差」，由我决定改设计还是改实现。

#### 界面设计线

- **先判档，再决定做多少。** 判档依据：这一版有没有新的用户可见界面；前端底座是不是
  已经把布局和组件定死。
  1. **定稿档**：首次定整体风格，或要改整体风格——出设计稿。
  2. **沿用档**：已有风格，这版只加页面或交互——不出稿，按已有风格做，验收只查风格一致性。
  3. **配置档**：界面锁在固定前端底座里（Vben／若依这类中后台模板）——不出稿，
     出「主题与布局配置清单」，只补底座没有的页面。
- 三档都不出稿的例外：改文案、调间距、换图标、单个组件的局部样式——直接改。
- 分寸按「够用」定，不追精致：固定 UI 风格，保证整个产品前端**风格一致**、交互体验顺；
  **把交互说清楚**，做简洁；水平线上拔高留给后面客户提定制化视觉需求时再做。
- 验收：定稿档按设计稿对比验收；沿用档和配置档查风格一致性。都先对齐视口与状态再比，
  别把缩放差异报成设计不一致。
- 技术选型时如果选了会锁死界面的底座，写进技术档案：**接受界面设计自由度受限**，
  设计工序走配置档。
- 这条线和上面那条**并行**，不是串行：不必等技术设计定稿才开始设计，也不必等稿子
  画完才动手写代码。

### 交付门

1. 先写或更新测试，再写实现；验证失败时先用测试复现问题。
2. 按档位运行检查，把真实结果告诉我，不能只说「应该没问题」：
   - 日常任务：`{{日常检查命令，例如 npm run check:fast}}`
   - 合并或推送前：`{{完整检查命令，例如 npm run check}}`
   - 纯文档、纯内容改动可以只跑测试，但要说明实际跑了什么。
3. 做一轮独立自查，发现的问题直接修进当前任务的提交里，不额外制造 fix 提交。
4. 交付说明包含：改了哪些文件、每个文件改了什么、如何预览或验证、未完成事项和风险。
5. 证据只记一处：同一次发现只写进验收清单或决策记录中的一处，其他文档放链接引用，
   不重复叙述。
6. 交付说明里固定一行「本次规则命中」：没有就写「无」，有就写清违反了哪条、发生了什么。
   命中只有一种口径——`AGENTS.md` 里已经写过的规则，我没照做、被你指出来了。临时改主意、
   需求变了、规则里根本没写过的，都不算命中。

## 界面改动的验证（浏览器与运行时）

界面改动不能只看类型检查和测试通过就报完成，要看到真实渲染结果。判断按「这次改了什么」
来定，不按对话来定：默认自动执行，不逐次询问。

- **自动执行（不问）**：改了页面上看得见的东西（组件、样式、界面文案）→ 起本机开发服务，
  打开对应页面确认渲染正常；报的是「白屏／点了没反应／显示不对」这类现象 → 先用浏览器
  复现，看到现象再改代码；动了核心流程（登录、下单、提交、支付这类）→ 真实操作一遍；
  任何界面改动收尾前 → 读一次运行时错误和编译问题，确认是干净的。
- **不执行**：纯文档、纯内容改动；只改数据层或工具函数，且日常检查能覆盖；类型、构建、
  代码检查配置类改动。
- **停下来找我（只有两种情况）**：① 要进的页面需要登录态、且没有保存的登录会话——需要我
  登录一次，不许拿我的账号去操作登录；② 操作会写入真实数据（提交表单、删除、确认保存）——
  先确认再动。
- **工具**：默认用浏览器工具（本机装了 `agent-browser`：打开页面、看文本、截图、点按）。
  需要框架层答案（哪个文件渲染了这个路由、为什么没渲染出来、编译有没有问题）时，问框架
  自己的诊断入口（Next.js 有 `/_next/mcp`）。用本机数据模式起服务验证界面，不用云端模式。

## 写代码的规矩（防过度设计）

AI 默认会多写：加抽象、装依赖、顺手重构。动手写代码前，按顺序停在第一个成立的台阶上：

1. 这件事需要做吗？不需要就不做。
2. 项目里已经有能复用的实现吗？有就复用，不重写。
3. 标准库、框架自带的能做吗？能就用。
4. 平台原生能力能做吗（例如浏览器自带的日期选择）？能用就用。
5. 已经装过的依赖能做吗？能做就用。
6. 能一行写完吗？一行写完。
7. 以上都不成立，才写满足需求的最小实现。

梯子是在看懂问题和整条链路之后才爬，不能用「简化」的名义跳过理解。

- 不加没人要的抽象、脚手架和依赖。
- 修 bug 按四步走：**先复现**（写清操作步骤、数据、报错原文；复现不了就先加观测，
  不改业务逻辑）→ **定位根因**（先搜这个函数的全部调用方，改共享函数一次，
  不只补报告里提到的那条路径；结论要能解释「为什么之前会那样」）→ **最小修复**
  （只改根因那一处，顺手重构另开一次）→ **回归**（补一条能挡住同类问题的检查，
  再按交付门跑一次检查）。
- 简化不许砍掉：校验、错误处理、安全、无障碍、防数据丢失和真实边界条件。
- 有意留下的简化，要在代码里注明它的上限和以后怎么升级。
- 非平凡逻辑留下一个能运行的检查；一行小改不强制写测试。
- 做完主动说明「这次省掉了什么」，不默默省。

两条边界优先于上面的规矩：

1. 设计门不变。涉及数据表、对外接口、新依赖时，仍然先写设计文档等我确认，
   「先做最简版再问」不适用。
2. 删除规矩不变。删文件、删数据、删功能仍要先得到我的确认；「简化优先」只限本次任务
   自己新增或直接改动的代码。

## 技能使用规则

### 默认使用

- 需求模糊时：先把上下文和约束问清楚，再动手。
- 涉及逻辑、数据或接口时：先给出验收标准或测试。
- 交付前：实际验证一遍再报完成。

### 默认不使用

- 写计划／执行计划类技能：由《设计 + 任务清单》替代。
- 并行子代理：个人项目默认不启用，除非我明确要求。
- 独立工作区（worktree）：串行开发时，**新功能**在项目目录内建功能分支；**修 bug
  不用单开分支**，直接在主分支上用 `fix:` 提交。多个会话并行时必须用独立工作区隔离，
  否则会出现提交落到别人分支上的情况。
- 合并前评审类技能：合并为交付门里的那一轮自查。

### 使用边界

- 只读取本次真正要用到的技能说明，不批量加载技能文件。
- 技能文档与这份文件冲突时，按这份文件执行，并在交付说明里指出冲突点。

## 版本与提交

- 一个版本只做一个子系统；需要同时改数据和界面、或涉及多条链路时，拆成两次发布。
- 一次提交只处理一个清晰目标，提交信息使用 `feat:`、`fix:`、`docs:`、`test:`、
  `chore:` 前缀。
- 每次提交前确认当前分支和工作区状态。工作目录可能被其他会话切走，提交落到错误分支
  是实际发生过的错误。
- 开新版本前，先确认上一个版本的验收清单已经签完。有未签项就先补验收，不开新功能。
- 多个会话并行开发时用独立工作区隔离（`git worktree` 或第二个目录）；只有串行开发
  才共用同一个目录。
- `main` 分支始终保持可运行，每个阶段完成后记录提交和版本标签。
- 未经确认，不执行 `git reset --hard`、强制推送或删除 Git 历史。
- 改这份文件时必须说明删掉或合并了哪条规则：规则只增不减，最后没人会读。

## 数据与安全

1. 未经明确确认，不删除文件、不删除或覆盖数据、不改动生产库、不执行破坏性 Git 操作。
   生产库的写入先说清改什么、为什么、怎么回滚，我同意后再做，做完登记一条事实记录。
   同意一次一议，只在对话里给，不存在「以后这类都可以」。
2. 未经确认，不引入第三方库、外部服务、远程仓库或部署环境。
3. 只有我主动点击后才把内容发送到 AI 服务；密钥不进入浏览器代码和 Git。
4. 优先修改指定范围，不做无关重构；只有我明确要求时才重写整个文件。
5. 普通实现细节可以自行决定，但要在交付说明里解释。

## 代码与文案

1. 重要代码块、复杂逻辑和容易误解的地方写中文注释，不给每一行代码加注释。
2. 所有用户可见文案使用中文。
3. 不提交无法运行的代码，不提交带 `TODO` 的占位功能。
