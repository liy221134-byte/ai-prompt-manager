# 实现规格（Spec）

> 用途：动代码之前先写这一页，让 AI 用自然语言把「这次具体怎么改」讲清楚，你确认之后才动手。
> 项目：`{{项目名称}}`
>
> **为什么需要它**：你不读代码，Spec 是唯一能在代码产生之前拦住 AI 的闸门。
> 尤其涉及数据结构变更时，「怎么变、对老数据什么影响」不先写清，迁移跑完就晚了。
>
> **和 PRD 的分工**：PRD 讲为什么做、做什么、成功标准（你拍板）；
> 这一页讲这次具体怎么改：改哪里、数据怎么动、边界在哪（AI 起草，你确认）。
>
> **用哪一档**：小功能只填第一部分；大版本连第二部分一起填。

## 一、小功能档（低风险改动：文案、样式、局部逻辑）

- 这次要改什么（一句话）：
- 动哪几个文件或页面：
- 动不动数据：动／不动（动了就写清改哪张表、哪个字段、老数据怎么办）
- 怎么验（一条能手工做一遍的步骤）：
- 不做范围（这次明确不碰什么）：
- 出问题怎么退回：

## 二、大版本档（涉及数据结构、接口约定、多条链路）

### 1. 需求追溯

| 项 | 内容 |
| --- | --- |
| 对应需求 | 哪份 PRD／需求编号 |
| 成功标准 | 满足什么算做完 |
| 不做什么 | 这次明确排除的范围 |

### 2. 现状

- 现在是怎么做的（读起来麻烦的地方在哪）：
- 涉及哪些文件、表、接口：

### 3. 方案

- 这次改成什么样（用自然语言描述，不贴整段代码）：
- 为什么选这个做法（还有哪些被排除的选项，为什么不选）：

### 4. 数据结构与迁移

| 项 | 内容 |
| --- | --- |
| 表／字段变化 | 新增、修改还是删除 |
| 对老数据的影响 | 已有数据会怎样，需要回填吗 |
| 迁移怎么执行 | 顺序、谁执行、执行前要备份什么 |
| 回滚方式 | 出问题怎么退回去，退回去数据会不会丢 |

### 5. 接口与状态

- 输入输出有没有变（字段、含义、错误码）：
- 状态怎么流转（草稿／待确认／生效…）：

### 6. 边界与错误

- 空数据、超长、重复、并发各自怎么处理：
- 明确不处理的边界（以及为什么可以不处理）：

### 7. 验收映射

| 验收条件 | 怎么验 | 对应验收记录 |
| --- | --- | --- |
|  |  |  |

### 8. 风险与回滚

- 风险（最坏会怎样，怎么提前发现）：
- 回滚目标和步骤：
- 上线后要盯什么、盯多久：

## 三、确认

- 起草人（AI 还是人）：起草时间：
- 确认人：确认时间：
- 确认结论：可以做／改完再做（写清还要改什么）

## 四、维护约定

- 每次动代码之前先填第一部分；涉及数据或接口的填第二部分。
- 实现和这一页不一致时，先改这一页再改代码，别让文档追着代码跑。
- 做完把实际结果和偏差记一行在最后，作为下次估算的依据。
- 这一页的更新触发条件：需求变了、数据结构变了、接口约定变了。
